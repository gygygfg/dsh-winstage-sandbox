# 沙箱审计：两种"记录 AI 读了/改了什么"的方式实测对比

日期：2026-10-08
目标：AI 在 Windows 沙箱里的**文件读取/修改**与**注册表读取/修改**，要能被记录、汇总成一个位置，
并返回沙箱外程序（用于分类统计、呈现、决定是否覆盖到宿主机）。

本文件对两种候选实现各做了一个**真实端到端**实验（ebk win10 VM，能跑通、能取回产物），给出对比与建议。

- **方案 A —— 进程内 API 记录件（C shim + 注入）**：在被注入进程及其子进程里钩住
  `CreateFileW`/`DeleteFileW`/`MoveFileExW`/`Reg*` 等，逐操作写结构化审计（`WINSTAGE_AUDIT_LOG`，JSONL）。
  代码：`shim/src/ws_util.c`（`ws_audit`）、`ws_file.c`、`ws_reg.c`；聚合：`tools/sandbox-audit.mjs`。
- **方案 B —— 命令/效果记录件（C 快照 diff，不注入）**：把操作都当 shell 命令，在一个
  **镜像根**里执行；记录件在命令前后快照该根并 diff，得出"进程及其子进程改了什么"。
  代码：`shim/audit/winstage-rec.c`。

---

## 1. 实验一：方案 A（shim 进程内记录件）

工作负载 `tools/demo-agent.cmd` 在**被注入的 cmd** 里执行：读写/删除文件 + 读写注册表。
shim 用 `WINSTAGE_AUDIT_LOG` 落审计，聚合器输出 `sandbox-audit.json`。`[实测]`：

```
sandbox-audit: files read=2 written=3 deleted=0 moved=0; registry read=13 written=3
(lines=47 parsed=47 malformed=0)
```

要点：
- **读**也捕获（`C:\Windows\win.ini`、`agent-work\a.txt`、以及 cmd 自身反复读的 `workload.cmd`）；
- **写**捕获（`agent-work\a.txt`、`seed.txt`）；
- **注册表**读写捕获（`HKCU\Software\WSTest#K/K2` 等）；
- 覆盖的是**整个进程树**（cmd 及其 `reg.exe` 子进程），无需改动被观测程序；
- 噪音：cmd 自身的系统读取（`HKLM\...\Command Processor`）、`nul` 重定向等也在里面，需要按根过滤；
- **`deleted=0` 是漏的**：同一个 workload 里的 `del seed.txt` 没进审计 —— 因为 cmd 的 `del`
  先做存在性判断，而它用的是与 `GetFileAttributesW` **不同**的 API，看不到只存在于 overlay 的
  暂存文件（这是仓库已记录的残余边界），于是根本没调用 `DeleteFileW`。
- 同一原因，`type seed.txt`、`reg query` 读回也报了"找不到"（overlay 透明读对 cmd 不完整）。

## 2. 实验二：方案 B（快照 diff，不注入）

`shim/audit/winstage-rec.c` 在镜像根 `C:\ebk\mirror` 里跑同样的命令，命令前后快照并 diff。
`[实测]` 审计全文：

```
{"op":"file.create","method":"snapshot","path":"a.txt"}
{"op":"file.create","method":"snapshot","path":"b.txt"}
{"op":"file.delete","method":"snapshot","path":"seed.txt"}
{"op":"run","method":"snapshot","cmd":"cmd /c echo hello > a.txt & type seed.txt & copy ... & del seed.txt & type C:\\Windows\\win.ini >nul & reg add ...","exit":0}
```

要点：
- **写/建/删**捕获，且**语义正确**：镜像是真实文件，cmd 的 `type`/`del`/`copy` 全部成功，
  `del seed.txt` 也被如实记为 delete（方案 A 反而漏了它）；
- **看不到"读"**：快照只能看**效果**，看不到"读了但没改"的文件（`win.ini`、`seed.txt` 读取均未记录）；
- **看不到根外与注册表**：`reg add/query/delete` 未记录，且它**写入的是真实 HKCU**（未重定向）；
- 零注入：不需要 DLL、不需要注入器 → 没有签名/Defender 负担、不会因注入破坏载体。

---

## 3. 对比

| 维度 | A：进程内 API 记录件（shim，注入） | B：命令/效果记录件（快照 diff，不注入） |
|---|---|---|
| 记录"读" | ✅（含未改动的读取） | ❌ 结构上看不到 |
| 记录"改/删" | ✅，但受 overlay 语义影响（本例 `del` 漏） | ✅（镜像里是真实文件，语义干净） |
| 根外绝对路径写入 | ✅ 透明捕获 | ❌ 不可见 |
| 注册表 | ✅（hook 的 Reg*）读写都捕获 | ❌ 除非另行重定向/导出 diff |
| 覆盖子进程 | ✅ 进程树 | ✅ 只要写在镜像根内 |
| 是否需要注入/未签名二进制 | **需要**（→ 签名 / P0-1 Defender） | **不需要** |
| 对被观测程序的破坏面 | 有（hook 透明性有残余，如 cmd 的 `del`/`type`） | 无（不碰进程） |
| 噪音 | 高（系统自身读写混入） | 低（只列净变化） |
| 语义保真（shell 工具读写回） | 受 overlay 限制 | 好（镜像=真实文件） |
| 性能 | 每次操作一次日志写 | 命令前后各一次全树哈希 |

## 4. 结论与建议

- **没有单一赢家**：A 保真在"覆盖任意子进程 + 读到读操作 + 覆盖注册表"，代价是注入/签名/Defender
  与 overlay 的透明性残余；B 干净、零注入、对 shell 工具语义最好，但**看不到读、看不到根外、看不到注册表**。
- 对"AI 读了/改了什么"这个**精确审计**目标，**A 是唯一能记录"读"的方式**；B 天生只能记录"效果"。
- 对"统一走 shell 命令"的目标，**B 更简单且更稳**（不需要注入），但必须接受"只能看到镜像根内的净变化"。
- **推荐组合**：
  1. 先把 AI 的修改面收敛到**镜像根 + 注册表工具**，用 B 做文件净变化（干净、零注入）；
  2. 需要"读行为"或"根外写入/注册表透明捕获"时，对**该命令**按需开 A（注入 + `WINSTAGE_AUDIT_LOG`）；
  3. 两者产出的都是同一种 JSONL/`sandbox-audit.json`，聚合器与呈现面**共用一套**（`tools/sandbox-audit.mjs`）。

> 证据（VM 现场日志）：`ebk-sandbox-audit.json`（A）、`ebk-rec-audit.jsonl`（B）、`ebk-audit.jsonl`（A 原始）。
> 两种方式都验证了"沙箱里跑 → 记录 → 汇总 → 写回共享目录 → 沙箱外程序读取"这条返回通道。

---

## 5. 定案：Method A 为主线（本次落地）

按"要精确统计读了什么、覆盖任意子进程与注册表"的需求，**选 A**。已落地：

1. **执行器自动开启审计**（`src/executor.mjs`，transparent launcher）：
   - 自动设 `WINSTAGE_AUDIT_LOG=<audit>`，写**整个进程树**的文件/注册表操作；
   - 审计文件**落在暂存树之外**（优先会话存储根 `registryStageDir`，否则与暂存根互斥的私有 temp）——
     `shim.log`/`overlay.hive` 的教训：暂存层自己的状态文件若在 `<stagingRoot>` 内会被
     `captureAfterExecution` 当成用户改动摄取（自指条目）；
   - `options.audit === false` 显式关闭；路径经 `executor.auditPath` 暴露给调用方做聚合。
2. **聚合器作为读侧权威**（`tools/sandbox-audit.mjs`）：
   - 导出纯函数 `aggregateAudit(lines, { root })`（可离线单测）；
   - `--root <工作区根>` 给每个文件条目打 `scope: workspace|outside`，summary 增加
     `filesWrittenInWorkspace/filesWrittenOutside/filesDeletedInWorkspace`，
     把"AI 的改动"与"系统/沙箱自身噪音"分开；
   - 非法行不静默忽略（计入 `malformed` 并留样本）。
3. **离线守门套件**（`tests/sandbox-audit.mjs`）：10 断言，已登记进
   `OFFLINE_SUITES`（`src/testrunner.mjs`）与 `verify.cmd`，两清单逐字一致
   （`tests/suite-wiring.mjs` 机器检查）。
4. 返回产物统一为 **`sandbox-audit.json`**：`files.read/written/deleted/moved` +
   `registry.read/written` + `summary`，供沙箱外程序分类统计、呈现、决定是否覆盖宿主。
