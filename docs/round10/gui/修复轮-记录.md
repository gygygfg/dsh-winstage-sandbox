## 1. 修复①（阻塞级 · D2）面板展开时 composer 被移出 DOM → **已修并实测**

### 做了什么

`client.js` 新增常量 `COMPOSER_FALLBACK_UNHIDE_CSS`，并在 `apply(ctx)` 里用 `ctx.effect` 注入一条样式（卸载即撤）：

```css
[data-chain-overlay-fallback="conversation.composer"]{display:block !important;}
```

### 为什么换方案（Lead 要求写清"为什么" + 实测反证）

| 候选方案 | 实测结论 |
|---|---|
| **Lead 首选：改挂 `conversation.input.dock`（list 槽位）** | **实测不可行**。该槽位 ownerProps **只有 `zone`、没有 `sessionId`**（渲染点 `dsh-client-ui-conversation/lib/client.js:16309` `renderSlot("conversation.input.dock", zone)`；对比 chain 的 ownerProps 是 `{ sessionId, session, pendingInteraction }`）。本面板全部动作（`executeCommand(matched.sessionId, …)`、`poller.observe(matched.owner)`）都依赖 sessionId ⇒ 改挂后**面板与 chip 一起消失**（实测 `panelMounted=false` 且 `chipMounted=false`） |
| **用 `fallback` prop 把输入条渲染回来** | **本机不可依赖**。`renderChainResult()`（`ui-renderer/lib/client.js:1198-1206`）确实把 `fallback` 放进传给条目的对象（`:1163-1172`），但本机安装的构建里组件收到的 `fallback` 恒为 `undefined`（实测：加了 `data-winstage-review-split` 锚点后**从未挂载**） |
| **兜底方案（面板自滚动 + 文案提示"收起后可继续对话"）** | **不需要**。因为输入条**从未被卸载** —— 平台把它保留在 `<div data-chain-overlay-fallback="conversation.composer" style="display:none">` 里，只是被隐藏 |
| **✅ 实际采用：覆盖那条 `display:none`** | 一条属性级 `!important` 规则（行内样式只能被 `!important` 覆盖），作用域严格限定在该属性，不碰平台布局。**版本无关**：不依赖 prop 透传、不依赖槽位形状 |

## 2. 修复②（头条级 · D3/D4）降级不可见 + 误导文案 → **已修并实测（含一处新发现的二次误导）**

### 做了什么（两处，第二处是实测过程中发现并一并修的）

**（a）头条改由"实测/已证事实"驱动**（`trustLine()`）：

- "根真的用不了（写入会失败）"**只在写账本证明时**成立 —— 判据由 `writes.count > 0 || (stageRoot.checked && alive === false)` **收紧为 `writes.count > 0`**。
  **为什么收紧**：实测发现 `stageRoot.alive === false` **本身就是误报源**。本会话把暂存根钉在缓存基之外（`WINSTAGE_STAGE_ROOT`）⇒ 没有 keeper/哨兵 ⇒ 活体查询**恒**答 `alive:false, reason:"marker-missing"`，而同一时刻写文件工具的候选**正常生成**。把"探针答不活"当成"写入会失败"正是原缺陷的根。
- 判据不足时**不许断言**，改为自述判据不足（新文案 `trustBaseUnverifiable`）+ 单列一行 `data-winstage-trust-basis-notice`。
- 降档（`tier.degraded`）成立时**优先**报降档，并给**可操作**提示（`trustDegradedAction`：跑 `/winstage status`；注入器被隔离则把 `shim\out\winstage-inject.exe` 加白名单后重启宿主）。
- `失根` 计数降级为一句可读说明（`trustLossNoise`："这是探测计数，不是写入失败次数，且每次查询都会 +1"），不再当头条。
- 详情行新增**判据自述**：`判据：宿主 level=… · tierEffective=… · degraded=…` ⇒ 以后"面板为什么这么判"可直接从截图读出。

**（b）新发现的二次误导（如实记，已一并改为不断言）**：面板拿到的那份卡片里 **`tier` 字段为空**（`tierEffective=?`、`degraded=no`），而**宿主路由** `GET /winstage-panel/trust` 返回的同一份卡是 `tier.status="degraded"`、`tierEffective="T1"` ⇒ 两者**不同源**（`client.js` 的 `readTrustCard` 取 `result.card ?? result`）。修复前因此出现第三种坏组合：面板既不知道降档、又拿着宿主的 `level:"lost"`，于是继续喊"写入会失败"。现在该组合走 `trustBaseUnverifiable`（不断言）。这一条**已记为新缺陷 `defects.md` §D11**（需 host 侧修）。

### 6.1 D11：面板信任卡与宿主 `/winstage-panel/trust` 同源（客户端侧能做到的那一半）

**查到的事实链**（源码追溯，无需运行）：

| 环节 | 位置 | 事实 |
|---|---|---|
| 路由入口 | `host-plugin.mjs:809` `buildPanelPayload({pathname, query, …})` | `const sid = read('session')` —— session **只从 query 取** |
| 目录解析 | `host-plugin.mjs:823` `readPublishedSnapshot({ workspaceRoot, sessionId: sid, env })` → `panelStoreDir()`（`:780`）→ `resolveReviewStoreDir()`（`review-service.mjs:180`） | `resolveReviewStoreDir` 优先用显式 `storeDir`，否则 `resolveStageRoot({sessionKey: sessionDirKey(sessionId) \|\| DEFAULT_REVIEW_SESSION_ID, workspaceRoot, env, override: stageRoot})` ⇒ **目录取决于 query 里的 session** |
| tier 来源 | `buildTrustCard({service: undefined, storeDir: published.dir, session, snapshot, now})`（`:832-842`）→ `readLaneJournalFile(dir)`（`host-plugin.mjs:458`） | **`tier` 有没有内容，完全等于 `published.dir` 里有没有 `sandbox-lane.json`** |
| 客户端取值 | `client.js` `readTrustCard()` → `fetchPanelRoute(PANEL_TRUST_ROUTE, sessionId)` | 面板发 `?session=<本会话 id>`；**不带 session 的调用会解析出另一个目录** ⇒ 两侧可能一个目录里有 lane、另一个没有 |

⇒ 面板侧那个"`tier` 为空"是**可复现的目录解析差异**，不是随机现象；但**正解在 host 侧**（两者必须解析到同一目录），不在本文件的写范围内。

**客户端侧已实现的修法**（`client.js::readTrustCard`）：
1. 先按 `?session=<id>` 取一次；2. **仅当**该卡没有"真的档位证据"（`tier.status`/`tierEffective`/`launchMode` 都缺失且 `degraded !== true`）时，才补打一次**不带 session** 的请求；3. 优先采用带证据的那份；4. 把胜负写进 `card.tierSource`（`scoped`/`unscoped`）与 `card.tierAlternate`，并在面板详情行显示 `卡来源=scoped(scoped=empty/unscoped=tier)`。
   - **副作用声明**：`/trust` 每次调用都会走 `noteStageRootLoss()`（`host-plugin.mjs:516-531`）⇒ 会推进 `失根` 计数。因此**只在需要时**多打一次；两次都正常时不重复打。

**待验证判据（窗口后取）**：
- **同源判据**：同一时刻，面板详情行 `卡来源=scoped(scoped=tier/n-a)` 且 `tierEffective` **非 `?`** ⇒ 面板卡与宿主路由**同源**（`tier` 相等，逐字段可比）。
- 若显示 `scoped=empty/unscoped=tier` ⇒ 客户端兜底生效、**host 侧目录解析仍是缺陷**（D11 只算"缓解"，不算"已修"）。
- 若两者都 `empty` ⇒ 兜底无效，必须 host 侧修。
