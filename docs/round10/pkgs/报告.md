## 2. 沙箱内可写面（本轮的关键机制发现，先讲清才能读懂后面）

在 WinStage 沙箱线程里，**真实盘的写不是"被 ACL 硬拒"，而是被 shim 重定向进暂存树**：

| 目标路径 | 现象（原始输出） | 真实盘 |
|---|---|---|
| `C:\wt\...`、`C:\Users\...\AppData\Roaming\pip\pip.ini`、`C:\Users\...\AppData\Roaming\Python\...` | 写入返回成功，内容出现在 `<stageRoot>\staged\fs\C\...` | **不存在** |
| `.t\round10\pkgs\ws\...`（真实工作区） | `Access to the path ... is denied.`（run-1） | 不写 |
| `C:\Users\...\AppData\Local\Temp\dsh-stage-temp\<uuid>\...`（会话私有 temp） | 可写；部分被捕获进暂存 | 不写 |
| `C:\Windows\Temp\...` | `BASE fallback` 分支：`mkdir` 探测失败 → 不可用 | 不写 |

`run-9` 原始日志（`runlog5.txt`）：

```
BASE fallback -> C:\wt\pkgs10x (windows-temp unusable)
at=... BASE=C:\wt\pkgs10x realparent=false dirs=false,false,false,false,false
```

**⇒ `C:\wt` 是一个"写得到、但 `exists` 为假"的虚拟根。** 这解释了后面所有 npm 失败：
npm/distlib 这类工具在写入前先做 `mkdir`/`stat`/`os.rename`，而它对虚拟路径的判断为"不存在"。

### 5.2 npm 局部安装：**❌ 在沙箱内不成立（阻断级）**

四次尝试、四种目标，全部倒在同一个错误上：

| run | 命令形态 | 结果（原始） |
|---|---|---|
| run-5 | `npm.cmd install …`（经 spawn） | `spawnSync npm.cmd EINVAL`（Node ≥20 对 `.cmd` 的加固，见 D-P4） |
| run-6 | `node npm-cli.js install … --prefix C:\wt\proj`，`cwd=C:\wt\proj` | `spawnSync … ENOENT`（`cwd` 在虚拟根上不可解析） |
| run-7 | `node npm-cli.js install … --prefix C:\wt\proj3`（无 cwd） | `npm error ENOENT mkdir 'C:\wt\proj3'` |
| run-9 | `--prefix C:\wt\pkgs10x\np`，另试 `C:\Windows\Temp` 基 | `mkdir 'C:\wt\pkgs10x\np'` ENOENT；`C:\Windows\Temp` 直接不可用 |

`node_modules=false lock=false`，`npm ls` → `npm error ENOENT syscall lstat path C:\wt`。

**根因**：`C:\wt` 是 shim 的虚拟可写根（`exists=false` 但写得到），npm 自己的 `mkdir`
在"父链不存在"时直接 ENOENT；而真实存在且可写的父目录（工作区）又被 shim 拒绝写。
⇒ **本轮沙箱配置下，node 包无法装到任何位置。**

> 这与"镜像不可用"无关：同一次 run 里 npm 已经成功 `GET 200 https://registry.npmmirror.com/cowsay`。
> 也**不是**平台 `SandboxedFileSystem` 的那种 EPERM——后者上一轮反而能装（`added 2 packages`）。

### 5.3 npm 完整性：**not-run（被 §5.2 阻断）** + 宿主侧对照

沙箱内没有 `package-lock.json`，因此 `npm ls --json problems=[]`、lock `integrity` 反解、
node 冒烟、tree digest **全部 `not-run`**（诚实标注）。

作为**方法对照**（不是沙箱结论），宿主未受限侧用同一套脚本跑同一组包
（`evidence/host-rehearsal-phase0/`）：

| 项 | 值 |
|---|---|
| 命令 / 结果 | `npm install lodash@4.17.21 left-pad@1.3.0 --loglevel http` → exit 0，12,496 ms |
| 域名 | 仅 `registry.npmmirror.com` + `cdn.npmmirror.com`；`hasOfficialNpmjs=false` |
| 四段哈希链 | lock `integrity` == registry `dist.integrity` == cacache index == `content-v2` 重算 sha512（`ALL_FOUR_B64_IDENTICAL=true`） |
| `npm ls --json` | `problems` 字段缺失 ⇒ 归一化后 `problemsIsEmpty=true`，2 依赖 |
| 冒烟 | `lodash.chunk([1,2,3,4],2)=[[1,2],[3,4]]`、`leftPad("x",3)="  x"`、`4.17.21` / `1.3.0` |

两个本轮查清的工具事实：
1. npm 的 packument 与 tarball **域名不同**（`registry.npmmirror.com` → `cdn.npmmirror.com`），
   cacache key 用**实际下载 URL** ⇒ 用 lock 的 `resolved` 直接寻址会 ENOENT，必须按 basename+integrity 回退匹配。
2. `npm ls --json` 在**无问题时根本不输出 `problems` 字段** ⇒ 判 `problems=[]` 前必须 `?? []` 归一化。
