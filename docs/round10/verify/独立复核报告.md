## 2. 被推翻（详细依据）

### R1 env 配方 §0 的三判据**无法判假**（假绿）

配方 §0 原文：「**判定"沙箱真的生效"的最小机器判据（三条同时成立）**：① `stderr.txt` 为空；② `stage-root-inventory.txt` 里出现 `staged\<文件>` 且 `candidates\*.json` 存在；③ `workspace-inventory.txt` 里只有种子文件。」

**我的构造**：把 `WINSTAGE_SHIM_INJECTOR` 指向一个**不存在的路径**（等价于 Defender 隔离后的 artifact-missing），其余不变，跑 `sbx-thread.cmd`（mode=`winstage`）。

**结果**（`docs/round10/verify/evidence/threads/run-n1-falsify/`）：

| 判据 | 预测 | 实测 | 结论 |
|---|---|---|---|
| ① `stderr.txt` 为空 | 应报红 | **0 字节** | **假绿** |
| ② `staged\<文件>` + `candidates\*.json` | 应报红 | `staged\v-inside.txt`(10 B) + `candidates\cs_0001_81c527a7.json` 均在 | **假绿** |
| ③ 真实 ws 只有种子 | — | `files=1`（仅 `seed.txt`） | 绿（此项确实成立） |

同一次 run 的 `sandbox-lane.json`（唯一显形处）：
```json
{"launchMode":"restricted-token","tierEffective":"T1","degraded":true,
 "fallbackClass":"artifact-missing",
 "fallbackReason":"transparent shim unavailable (not found: …\\missing\\winstage-inject.exe) — fail-closed fallback to the restricted-token mode",
 "history":{"shimCount":0,"degradeCount":6}}
```

**为什么重要**：三判据全绿时，命令面已从"垫片透明拦截（可暂存/可审批）"变成"受限令牌硬拒"——同一句话"沙箱已生效"覆盖了两种完全不同的语义。**修复建议（1 行）**：把配方 §0 改为四判据，第 4 条 = `sandbox-lane.json` 的 `degraded === false && tierEffective === 'TS'`（或调用方等价的显式读数）。这也与域三 `D-EXE-3`、域七 `defects §D4` 相互印证。

### R2 network §4「外部 `.exe` 一律 `ENOENT`」不成立（普遍化过头）

network 报告 §4 结论原文：「⇒ `ENOENT` 不是"文件不存在"，而是**沙箱会话里对外部 exe 的进程创建/解析被改变**」。

**我的反例（全部 TS 档，`sbx-run`/`probe` 原始读数）**：

| 外部 exe | 调用者 | 结果 |
|---|---|---|
| `7zr.exe`（绝对路径，dl 目录） | node `spawnSync` | `exit=0`（T1 档）/ `0xC0000005`（TS 档，另一问题） |
| `7z2604-x64.exe`（绝对路径） | node `spawnSync` | **`exit=0`，并完成安装**（域三 run-3） |
| `tasklist.exe` / `sc.exe` / `schtasks.exe`（`C:\Windows\System32\…`） | node `spawnSync` | **全部 `exit=0`**（域三 run-3 surface） |
| `cmd.exe`（PATH 解析） | node `spawnSync` | `exit=0`，写出 `reg add` 的成功输出 |
| `cmd.exe /c …` | **PowerShell** | `exit=0` + "The operation completed successfully."（域我 n2） |
| `node.exe` | node `spawnSync` | `exit=0` |

⇒ 至少 6 类外部 exe 在 TS 档下**能**被创建；他们的 `curl.exe ENOENT` 可能是该二进制/该次会话的个别现象。**结论修正建议**：把"一律"改为"已观测到 `curl.exe` 的 `ENOENT`（成因未定）"，否则会把复核者引向"沙箱禁用一切外部进程"的错误模型（与域三的 `requireAdministrator`/`0xC0000005` 现象混淆）。

### 8.3 判定：**是回归**

- 单变量对照成立：同一驱动、同一目标、同一机器，**只有 DLL 不同**（`shim.log` 的 `self=` 分别指向备份 DLL 与 `shim\out`）。
- 旧 DLL：越界写被重定向进暂存，宿主真实盘**零痕迹**；新 DLL：同一路径**直接落宿主真实盘**，且**不进暂存、不进审计**。
- 因此这不是"既有缺口的独立复现"：既有缺口（`LdrLoadDll` 路径本身）在旧 DLL 上被"后续任意一次 LoadLibrary 触发的全量重扫"**顺带覆盖**；D-SHIM-1 恰好移除了这层顺带覆盖。

### 8.4 严重性：**静默**比"未覆盖"更糟 + 加固建议

本轮最严重的不是"允许写"，而是**写得无声**：
- **无候选**：`review.json` 里没有该项（不会出现在审批面板，用户没有任何批准机会）。
- **无审计**：新 DLL 的 run 里 `audit.jsonl` 对 `…-c-ldr.txt` **0 条**记录（同一 run 的 `ll-only` 目标有记录）⇒ 事后取证的唯一线索是"宿主真实盘上多了个文件"。
- 对比：`ll-only` 在**新旧 DLL 下都是绿的**（镜像 + 审计 + 宿主无文件）⇒ 只跑正向路径会把这次回归读成"修复成功"。

**建议加固（按优先级）**：①（正解）保留"只补刚加载模块"的快路径，但在每个 LoadLibrary 钩子里做**增量收敛**：维护已打补丁模块基址集合，只补集合外的新模块（O(新增)，不重复重扫 ⇒ 有望同时保住 `carrier-flake 28/100→0/100` 与顺带覆盖）；②（立即缓解）回滚 DLL —— Lead 已执行；③（兜底）把 `LdrLoadDll` 载入的模块显式视为**未覆盖**，并对其中发起的文件写 **fail-closed 或至少告警**（当前 `failClosed=1` 只对"暂存写失败"生效，管不到"根本没进钩子"的写）；④ 若长期不修，必须把"TS 覆盖只对经 LoadLibraryW/A/ExW/ExA 载入的模块成立"写进残余边界，并对不可信载体默认 T1。

### 8.6 方法论（Lead 要求写入）

> **修复必须用单变量 + 宿主真实盘判据在反向路径上复测；只测正向路径会把隔离回归读成成功。**

展开：本次正向路径（`LoadLibraryW` 载入 ⇒ 钩子必然看到）在新旧 DLL 下**表现完全一致且都是"正确"的**——镜像有、审计有、宿主无文件。若复核只覆盖正向路径，会得到"修复成功、无回归"的结论。回归只在**反向路径**（不经 LoadLibrary 的加载方式）暴露，且只有**宿主真实盘**这个判据能把它与"被暂存"区分开（`hrOutside=0`、进程内视图、`sandbox-audit.json` 都可能给出误导读数）。
