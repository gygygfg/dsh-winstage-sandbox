## 1. D1：工作区外写的回执语义

### 1.1 先测"上界"：回执里加键**到不了模型**（实测读码，决定性）

`write` 工具的模型可见面**不是**插件能决定的。逐层实测：

1. **输出 schema 是封闭的**（`@deepseek-ai/dsh-tool-fs/lib/index.js`，`applyWriteTool`）：
   ```js
   output: { schema: { type:"object", additionalProperties:false,
     properties: { path:{...}, operation:{enum:["create","update"]}, before:{...}, after:{...} } } }
   ```
   ⇒ 插件在返回对象上**增任何键都会被 schema 丢掉**。
2. **渲染器只认 `operation`**（同一文件 `formatWriteOutput`）：
   ```js
   `${outcome.operation === "create" ? "Created" : "Updated"} file`
   ```
   ⇒ 模型看到的那句话只有 Created/Updated 两态，**没有第三个位置**放"待审批/未落盘"。
3. 与本轮 C1 证据一致：run-1 里 4 次工作区外写，模型可见回执逐字是
   `<path>…</path><type>file</type><content>Created file</content>`。

**结论（诚实声明）**：在"只改 `dsh-plugin/staging-fs.mjs`"的范围内，**默认 `'stage'` 档的"成功回执"无法携带诚实信息**——
不是没做，是被 DSH 工具层的 schema 与渲染器挡死。因此本任务的这一半改为：
① 诚实信息放在**插件自己的记账面**（非枚举 diagnostics + error 级日志 + 候选/面板）；② 需要**模型面诚实**时用 `'deny'` 档（§1.3）。
③ 若要让默认档也诚实，最小上游改动是把 `operation` 扩一态或在渲染器里加一个可选字段——**处方见 §1.5**。

### 1.2 默认档（`'stage'`）实际落地的诚实记账 —— 前后对照

`locationDiagnostics()` 在 `isExternalKey(key)` 时新增：

```js

diagnostics.stageOutside = stageOutside
diagnostics.appliedToDisk = stageOutside === 'direct'   // 默认档 = false
diagnostics.pendingApproval = stageOutside !== 'direct' // 默认档 = true
```

实测（D1 用例，前后对照见 [toolface-consistency-before.json](evidence/fix/toolface-consistency-before.json) / [-after.json](evidence/fix/toolface-consistency-after.json)）：

| | 改动前 | 改动后 |
|---|---|---|
| diagnostics | `{layout, stagedPath, logicalPath}` | `+{outsideWorkspace:true, stageOutside:"stage", appliedToDisk:false, pendingApproval:true}` |
| 真实盘 | 未写 | **未写**（`realExists=false`） |
| 模型可见面 | `Created file` | `Created file`（**同上界**，不假装） |

> 这些字段走 `STAGE_DIAGNOSTICS` **非枚举旁路**（`stageDiagnosticsOf()` 读），因此既不会触发装载期透明性自检
> （`STAGE_ROOT_MARKERS` 扫字符串值），也不会被 JSON 化泄漏到模型面。

### 1.3 `stageOutside: 'deny'`：模型面**真诚实**的那一档

**关键实测（先做，再写代码）**：`FS_SANDBOX_DENIED` 在本插件的暂存面（`sandboxMode === undefined`）抛出去，模型看到的是什么？
用**已经存在的同一通道**（`denyStoreWrite`，P0-8）起了一个带沙箱的嵌套线程实测（[probe-store-deny/](evidence/fix/probe-store-deny/)）：

```
R2=Error: refusing to modify "…\.dshstage\review.json": this path belongs to this tool's own bookkeeping files, and a change there could never be approved
```

⇒ **没有** `[sandbox: …]` 标记、**也没有崩**；模型看到的是**插件自己的诚实文案**。
（读码旁注：`FsSandboxController.mapError()` 会读 `policy.mode`，而暂存面 `escalationModes=[]`、`policy=undefined`，
`resolvePolicy()` 返回 `undefined` ⇒ 读码上这里**有崩溃风险**；但实测该分支未被走到，说明 `mapError` 当时返回了原错误对象。
**如实标注：这是单次实测结论，不是对 `mapError` 全部输入空间的证明。**）

因此 `'deny'` 档按"文案必须自己就诚实"来写：

```js
denyOutsideWrite(place, verb) {
  this.logError(`stageOutside='deny' refused to ${verb} outside the workspace: ${target}（未写真实磁盘、未产生条目/候选）`)
  throw new FsError(MODEL_VISIBLE_FAILURE_TEXTS.outsideWriteDenied(target), 'FS_SANDBOX_DENIED')
}
// outsideWriteDenied: `refusing to write "<path>": this tool is configured to refuse writes outside the workspace, and nothing was written`
```

插入位置：`writeTextStaged` 与 `editTextStaged` 里，紧跟 `'direct'` 分支之后、**任何状态变更之前**。

### 2.3 根因与改法

**根因**（`listDirInner`）：删除标记只从**内容树 `fs\`** 出发被发现 —— `shimChildrenOf()` 遍历 `staged\fs\<盘符>\<绝对路径>\<dir>` 的每个子项，
再看该子项有没有同名 `wo\` 标记。于是最常见的那条删除形态（**真实盘上的文件被删、内容树里没有对应项**）根本不会被看见；
更糟的是内容目录 `fs\...\<dir>` 不存在时 `shimChildrenOf()` 返回 `undefined`，`listDirInner()` 直接早退回 `super.listDir()`，
**整棵 `wo\` 树被忽略**。而 `stat` 走 `currentOf() → shimWhiteoutOf()`，**承认**这个删除。
⇒ 同一目录：`readdir` 列着它、`stat` 说不存在（与 `exe` 域 **D-EXE-6** 同形）。

**改法**（新增 `shimDeletionsOf()`，与 `currentOf()` 同一棵树、同一口径）：

```js
shimDeletionsOf(ws, dirAbs) {
  const woDir = shimLayoutPathOf(this.stagedDirOf(ws), dirAbs, SHIM_WHITEOUT_LEAF)
  ... readdirSync(woDir) ...
  return { deleted, selfDeleted: this.shimWhiteoutOf(ws, dirAbs) !== undefined }
}
```
接入点（`listDirInner`）：`wo` 树**独立于内容树**扫描；`selfDeleted` ⇒ 返回空列表（与 `stat` 的"不存在"一致）；
早退条件加上 `woDeleted.size === 0`；合并真实盘 + shim 内容树后，**最后再按 `woDeleted` 压一次**。

### 2.4 残余与边界（不夸大）

- 只修了 `listDir`。`readBytes/readByteRange/streamText` 走 `currentOf()`，本来就承认白障（C6 的 `stat` 侧即证）。
- **真目录删除**（`rmdir` 型白障）本轮**未单测**（`not-run`）：标记口径与文件相同，但未取证据，不作结论。
- 本项只覆盖**插件 `ctx.fs` 面**。shim 面对 `cmd.exe if exist` 的既有 GAP（`c6cmd-canary`）**不属本次范围**，仍如实留在 `file-cow-dispositions` 的 KNOWN GAPS 里。
- 替身基类是我写的，**不是**真实 `SandboxedFileSystem`；因此本项证明的是"插件合并逻辑内部自洽"，**不能**替代整机实测。
