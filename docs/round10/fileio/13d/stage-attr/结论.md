## 1. 决定性原始行（同一 run、同一夹具）

**node（pid 9548，探针自身；`existsSync=false`、`stat=ENOENT`、`read` 成功）**：

```
[9548][323] ATTRDBG api=GetFileAttributesW path=\\?\C:\…\ws-stage3\probe\count-fixture.txt   ← 暂存路径，verbatim 形态
[9548][326] ATTRDBG api=GetFileAttributesW path=\\?\C:\…\13d-count-probe\ps-seed.ps1         ← 真实文件（对照）
```

**同 run 其它进程（`all-probes.ps1` 的 pwsh，pid 6460；该 run 的 `.NET Exists=true`）**：

```
[6460][5047/5058/5059] ATTRDBG api=GetFileAttributesW   path=C:\…\count-fixture.txt          ← 普通形态
[6460][5060/5062/5064/5065] ATTRDBG api=GetFileAttributesExW path=C:\…\count-fixture.txt     ← 普通形态
```

⇒ **判定 ①**：node 的 `existsSync/statSync` **确实调用了已挂钩的 `GetFileAttributesW`**，入参就是暂存文件路径；
该调用**没有拿到 overlay 内容**（返回 not-found），而同一文件的读路径（`CreateFileW`）在 Stage 0 里被 overlay 正常服务（`read` 成功）。

## 2. 静态分析：失败在**规范化之后**（不是 `\\?\` 前缀本身）

- **（A）受控 A/B（pwsh 同进程、先造夹具、只变形态）**：`plain_dotnetExists=true`、**`verbatim_dotnetExists=true`**、
  两者 `Test-Path=true`、`attrs=Archive`、`read=FORM-AB-FIXTURE` ⇒ **`\\?\` 形态在 pwsh 这条路上是通的**
  （PID 7708 的 `ATTRDBG` 里 `ExW` 与 `W` 都收到过 `\\?\` 形态）。**故"形态本身"不是充分原因** —— 我最初把它当结论是**过早的**。
- **（B）源码**：`ws_should_intercept()`（`ws_file.c:102-146`）先 `GetFullPathNameW` 再 `ws_normalize_path()`；
  而 `ws_normalize_path()`（**`ws_util.c:815-827`**）对 `\\?\UNC\` 与 `\\?\` **都有显式剥离分支**（`p += 4`）。
  ⇒ norm 会变成 `C:\…\count-fixture.txt`，**前缀已被剥掉**。
- ⇒ 因此"overlay 未被服务"发生在**规范化之后的属性解析分支**（`ws_GetFileAttributesW` 内的 `ws_stat_resolve`/overlay 查询/意图参数），
  而不是"钩子没被调用"、也不是"`\\?\` 没被剥离"。

## 3. 如实标注的 not-run / 未定项

- **逐 API × 逐形态直测 = not-run**：本会话 `Add-Type`（P/Invoke 定义）被拒（`addtype=ERR: Win32Exception`），
  故**未能**在同一进程内用同一形态分别直调 `GetFileAttributesW` 与 `GetFileAttributesExW`。
  目前"罪魁是 `W` 而非 `ExW`"**仍只是强指向，不是定名**（pwsh 的 `\\?\` 成功那条路按族级二分走 `ExW`）。
- `cmd if exist` 侧：本 run 的 cmd 输出仍是 `CMD_IFEXIST_NO`/`DIR_FAIL`/`TYPE_FAIL`/`ATTRIB_OK`，**未按 pid 归属**（cmd 进程未记录 pid）。
