## 3. (b) 为什么 `{size:12}` 与 `0xc000003b` 并存 —— 成功来自 **libuv 的 CreateFileW 回退**

c14 `statSync` pid=9856 的同 pid 逐行（原文）：

```
[9856][535] ATTRDBG-NQIFBN … path=<逻辑绝对名> mapped=<覆盖层绝对名> staged=1 status=0xc000003b class=77 seq=165
[9856][536] ATTRDBG-CFW seq=166 desiredAccess=0x80 … flags=0x2000080 path=\\?\C:\…\13d-t4-ws\probe\pa-fixture.txt
[9856][540] read-branch resolved flags=0x11 mapped=C:\…\stage-c14\staged\fs\C\…\pa-fixture.txt
[9856][541] ATTRDBG-CFW-OVL handle=00000000000002DC valid=1 err=0 path=\\?\C:\…\pa-fixture.txt
[9856][542] CreateFile overlay(read) C:\…\stage-c14\staged\fs\C\…\pa-fixture.txt
[9856][543] ATTRDBG-NTQIF seq=170 handle=00000000000002DC class=18 status=0x80000005
```

⇒ 失败的 by-name 查询之后，libuv **回落到 `CreateFileW`**（overlay 感知，命中覆盖层）⇒ 拿到 `size:12`。
**逐项排除**（都给了原始行）：
1. **不是**真实盘面给的：夹具只有 `staged=1` 的 NQIFBN 行（6/6），**没有** `staged=0` 的夹具行；`<ws>\probe\pa-fixture.txt` 在真实盘运行后仍不存在。
2. **不是** CWD 命中：查询名是**绝对逻辑名**；且同一 pid 的 `CreateFileW` 走的也是该逻辑名 + `ATTRDBG-CFW-OVL valid=1`（overlay 路径为 `…\staged\fs\C\…`）。
3. **不是**被修的 API 给的：那条 `status=0xc000003b` 是**失败**；`lstat`/`exists` pid 同形（`verify-v2.mjs` 三个 pid 均 `cfwFallback=yes`）。
4. 修前 b13 的同位置：`[2312][361] … status=0xc0000034`，**下一行直接是 evidence 目录查询**（`[2312][362]`）⇒ 修前**没有**回落 ⇒ 修前的 `ENOENT` 是直接失败。
   ⇒ 差异只在**失败码**：`0xC0000034`（直接返回）vs `0xC000003B`（触发 libuv 回落）⇒ **脆性绿**。

## 5. 偏差1：`existsSync` `false → true` = **优于规格预期的正确答案**，并**反证 D87**

- 两侧 `ATTRDBG-W`（决定 D87 结论的那条）**逐字同形**：
  `rc=0 … staged=1 attrs=0x20 err=203`（b13 pid 2648 / c14 pid 3500；`err=203` 是陈旧残留，按 D88 不作判据）
- 但 `existsSync` 从 `false` 翻成 `true`，而两者之间**唯一的相关差异**是 `statSync`/NQIFBN 的结果（`0xc0000034` 直接失败 → `0xc000003b` 触发回落成功）。
- ⇒ **决定 `existsSync` 的不是 `GetFileAttributesW` 的返回值**（两次都成功且 `attrs=0x20`），而是 **stat 那条路**（Node 的 `existsSync` = `statSync` 包 try/catch）。
- ⇒ `.t\round10\shim\D87-existsync-deciding-line.txt` 的「`GetFileAttributesW` 成功但**返回值被 post-call 丢弃/改写**」结论**被反证**；该文件第 17-19 行的二分（"排除 that call failed ⇒ 只剩 post-call"）**漏了第三条分支**：`existsSync` 根本不经 `GetFileAttributesW` 定值。
- 判据按 Lead 改判：`existsSync` 对已暂存文件**必须为 `true`（正确值）**，即"不得返回错误答案"。**线 B 前提待 v2 复核**：若 v2 下 `true` 由 `staged=1 status=0x0` 的那条 NQIFBN 产生（`viaNqifbn=true`），则线 B 可结案为"前提被证伪"。

## 6. 额外发现（建议进纪律清单）

1. **`nqifbn-probe.exe` 不能作判据**（`FileInformationClass=4` 被该 API 拒绝）。**无 shim 直接实验**（离线，我跑）：
   `nqifbn-probe.exe C:\Windows\System32\kernel32.dll` → `status=0xC000000D`；不存在的路径同样 `0xC000000D`。
   探针本身是**合法 `OBJECT_ATTRIBUTES`**（`InitializeObjectAttributes` + `\??\` 绝对名 + 正确 `Length`）。
   ⇒ `.t\round10\fileio\13d\线A-收束.md` §5.1 与规格 §7 把 `0xC000000D` 归因于"裸路径串调用"是**误归因**；真因是 **class=4 不被支持**。判据必须用 `class=77` 的行。
2. **`0xC0000034` 与 whiteout 同码**：修前真实缺件与候选的 whiteout 分支返回同一 NTSTATUS ⇒ 单看 `status` 无法区分；须读 `mapped=<whiteout> staged=0`。
3. **过度命中祖先目录**：`path=C:\`、`C:\Users`、… 也被判 `staged=1`（覆盖层为暂存文件建了同名目录树）并换名。v1 下它们同样 `0x3b`（多触发回落）；**v2 补上 `\??\` 后会"成功"** ⇒ 对**真实存在的目录**返回**覆盖层目录**的属性（时间戳/大小），属静默语义改写。建议：只对"覆盖层条目本身"换名，或对目录走 `ws_GetFileAttributesW` 的既有策略（`ws_file.c:283-300`）。
4. **小写盘符**：`ws_normalize_path` 不折叠大小写、`ws_fs_map` 逐字复制 ⇒ `mapped=` 可能显示 `…\staged\fs\c\…`；但占位盘 **NTFS 大小写不敏感** ⇒ 判据只看 **`staged=1` 且 `status=0x0`**，`mapped=` 的小写只是**显示形态、不是缺陷**。
5. **诚实披露（冻结驱动的一处瑕疵，已被判据绕开）**：`driver.cmd` 里小写盘符子探针写成了 `%WSL%` = 小写化的 **`%WS%`**（应是小写化的 `%TARGET%`）⇒ 它实际探的是 `<ws>` 目录而非夹具；且因为 class=4 本身不可判，该子探针**既错又无用**。为保证 v1↔v2 逐字可比，**故意不改**该冻结件；判据不依赖它。
