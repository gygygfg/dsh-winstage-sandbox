## 2. 定案：(a)

`valid=1`、`err=0` ⇒ **overlay 打开成功、拿到有效句柄**（未出现 `CreateFile overlay(read) miss -> read-through real` 回落行）。
结合此前两级：属性查询成功（`attrs=0x20/err=0`）、`CreateFileW` 到达且命中覆盖层。
⇒ **属性面、`CreateFileW` 意图分支、overlay 打开本身，三者都不是失败点**；缺口被压到**打开之后**。

## 3. 如实标注的**悖论**与未定项（不得粉饰）

按常理，句柄指向的是**真实文件**（`mapped` 落在真实盘的 `staged\fs\…`），那么在其上调用 `GetFileInformationByHandle` 这类**未挂钩**API **本应原生成功** ⇒ stat 应当成功。
**但 node 的 `existsSync=false`/`statSync=ENOENT` 是实测事实。** ⇒ 目前证据**不足以**解释这一步，两种仍未排除的可能：
1. node 的 stat/exists **并不使用**这次成功的打开（该打开服务于别的调用），其真实路径是另一个我们尚未覆盖的入口；
2. 句柄虽有效，但 node 在其上走的是**我们未挂钩**且被其它机制影响的信息查询（例如 `GetFileInformationByHandleEx`/`NtQueryInformationFile` 的**类/参数**路径）。
**逐 API 直测 = not-run**（本会话 `Add-Type` 被拒），因此"句柄信息族"这一步**尚未取得直接读数**。

## 4. 下一步（**新增挂钩目标**，须 Lead 单独批准 + 安全写法）

现在 (a)/(b) 已分出，(a) 成立 ⇒ 需要**新候选**（不得与既有日志同车），对**句柄信息族**做**只计数/只日志的 pass-through**：
优先 `GetFileInformationByHandleEx`（含 `FileBasicInfo`/`FileAttributeTagInfo`）、`GetFileInformationByHandle`、`NtQueryInformationFile`。
**硬约束（`D-FILE-2` 教训）**：per-site 保存原函数 / **绝不 fail-closed**（未解析该站点就不打补丁）/ 包装内零 I/O / 先日志 / **先过㈠**；若㈠不过立即回滚并停下上报。
