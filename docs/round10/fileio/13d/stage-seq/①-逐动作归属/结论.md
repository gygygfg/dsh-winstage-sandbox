# ① 逐动作归属（部分成功）：**四个动作进程中「两个零命中」** ⇒ 至少两个存在性动作走未挂钩入口

## 0. 构造与门槛

| 项 | 值 |
|---|---|
| 探针 | `.t/round10/fileio/13d-count-probe/per-action.mjs`：**一个进程只做一个动作**（`exists` / `stat` / `lstat` / `read`），每次调用即独立进程 ⇒ 每进程的 `seq=` 流**只属于一个动作** |
| 驱动 | 同一 TS 车道内：pwsh 写夹具 → **依次**跑 4 个独立 node 进程 |
| 候选 / ㈠ | `out-13d-count10` = `07CC5A88…`；`"tierEffective":"TS"` / `"launchMode":"shim"`、无 `fallbackReason` |
| 夹具 | `…\ws-stage11\probe\pa-fixture.txt`（`PER-ACTION`） |

## 1. 实测（夹具相关 `seq=` 行，按 pid）

```
pid=2172 fixtureSeqLines=5   ← 驱动 pwsh（写夹具/目录操作）
pid=5420 fixtureSeqLines=1   ← 1 次 GetFileAttributesW  path=\\?\…\pa-fixture.txt
pid=7440 fixtureSeqLines=1   ← 1 次 CreateFileW(0x120089) path=\\?\…\pa-fixture.txt   （= read，成功）
其余 pid（含另外两个动作进程） fixtureSeqLines=0
```

⇒ **四个动作进程里只有两个对夹具产生了已挂钩调用**（一个 `W`、一个 `CreateFileW`）；**另外两个动作进程的夹具调用数为 0**。
`0x120089` = `SYNCHRONIZE|READ_CONTROL|FILE_READ_ATTRIBUTES|FILE_READ_EA|FILE_READ_DATA` ⇒ 那条 `CFW` 就是 **`read`**（`readFileSync` 成功）。
⇒ 因此**三个存在性/属性动作中，至少两个完全没有已挂钩调用** ⇒ **对这两个动作，"走未挂钩入口"（真 ②）成立**。

## 2. 未闭合的部分（**必须与结论同读**）

**动作 ↔ pid 的映射没有取到**：
- 期望落盘的 `pa-<action>.json` **未出现在证据目录**（输出路径含全角字符 `①`，写入未成功）；
- 驱动 pwsh 的 stdout 也**未被** `run-cli` 的 `stdout` 字段捕获 ⇒ 无法从 `run.txt` 反推。

⇒ 因此**不能**断定"哪一个是 `exists`、哪一个是 `stat`、哪一个是 `lstat`"，也就**还不能回答 Lead 的子悖论**："那次成功的 `W` 究竟服务了哪个动作"。
**目前能说的最窄结论**：**它最多服务三个动作中的一个；另外两个动作零覆盖**。

## 3. 闭合它只需一步（微步，待裁定）

把每进程的输出写到**纯 ASCII 路径**（例如 `.t/round10/fileio/13d-count-probe/pa-out/<action>.json`），或让 `per-action.mjs` 把 `{"action":…,"pid":…}` 直接**追加写入 stage 内的证据文件**，再重跑一次同车道即可给出确定的 `action ↔ pid ↔ seq` 三元组。
（本次失败纯属**输出路径/捕获**问题，探针本身与 shim 无关。）

## 4. 与 Stage-seq 的关系

- Stage-seq（同进程四动作）判 **③（次数不符）** + 兼有 ②；
- 本 ① （**分进程**四动作）直接观察到 **两个动作零命中** ⇒ 把"兼有 ②"**升级为对这两个动作的确定结论**；
- 合并：**node 的存在性/属性三动作中，多数走未挂钩入口；读动作走已挂钩 `CreateFileW` 并被 overlay 服务** ⇒ "**read 通、`stat`/`exists` 不通**"的解释成立。
