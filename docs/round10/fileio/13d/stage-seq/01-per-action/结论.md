> 本文档 §2 原有"`err≠0` ⇒ 该次调用失败"**对 `GetFileAttributesW` 不成立**：该 API **成功时不清 `LastError`**，

## 2. 定名结论

1. **`statSync` 与 `lstatSync` ⇒ 走未挂钩入口（② 定名）**：两个动作进程对夹具**没有任何**已挂钩调用 ⇒ 它们经由**未被本仪器覆盖**的入口判定存在性 ⇒ 返回 `ENOENT`。
   下一步按 Lead 名单 + `D-FILE-4` 约束逐个候选：`NtQueryAttributesFile` → `NtQueryFullAttributesFile` → `NtQueryInformationByName`，**每级先做同车道活性正对照**（否则 0 行只能记 `inconclusive`/覆盖边界）。
2. **`existsSync` ⇒ 走已挂钩 `GetFileAttributesW`**：它是该进程**唯一**的夹具调用 ⇒ **子悖论闭合点**："那次成功的 `W` 服务的就是 `existsSync`"。
   但 `existsSync` **仍报 `false`** ⇒ 只剩两种可能，需**一行**判据分开：
   - 若该 `W` 调用**成功**（`ATTRDBG-W rc=0 … attrs=0x20 err=0`，pid 4680）⇒ **返回值被丢弃/改写**（分支 ① 后半；问题在调用方/libuv 侧或句柄语义，**不在 shim 解析**）；
   - 若该 `W` 调用**失败**（`branch=masked` / `branch=resolve-fail` / `err≠0`）⇒ 在该次调用的**具体分支**上定案。
   **判据（一行 grep，未做）**：`Select-String shim.log -Pattern '\[4680\].*ATTRDBG-W'`。
3. **`readFileSync` ⇒ 已挂钩 `CreateFileW` 且被 overlay 服务**（成功）——与历次一致。

## 3. 与 Stage-seq 的合并

Stage-seq（同进程四动作）判 **③ 次数不符**；分进程 01 把它**升级为定名**：**两个动作（`stat`/`lstat`）完全零覆盖、一个动作（`exists`）落在已挂钩 `W` 上且异常**。
⇒ "**read 通、`stat`/`exists` 不通**" 现在有两段互不相同的根因候选：
(i) `stat`/`lstat` 的**未挂钩入口**（②）；
(ii) `exists` 的**返回值被丢弃/改写**（或该次 `W` 失败）。
