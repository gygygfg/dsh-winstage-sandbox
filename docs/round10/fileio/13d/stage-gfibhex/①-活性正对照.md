# Stage-gfibhex ① 活性正对照：**钩子可装可用** ⇒ 上轮 0 的解释被确证

> ## ★ 一等结论（可引用）：**IAT 钩子存在覆盖边界**
> **判据**：**显式探针可命中**（本文件：`ATTRDBG-GFIBHEX` 4 行、`hit n=2`，`ok=1 err=0`）**而目标进程 0 行**（主探针：全进程 0 行、hit 0）。
> **含义**：**仅经 `GetProcAddress` / 延迟导入使用的 API，IAT 挂钩天然不可见** ⇒ 隔离面在此类调用上存在**盲区**。
> **性质**：这是**方法论/设计边界结论**，**不得**当作"node 调用了/没调用某 API"的**行为证据**；它**不是回归**、**不是 fail-open**。
> **与 `D-R8` 的区别**：`D-R8` 说的是"**该拦截失败时平台是否裸跑**"（fail-open 判据，窗口 #8 仍未被演示）；本条说的是"**拦截面本身看不看得见**"（覆盖/可见性），两者**不同层**。
> 正式条目见 `docs/round10/fileio/defects.md` 的 **`D-FILE-4`**。
>
> ## ★ 副产物（正面证据，② 的对照对象）
> **普通形态**路径的 `CreateFileA` + `GetFileInformationByHandleEx`×2 + `GetFileInformationByHandle` 在**暂存夹具**上**全部成功**（`ok=1 err=0 size=12`）
> ⇒ **overlay 对普通形态的"打开 → 句柄信息"链路是通的**。与 node 那条失败路径（`\\?\` 形态 + `ENOENT`）构成**形态对照** —— 这正是 ② 要绑定的对象。

## 3. 结论

**① 成功**：**该目标可被挂钩、计数与日志都活**（4 行 / 2 pid / `n=2` 各一），且 `ok=1 err=0`。
⇒ 上轮主探针的"全进程 0 行 + hit 0"**不是**"node 调用了却未被计数"，而是 **(B) 该进程集合里没有任何进程按名导入它 ⇒ 无 IAT 站点可打**（与 `ws_hook.c` 安装期注释"a hit count of 0 means no loaded module imported it — it is then only reachable through GetProcAddress"一致）。
⇒ 因此上一 Stage 记 `inconclusive` 的那个 0，现可**定性为"覆盖边界"**：**IAT 钩子对只在 `GetProcAddress`/延迟导入下使用的 API 天然不可见**；这属于**方法与覆盖的结论**，**不是** node 行为的证据。

**副产物（正面证据）**：一个**普通形态**路径的 `CreateFileA` + 两次 `GFIBHEX` + `GFIBH` 在暂存夹具上**全部成功**（`ok=1 err=0 size=12`）⇒ overlay 对**普通形态**的打开与句柄信息链路是**通的**（与 Stage-ovl 的 `valid=1` 一致）。

## 4. 下一步（②，待出件）
