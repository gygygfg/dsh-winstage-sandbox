- `desiredAccess=0x120089` = `SYNCHRONIZE(0x100000)` | `READ_CONTROL(0x20000)` | `FILE_READ_ATTRIBUTES(0x80)` | `FILE_READ_EA(0x8)` | `FILE_READ_DATA(0x1)` ⇒ **属性专用打开确实到达了 `CreateFileW`**（不是"没走"）。

## 2. 三选一定案（取数前写定，`CFW-OPENFORM-HANDOFF.md §2`）

| 结局 | 是否成立 |
|---|---|
| ① 有 fixture 的 `ATTRDBG-CFW` 却**无** overlay 行 ⇒ stat-open 未被服务 | ❌ |
| **② 有 overlay 行 ⇒ 失败点在句柄信息 API** | ✅ **成立** |
| ③ 连 `ATTRDBG-CFW` 都无 fixture | ❌ |

⇒ **node 的 stat/exists 链：打开这一步是被 overlay 正确服务的**（属性查询本身也成功：`attrs=0x20/err=0`）。
**失败点因此被推到"打开之后"** —— 最可能是 **`GetFileInformationByHandle`（句柄信息）**这条**未被挂钩**的入口（node 全程 `GetFileAttributesExW=0`、`NtOpenFile=0`，与该结论一致）。

## 3. 如实标注的局限（**必须与结论同读**）

`CreateFile overlay(read)` 是**分支日志**，它在**实际打开动作之前**打印；本仪器**没有记录该次 overlay 打开的返回值/错误码**。
因此"被服务"目前的依据是"走了 overlay 分支"，**不是**"拿到了有效句柄"。两种可能的下一层原因：
- (a) overlay 打开成功 ⇒ 失败在**句柄信息 API**（`GetFileInformationByHandle`，未挂钩）；或
- (b) overlay 打开**失败**（如 `err=2/3`）而分支行照打 ⇒ 失败在 `CreateFileW` 的 overlay 打开本身。

**判定 (a)/(b) 只需再一步**（仍为零语义日志）：在 `CreateFile overlay(read)` 之后补打**该次 `CreateFileW` 的返回（句柄是否有效）与 `GetLastError()`**。
在此之前**不得**把 (a) 当结论、也**不得**据此新增挂钩目标（`GetFileInformationByHandle` 属 `D-FILE-2` 风险面，须另立候选 + 先日志 + 先过㈠）。
