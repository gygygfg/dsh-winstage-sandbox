## 2. 定名（与预期相反，如实报告）

**`ws_GetFileAttributesW` 对 node 的 `\\?\…count-fixture.txt` 调用：解析正确（`mapped` = 覆盖层路径、`staged=1`），且真实 API 成功（`attrs=0x20` = `FILE_ATTRIBUTE_ARCHIVE`、`err=0`）。**

## 3. 新的、更锋利的判别数据

node 进程**总共只有 2 次** `GetFileAttributesW`（fixture + `ps-seed.ps1`，**两次都成功**）、**0 次** `GetFileAttributesExW`、**0 次** `NtOpenFile`。
而探针在同一路径上做了 `existsSync` + `statSync` + `lstatSync` **三次**存在性/属性查询：

- 若这三次走 `GetFileAttributesW`，**fixture 至少应出现 3 行** `ATTRDBG-W`；实测**只有 1 行** ⇒ **node 的 `existsSync/statSync` 并不走 `GetFileAttributesW`**。
- 且那一行**返回了成功属性** ⇒ **`W` 不可能是失败路径**。

⇒ **假设②（"走未挂钩句柄族"）重新成立，而且这次有正面判别**：node 的 stat/exists 走的是**未被本仪器覆盖**的入口。
最可能的是 libuv 的经典 Windows stat 实现：**`CreateFileW` 打开 + `GetFileInformationByHandle` 取句柄信息**——
`GetFileInformationByHandle` **不在 shim 的 `g_targets[]` 里**（本轮未列、也未挂钩），因此其句柄信息路径不受 overlay 影响；
而 `CreateFileW` 那一半虽被挂钩，但**属性专用打开**（`FILE_READ_ATTRIBUTES`/打开意图）可能走了**不服务 overlay 的分支**。
**注意**：node 的 9 次 `CreateFileW` 只对**读**打了 `read-branch`/`CreateFile overlay` 行；**属性专用打开**是否被 overlay 服务，现有日志**看不出** ⇒ 这正是下一步要补的那一行。
