## 1. R1（Lead 必答）：`ws_hook_resolve` 定义域枚举 + 身份可证明性

### 1.1 定义域（源码级）

`ws_hook_resolve(name)` 只服务两类（`ws_hook.c`）：
1. **`g_targets[]` 里的名字**（`ws_find_target`，并经 `ws_family_enabled` 过滤）；
2. **特殊例 `"LdrGetProcedureAddress"`** —— 它**不在 `g_targets[]`**（`WS_TARGET(LdrGetProcedureAddress)` **不存在**；它只出现在 `g_targetNames[]` 与 `map[]`），所以解析器里单独 `if (strcmp(...)=="LdrGetProcedureAddress") return ws_LdrGetProcedureAddress;`。

### 1.2 三类身份来源（逐类证明）

| 类 | 名字 | 身份证据 | 结论 |
|---|---|---|---|
| A. `g_targets[]` 且 `g_orig` 已捕获（约 58 个） | 文件/注册表/进程/加载器族 | `originalSlot`（init 时由 `{kernelbase, kernel32, advapi32, ntdll}` 顺序解析）+ **新增**四模块变体比对 | 可证明 |
| B. 仅 `g_d4OrdMap[]` 惰性真身（6 个：`GetFileInformationByHandle`/`NtQueryInformationFile`/`GetFileInformationByHandleEx`/`NtQueryAttributesFile`/`NtQueryFullAttributesFile`/`NtQueryInformationByName`） | 同名 API | `ws_hook_resolve` 仍能给出包装（它们在 `g_targets[]` 内）+ 四模块变体比对 | 可证明 |
| C. 解析器特殊例（1 个：`LdrGetProcedureAddress`） | 加载器原语 | `ws_hook_resolve` 特殊例给包装；真身在 ntdll 导出表（四模块之一） | 可证明（实测 `nt:S` 保持） |
| D. 真身不在四模块导出 | **实测不存在**（MODMAP 19 个抽样名全部落在四模块之一；`map[]` 的解析顺序就是这四模块，init 期 "original not found" 只在 verbose 下记录） | — | 无 |

### 1.3 ★ 关键实测：**单一 `g_orig` 地址不足**（这就是 R1 指出的"静默丢失"）

无 shim 的 ground-truth（`D4O1-offline-post.txt` [1] 段）：

```
MODMAP GetFileAttributesW   kb=00007FFB60FBCCB0 k32=00007FFB621573E0 adv=- nt=-  kb==k32:0
MODMAP CreateFileW          kb=00007FFB60FA3170 k32=00007FFB621571C0 adv=- nt=-  kb==k32:0
MODMAP RegCreateKeyExW      kb=00007FFB60F85C60 k32=00007FFB62146D50 adv=00007FFB62E30AF0  kb==k32:0
MODMAP RegQueryValueExW     kb=00007FFB60F8B090 k32=00007FFB62145270 adv=00007FFB62E287D0  kb==k32:0
MODMAP GetProcAddress       kb=00007FFB60FAF310 k32=00007FFB62133D20 adv=- nt=-  kb==k32:0
MODMAP LoadLibraryW         kb=00007FFB610606F0 k32=00007FFB6213F870 adv=- nt=-  kb==k32:0
MODMAP GetFileInformationByHandleEx kb=00007FFB60F9F7F0 k32=00007FFB62138320  kb==k32:0
MODMAP MoveFileWithProgressW kb=00007FFB6104BF80 k32=00007FFB6215B530 kb==k32:0
```
⇒ `GetProcAddress(GetModuleHandleW("kernel32.dll"), "GetFileAttributesW")` 返回的是 **kernel32 自己的 stub `621573E0`**，**不等于** `g_orig.GetFileAttributesW`（init 从 kernelbase 捕获的 `60FBCCB0`）；`advapi32` 对 `Reg*` 又是第三个地址。
⇒ 若名字路径只用"单一 `g_orig` 地址"做同一性，则**所有经 kernel32/advapi32 句柄解析的调用都会静默丢掉替换**（拿不到我们的包装）= 覆盖率回归。

### 1.4 采用的解（"扩展同一性表"）：名单内 × 四系统模块导出地址

`ws_name_identity()`：`real` 只要等于**该名字在 `{kernelbase, kernel32, advapi32, ntdll}` 任一模块的当前导出地址**，即判为"我们的函数"并给出包装；否则回落 `real`。
- 地址唯一属于一个模块 ⇒ **外部模块的同名导出不可能等于这四个地址** ⇒ 天然排除"同名不同址"。
- 覆盖：由 `ws_hook_resolve(name)` 先做**名单门**（非覆盖名直接 NULL，连解析都不做），再最多 4 次**真实解析器**调用（`g_orig.GetProcAddress`，不经我们的钩子 ⇒ **无递归**）。

**覆盖对照（实测，`MODMAP cov=`）**：

| 名字 | 修前（count18） | 修后（d4-o1-shim） |
|---|---|---|
| `GetFileAttributesW` / `CreateFileW` / `GetProcAddress` / `LoadLibraryW` / `GetFileInformationByHandle(Ex)` / `MoveFileWithProgressW` | `kb:S k32:S` | **`kb:S k32:S`（相同）** |
| `RegCreateKeyExW` / `RegQueryValueExW` / `RegDeleteValueW` | `kb:S k32:S adv:S` | **`kb:S k32:S adv:S`（相同）** |
| `LdrLoadDll` / `LdrGetProcedureAddress` / `NtQueryInformationByName` / `NtQueryInformationFile` / `NtQueryAttributesFile` / `NtQueryFullAttributesFile` / `NtOpenFile` / `NtSetInformationFile` | `nt:S` | **`nt:S`（相同）** |
| `NtClose`（非覆盖） | `nt:R` | **`nt:R`（相同，未误伤）** |

⇒ **R1 结论：无任何名字丢失替换；三类身份全部可证明；不存在"真身不在四模块"的项。**

## 2. R2：实现（纯同一性，**不**回落名字匹配）

名字路径最终形态（`ws_hook.c`）：

```c
    if ((ULONG_PTR)lpProcName > 0xFFFF) {
        /* O1: identity, not name matching. First the captured originals / ordinal
         * table (no API calls), then the system-module export variants of a
         * covered name. A miss keeps `real` -- so a foreign module's same-named
         * export is returned as-is (fidelity), never replaced by our wrapper. */
        void *rep = ws_wrapper_for_real((const void *)real);
        if (!rep) {
            rep = ws_name_identity(lpProcName, (const void *)real);
        }
        return rep ? (FARPROC)rep : real;
    }
```

与 D4S2 的关系：`real == NULL` 的早退（(i)）**未动**；序数分支（(ii)）**未动**；`ws_LdrGetProcedureAddress` **未动**。

**为什么不用"失败回落名字匹配"**（Lead R2）：那会让"名字命中但地址不是我们的函数"（= 本案缺口）重新被换成包装，**修了等于没修**。故一律 `return real`。

## 6. 已知残留（明写，避免被当既成事实）

1. ~~**`ws_LdrGetProcedureAddress` 的名字路径仍按名匹配**~~ ⇒ **已由 `D101b`（O1b）闭合**：Lead 2026-10-10 裁定扩展（见 `docs/round10/shim/D4-阶段2-O1b-LDR名字路径同一性.md`）。本件保留当时的残留描述以存原貌：该入口解析外部模块同名导出时**曾会被换成我们的包装**（实测 `LDR-NAME` 在 D101-only 上仍为 shim 指针）；`D101+D101b` 起回落真身（`result=0xDEADBEEF`）。
2. **序数路径对 `kernel32` 转发 stub 不换**：D4S2 的序数判据用 `ws_wrapper_for_real`（单一地址），`GetProcAddress(kernel32, MAKEINTRESOURCE(ord))` 得到的是 kernel32 stub 地址 ⇒ 不命中 ⇒ 保持透传。属**保守**行为（不误换、但也不覆盖）；未在本任务改动范围。
3. `ws_name_identity` 每次"名字路径未命中全局表"时最多 4 次真实解析（仅对**已覆盖名**）；无 I/O、无锁、无递归。
4. 本任务只做名字路径；`real == NULL`、序数、`LdrLoadDll` 修复、injection/路径逻辑、`ws_file.c` 均未动。
