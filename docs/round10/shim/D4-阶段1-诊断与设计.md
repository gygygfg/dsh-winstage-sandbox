### 1.2 离线探针：一条路由 = 一个进程

探针 `.t/round10/shim/d4/probe/d4-probe.c`（`zig cc -target x86_64-windows-gnu -O2 -Wall -Wextra`，**零告警** ⇒ `d4-probe.exe` = `6F04D6F5…`，167,936 B），同一 **API**、同一 **路径**（`<ws>\probe\d4-fixture.txt`，NT 形态 `\??\C:\…`），每个 mode 独立进程：

| mode | 路由 | 说明 |
|---|---|---|
| `static-w` / `static-nq` | **静态 IAT** | 正常链接调用；`GetFileAttributesW`（KERNEL32 → kernelbase）与 `NtQueryInformationByName`（ntdll） |
| `gpa-w` / `gpa-nq` | **动态 `GetProcAddress`** | `GetProcAddress(GetModuleHandleW(dll), "<同一名字>")` 取指针后调用 |
| `manual-w` / `manual-nq` | **自走导出表** | 自己解析 PE `IMAGE_EXPORT_DIRECTORY`（纯内存读，不用任何 loader API） |
| `rawgpa-nq` | 自解析出**真身** `kernelbase!GetProcAddress` 再用它解析 | 模拟"解析器本身也被自解析" |
| `rawldr-nq` | 自解析出**真身** `ntdll!LdrGetProcedureAddress` 再用它解析 | 同上 |
| `ordinal-nq` | **按序数**解析（`GetProcAddress(h, (LPCSTR)495)`） | NQIFBN 在 ntdll 的序数实测 = **495** |
| `wrongmod-nq` | `GetProcAddress(kernel32, "NtQueryInformationByName")` | 问"错"的模块；真实值应为 `NULL` |
| `mixed-nq` | 同进程先 3 次 static、再 3 次 gpa | 同进程对照 |
| `identity` | 只解析、不调用 | 打印每条路由的指针 + **指针归属模块** |

**NQIFBN 的 `OBJECT_ATTRIBUTES` 全程合法**：`InitializeObjectAttributes` + 绝对 NT 名 `\??\C:\…` + `OBJ_CASE_INSENSITIVE` + 正确 `Length`，`FileInformationClass=77`（`class=4` 无区分力，见线程#9 §1.4，本次不用）。

### 1.3 两条**互相独立**的判据

1. **探针自报的指针 + 指针归属模块**（`GetModuleHandleExW(FROM_ADDRESS)` → `GetModuleFileNameW`）⇒ 不需要读 `shim.log` 就能判"拿到的到底是不是包装"。
2. **`shim.log` 逐 pid 计数**：每条 `ws_log` 行都有前缀 `[winstage-shim][<pid>][<seq>]`，每个路由一个进程 ⇒ **只按前缀 pid 关联**（不跨进程、不跨时刻；不做 `canonical=` 之类部分字段 join）。

### 1.4 判据纪律（预登记，防"看数下判"）

- `0 行` 结论**必须**附**同一 run 的活性正对照**：`static-w` / `static-nq` 命中即证明"钩子活着、日志在写、注入到位"；否则只记 `inconclusive`。
- 期望值在取数**之前**写进 `analyze.mjs`（12 条路由逐条期望），取数后逐条比对（§2.6 全部 HIT）。
- 计数只认 `ATTRDBG-*`，不认 `err` 残留（D87 纪律）；NQIFBN 的成功/失败用 `status=`。
- 探针的 `attrs=` / `st=` 是**调用方视角**的第二证据；`identity` 进程不调用任何目标 API（其 0 行是构造性的，不作阴性判据）。

## 3. 结论：`D-FILE-4` 应当如何更正

**实测推翻的部分**

1. ❌ "仅经 `GetProcAddress` / 延迟导入使用的 API … 隔离面存在盲区" —— 对**名字在 `g_targets[]` 里**的 API，`GetProcAddress` 路由**是**被覆盖的（`ws_hook.c:824-836` 的 `ws_GetProcAddress` → `ws_hook_resolve()` 静态名表 → 返回包装；实测指针同址）。
2. ❌ "目标进程 0 行 ⇒ 该 API 只能经 `GetProcAddress` 到达且不可见" —— 0 行还有一个更省的解释：**该进程根本没调用**。`①-活性正对照.md` 的两条件（显式探针命中 + 目标进程 0 行）只能证明"**该 API 没有静态 IAT 站点**"，**不能**证明"动态解析不可见"。

**仍然成立、应当保留的部分**

3. ✅ "该 API 无 IAT 站点 ⇒ `ws_patch_module` 打不到点" —— 这与 `ws_hook.c` 安装期注释一致，仍是对的（但由解析器钩子兜住）。
4. ✅ 方法学：**0/阴性结论必须附活性反证** —— 本报告 §2.4 正是这么做的；这条纪律不因本更正而放松。

**更正后的边界定义（建议写入 `defects.md`）**

> `D-FILE-4`（重写）= **私有解析边界**：当调用方**不经过任何已挂钩的解析入口**就取得函数指针时，包装不可见。可判定的具体形态：
> ① **自走导出表**（`IMAGE_EXPORT_DIRECTORY` 手工解析）；
> ② **自解析出真身解析器**（自走导出表拿到真 `kernelbase!GetProcAddress` / `ntdll!LdrGetProcedureAddress` 后再用）；
> ③ **按序数解析**（`GetProcAddress(h, MAKEINTRESOURCE(ord))`：`ws_GetProcAddress` 只按名匹配，`(ULONG_PTR)lpProcName <= 0xFFFF` 直接透传）；
> ④（**未实测**，推理）注入前已缓存的函数指针；
> ⑤（**未实测**，推理）ntdll/loader 内部解析（`Ldrp*` 本机未导出）；
> ⑥（**未实测**，推理）直接 `syscall`、其它进程代办。
> ①②③ 已由本报告实测（各 3/3 未进包装）；④⑤⑥ 明确标为未实测。

### 4.1 递归/自调用保护写法（若将来真要加 C/D）

现状范式（**照抄，不要自创**）：

- 语义重入：`static _Thread_local int t_wsFileBusy;`（`ws_file.c:36`）——进入会打到内核的包装前 `++`，退出 `--`；所有判断处 `if (!t_wsFileBusy && …)`。**线程局部 ⇒ 可嵌套且不跨线程误伤**。
- 日志重入：`static volatile LONG g_attrLogBusy;` + `InterlockedExchange(&g_attrLogBusy, 1)` 门（`ws_file.c:870-894`）——因为日志 = 文件 I/O = `CreateFileW` = 整套钩子。
- 结构锁：`WsLock`（owner tid + depth，`winstage_internal.h:167`）**可重入**；纪律：**绝不持 `g_hookLock` 做 I/O**（`ws_hook.c:748-752` 注释就是为此改的）。
- 硬规则：新解析器钩子的实现里**不得**调用 `GetProcAddress` / `LoadLibrary*` / `LdrGetProcedureAddress`（它们都是我们自己的目标）——只能读 `g_orig` / 静态名表 / 自己的 PE 解析。

### 4.2 失败即安全降级、绝不 fail-closed

`D-FILE-2` 的教训（新增 pass-through 包装在 `g_orig` 为空时伪造失败 ⇒ `powershell.exe` 连崩 3 次）直接适用：任何**不**满足"参数合法 + `g_orig` 已解析 + 名字命中 + 未重入"的组合，**原样调用真实 API 并返回其结果**；任何异常路径**不得**返回自造的错误码。

### 4.3 指针身份 / ABI（实测 + 推论，务必分清）

- 实测：`GetProcAddress` 结果 == IAT 槽值（`6FBF3890` / `6FBF4CE0`）⇒ 调用方把两者比较/缓存看到的是**同一地址**（好）。
- 实测：`GetProcAddress` 结果 **≠** ntdll/kernelbase 真身 ⇒ 任何"与模块基址+偏移比较""与自走导出表结果比较"的代码会看到差异（`manual` 与 `gpa` 实测不同址）。
- 推论（未实测）：包装在 shim 模块内，调用方缓存的包装指针在 shim 卸载（`ws_hook_remove`）后会悬空 ⇒ **既有**风险面，非本次新增。

## 7. 建议（明确结论）

1. **不建议**为 `D-FILE-4` 进入"非 IAT 拦截"的产品改动阶段。理由：①字面主张被实测证伪；②残余边界（自走导出表 / 自解析真身 / 序数）**任何用户态解析器钩子都闭合不了**，能闭合的只有 inline/内核（§4 F/G），代价与收益不成比例；③现状对"正常动态解析"已有覆盖（且采纳件里就有）。

## 9. 限制与未实测项（明写，避免被当既成事实）
