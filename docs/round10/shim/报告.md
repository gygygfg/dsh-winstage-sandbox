## 2. D-SHIM-1【产品缺陷·未修】注入后 PowerShell 载体在 AMSI 初始化处崩溃

### 2.1 实测率与形态

`node tools/carrier-flake.mjs 30`（`evidence/D1-carrier-flake-30.txt`）：

| 结果 | 次数 | 退出码 |
|---|---|---|
| 成功（`SMOKE-PS-2`） | 24 | `0x0` |
| 访问冲突 | 5 | `0xc0000005` |
| CLR 异常 | 1 | `0xe0434352` |

**失败率 6/30 = 20%**；每次失败运行里 shim 日志都出现 `STUCK waiting on lock hook`（6 次）。

### 2.2 根因（逐字原始输出 `evidence/D4-ps-amsi-crash-excerpt.txt`）

```
System.TypeInitializationException: “System.Management.Automation.AmsiUtils”的类型初始值设定项引发异常。
  ---> System.AccessViolationException: 尝试读取或写入受保护的内存。
   在 System.Management.Automation.AmsiUtils.AmsiNativeMethods.AmsiInitialize(String appName, IntPtr& amsiContext)
   在 System.Management.Automation.AmsiUtils.Init()
   在 System.Management.Automation.AmsiUtils.CheckAmsiInit()
   在 System.Management.Automation.AmsiUtils..cctor()
   在 System.Management.Automation.Runspaces.EarlyStartup.<>c.<Init>b__0_1()
```

⇒ 注入后的 PowerShell 在 **AMSI（`amsi.dll` / AmsiInitialize）初始化**阶段崩掉，**脚本载荷根本没执行**
（成功标记不出现、真实盘未被写）。这解释了三处看起来无关的红：

| 观测 | 解释 |
|---|---|
| `delete-capture`：`whiteout:V3-inside`（PS Remove-Item 无白障）而 `host-intact:V3-inside` 绿 | PS 载体崩了 ⇒ 既没删、也没记录白障 |
| `delete-capture`：`write-staged:R1-ps` 红而 `write-not-real:R1-ps` 绿 | 同上（孙子 PS 没跑到写） |
| `registry-guard`：`E8.carrier-powershell exit=null` | 注入器 30 s 超时（`STUCK waiting on lock hook` 的同形） |

### 2.3 处置（如实保留为产品缺陷 + 让判定不再被偶发绑架）

* **测试侧**：把该签名（ASCII 片段 `TypeInitializationException` / `AmsiUtils` / `AmsiInitialize` /
  `AccessViolationException`）加入 `tests/delete-capture.mjs` 的 `PS_LOADER_SIGNATURES`。
  这是**既有 SKIP 纪律的延续**（"载体未启动 ⇒ 未判定，不计失败"），守卫全部保留：
  真实盘被改、或 PS 成功标记出现 ⇒ 仍然 FAIL。
* **门禁侧**：`tools/run-shim-closedloop.mjs` 的 `E8.carrier-*` 改为**有界重试（默认 3 次）**，
  把每次尝试逐条记进 `evidence.carriers[].attemptDetail` 与 `evidence.carrierFlakes`。
  判据不放松：**所有尝试都失败 ⇒ 仍然红**；真实回归（载体永远起不来）100% 会被抓住。
  实测：`E8.carrier-powershell ok=true attempts=3 FLAKE: 2 attempt(s) failed before it started`。
* **未做的真修**：这需要改 `shim/src`（见 §2.4 的限时定因结论），**并重建 `shim/out` DLL** ——
  按纪律必须先问 Lead；本轮未做，DLL 哈希保持原值。

## 2.4 task-11 限时定因（当轮结论：**未修**；已在 task-11b 修复 → 见 §2.5）

### 2.4.1 更紧的率与归因

| 测量 | 结果 | 证据 |
|---|---|---|
| `node tools/carrier-flake.mjs 30`（注入） | **6/30 = 20%** | `evidence/D1-carrier-flake-30.txt` |
| `node tools/carrier-flake.mjs 100`（注入） | **28/100 = 28%** | `evidence/D14-carrier-flake-100-baseline.txt` |
| `node tools/carrier-flake.mjs 40 --direct`（**不注入**） | **0/40 = 0%** | `evidence/D15-carrier-flake-40-direct-control.txt` |

失败形态分布（100 次）：`0xe0434352` × 18、`exit=null`（注入器 30 s 超时） × 7、
`0xc0000005` × 2、`0xffff0000`（"The shell cannot be started…"） × 1；
旁证 `COMException: The specified…` × 3。`STUCK` 行 **30 次 vs 失败 28 次**（强相关）。

⇒ **归因确定**：不注入 0/40；注入后 20–28%。崩溃由 shim 引入，不是 PowerShell/机器本身的问题。

### 2.4.2 死亡点定位（shim 日志逐字，`evidence/D14-…` 的 `lastShimLines`）

28 条失败里日志几乎全部停在
`read-branch resolved flags=0x4 mapped=<一个 .NET 程序集/资源 DLL/pdb>`
（`mscorlib.resources.dll` / `Microsoft.PowerShell.ConsoleHost.resources` / `System.Data.dll` /
`System.Management.Automation.dll` / `.pdb` / `CatRoot\…`），少数停在
`read-branch real-open ok=0 err=2|3`（正常探测未命中）。

`shim/src/ws_file.c:329-335` 的注释给了判据：**只有 `resolved` 没有 `real-open`
⇒ 死亡点在 `g_orig.CreateFileW` 之内/紧后**，即"CLR 正在读程序集、钩子刚解析完路径"的那一刻。

### 2.4.3 机制（代码级路径 + 已排除的假设）

**代码路径**：`shim/src/ws_hook.c:693-727` 钩住 `LoadLibraryW/A/ExW/ExA`；每次真实加载返回后
**同步**调用 `ws_hook_refresh()`（`ws_hook.c:629-638`）→ `ws_lock_enter(&g_hookLock)` →
`ws_patch_all()`（**全量重扫并改写所有已加载模块的 IAT**）。
`g_hookLock` 就是日志里名为 `hook` 的锁（`ws_hook.c:131`）；`STUCK waiting on lock hook`
只在 `ws_util.c:151` 自旋 400,000 次后打印（该锁可重入、带 Sleep(0) 退避，但不设上限）。

**推断**：PS 启动期大量加载 DLL（每次都触发**全量**重扫），同时 CLR 在 loader-lock 窗口里
加载程序集/读文件；`ws_patch_all()` 与加载器/CLR 的模块状态**无协调地并发** ⇒
偶发地遍历/改写"正在初始化中"的模块导入表 ⇒ IAT 槽位被写成错误地址 ⇒
随后真正调用该导入（例如 `AmsiInitialize`）时 AV（`0xc0000005` / `0xe0434352`）。
`STUCK`(30) ≈ 失败(28) 与"某线程长时间卡在 `g_hookLock` 里做全量重扫"一致。

**已排除的假设**：
1. **PowerShell/机器本身**：`--direct` 不注入 0/40 ⇒ 排除；
2. **Defender 隔离**：22:52 后 0 条新隔离事件，且崩溃在修复前后都在 ⇒ 排除（环境问题另记 D-DEFENDER-1）；
3. **verbose 造成的 LastError 污染**：本次测量就是生产路径（`carrier-flake` 默认不 verbose）⇒ 排除；
4. **AMSI 特有缺陷**：注入不改 `amsi.dll` 字节，死亡点在读 CLR 程序集那一刻 ⇒ 更像"导入表被写坏后的首次调用"；
5. **读不到真实文件（WP13）**：`ws_file.c:292-324` 的 overlay-miss 回落实测在，且 `real-open ok=0` 只占少数 ⇒ 不是主因。

### 2.4.4 下一步建议（未实施；改 C + 重建 DLL 需 Lead 授权）

1. **把"全量重扫"换成"只补丁刚加载的那个模块"**：`ws_LoadLibrary*` 已拿到 `HMODULE h` 与
   `lpLibFileName`，改成 `ws_patch_module(h)` 可把竞态窗口从"所有模块"缩到"一个模块"；
2. 或在 `ws_patch_all()` 前用 `LdrLockLoaderLock` 与加载器串行化（需实测是否与注入等待互锁）；
3. 或把 `ws_hook_refresh()` 从 LoadLibrary 钩子里**移出**（惰性/排队到下一次非加载器上下文的钩子进入时）；
4. 想把它从 28% 变确定性：注入一个"启动即并发加载 N 个 DLL"的 PS 载体，同时另一线程反复
   `LoadLibrary` 逼 `g_hookLock` 竞争 —— 本轮**未做**（超出限时）。

**本轮动作**：**未改任何 `shim/src`、未重建、未替换 DLL**。

`47DF4A5AAAB32EBE4A533270EDD6C598F21DB91EE558F5BF326B1469712DD6F2`（= 任务要求的原值）。

## 6. file-cow-dispositions：`c4d` 定因（确定性）+ GAP 如实保留

### 6.1 谁在红：不是 GAP，是 `c4d`

套件输出 `FAILED (18/19)`，而 `strictFails = failedCases.length + (STRICT_GAPS ? gaps : 0)`，
`--strict-gaps` 未开 ⇒ 计分失败是 **`c4d`**；`c6cmd-canary` 只进 `KNOWN GAPS` 记录（**不抹掉**）。

### 6.2 `c4d` = 夹具缺陷（期望建立在不成立的前提上）

旧期望：`openOk===false && openCode==='EPERM' && stagedStat===null && cowFailLog`
（前提："目标是真的目录 ⇒ CopyFileW 复制不了 ⇒ 打开必须 fail-closed"）。

实测两侧一致（`evidence/D10-c4d-uninjected-control.txt`）：

| 侧 | `fs.openSync(<real dir>, O_RDWR\|O_CREAT)` |
|---|---|
| 未注入主机 | `openOk=true code=null` |
| 注入沙箱 | `openOk=true code=null/errno=null`（`D9-file-cow.txt` 的 c4d 行） |

⇒ 在 Windows 上 libuv 对目录就是能打开（`FILE_FLAG_BACKUP_SEMANTICS`），
**CoW 失败分支根本不会被执行**；沙箱在这一路径上是**透明**的，`realDirIntact=true`、
暂存面里只有目录镜像（没有文件内容）⇒ 安全不变量成立。旧断言把"主机的目录语义"误判成"未 fail-closed"。

**修复**（夹具，保判定力）：分两支判定 ——
* 真走到 CoW 失败分支（`openOk===false`）：仍然要求 `EPERM` + 无暂存产物 + `fail-closed copy-on-write failed` 日志；
* 主机允许打开时：只接受"真实目录完好 **且** 暂存面里没有出现**文件内容**（目录镜像可以）"。

并附 `D10-c4d-uninjected-control.txt` 作为差分证据。结果：**PASSED 19/19**，GAP 行照旧打印。

### 6.3 GAP `c6cmd-canary` —— **如实保留，不动**

`cmd.exe` 的 `if exist <f>` 不认暂存文件（它走的不是 `GetFileAttributesW/ExW`），
而同一进程里的 `type` 能读到覆盖层。这是**产品缺口**（shim 少钩一个 API 面），
真修需要改 `shim/src` 并重建 DLL（需 Lead 许可）⇒ 本轮**不修、不抹**：
`KNOWN GAPS` 段照旧输出，`--strict-gaps` 下仍会把它计成失败（`knowngaps` 的 strict 分支未改）。

## 7. 对抗性复核：Lead 的 F1 / F2 是否引入假绿

### F1（`tests/delete-capture.mjs` 用 CLI 报出的 `sandboxInit.stagingRoot` 定位暂存树）——**判定：成立，无假绿**

逐条核过实现：

| 检查点 | 结论 |
|---|---|
| 找不到落点是否"跳过" | **否**。`resolveStageRoots()` 拿不到 `sandboxInit.stagingRoot` 就返回 `false`，`check(notes, stageResolved, 'stage-root-resolved', …)` 是**致命**断言（`ok:false` 进 `failed` ⇒ `exitCode=1`）。 |
| 是否有悄悄退回旧路径 | **否**。`usePaths()` 每次 attempt 都把 `STAGED`/`STORE_DIR` 重置成 `undefined`；`candidateStats()` 在 `STORE_DIR` 为空时只是返回空统计，而此时的 `stage-root-resolved` 已经致命红（不会静默）。 |
| 是否放松了断言 | **否**。修复后检查数从 14 → 36（多了 `stage-root-resolved` 与既有未跑到的项），是**变严**。 |
| 证据一致性 | CLI JSON 的 `stagingRoot` 与 `src/store.mjs:236-239` 的 `stagedDir`/`candidateDir` 同根 ⇒ 定位正确。 |

补充：我复核时把新签名（AMSI 崩溃）接进了它的 SKIP 机制。**守卫不变**：`realGuard` 必须绿、
`psMarker` 必须未出现，否则 `skipBlocked` 并保持 FAIL。所以"找不到就跳过"这种形态不存在。

### F2（重试取"致命红更少"的那次）——**判定：不会造成假绿，但原实现有一个"红项消失"的诊断缺口（已补）**

* **为什么不会假绿**：`final` 只有在被判定的那次**自身零致命红**时才会 PASS。重试只在 attempt 1 出现
  ps/cli 级红项时触发 ⇒ 若 attempt 1 零红则根本不重试；若 attempt 2 零红而 attempt 1 有红，
  取 attempt 2 是"消除偶发"的本意，且 attempt 1 的红项在 `RETRY:` 行里已逐条打印。
* **缺口**：旧逻辑只比**数量**。`attempt 1 = {A}`、`attempt 2 = {B}`（不同红项、各 1 条）时取 attempt 1，
  attempt 2 的 `B` 就**永远不会被打印**（判定仍是 FAIL，不假绿，但红项消失）。
* **补法**（已实施）：无论取哪一次，都把"不在判定输出里的红项"逐条打印
  `WARN: 红项「B」不在判定的输出里（判定取 attempt 1）—— 重试不得让任何红项消失`。
* 原则不变：两类 attempt 的完整输出都会打印，平手取第一次，取更差的那次永远不可能。

**结论**：F1 无假绿；F2 无假绿，但其"红项可见性"缺口已补齐。二者都符合 Lead 声明的原则
（重试只为消除宿主侧偶发，不允许掩盖确定性红项）。
