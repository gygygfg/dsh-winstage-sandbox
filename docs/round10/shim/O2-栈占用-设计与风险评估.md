# O2 · 栈占用：设计与风险评估（`task-17`）

> 作者：`line-a-fix` ｜ 日期：2026-10-10 ｜ 性质：**只读评估 + 离线实测**，**未改任何 `shim/src`**，未动 `shim/out`/冻结候选/`ws_reg.c`/`ws_regstore.c`/injection 与路径逻辑，未开换件窗口。
> 被测件状态（当时的树）：`shim\src\ws_file.c` = **`9826329BDFCBA8419BDE9C3218DC072B4DD4FB87ABD2D9757721CE9FB7B1CB06` / 87,118 B**（= D99 + v2 守卫）。
> 一句话：**实测显示不需要做**（单次 80 KB 是"一次付清"且现场余量充足），但若将来要做，**唯一正确的做法必须先修守卫位置**；本研究给出可执行设计。

## 1. Q1 —— 是否真的需要？先看两个硬读数

### 1.1 载体给这个 API 的栈配额（PE 实测，`.t\round10\shim\o2\o2-pe-stack.mjs`）

| 可执行件 | `SizeOfStackReserve` | `SizeOfStackCommit` | 备注 |
|---|---|---|---|
| **`powershell.exe`**（本项载体） | **524,288 B = 512 KB** | 8 KB | 只有常见 1 MB 的一半 |
| `node.exe` | 8,388,608 B = 8 MB | 4 KB | libuv 载体，宽裕 |
| `cmd.exe` | 1,048,576 B = 1 MB | 1,008 KB | |
| `powershell_ise.exe` | 4,194,304 B = 4 MB | 16 KB | |

⇒ 讨论"49 KB 是否危险"必须按 **512 KB** 这个真实配额来算，而不是按 1 MB。

### 1.2 单次顶层调用的真实栈成本（离线复刻实测，`.t\round10\shim\o2\o2-stack-probe.c`）

我把一次顶层 NQAF/NQFAF overlay 调用的**帧形状**逐层复刻（wrapper 3×8 KB → helper 2×8 KB →
`ws_stat_resolve` 1×8 KB → `ws_should_intercept` 2×8 KB → provider 1×8 KB → wo/fs 2×8 KB），
以 `-Wl,--stack,524288` 让主线程与 `powershell.exe` 同配额，`-O0 -fno-inline` 保证帧不被优化掉，
在每个线程上读 `GetCurrentThreadStackLimits` 并记录最深局部变量地址：

| 线程栈（reserve，`STACK_SIZE_PARAM_IS_A_RESERVATION`） | 链峰值占用 | 距栈底余量 | 结果 |
|---|---|---|---|
| **512 KB（= powershell.exe 主线程）** | **82–83 KB** | **429 KB** | 正常 |
| 512 KB（显式创建） | 81 KB | 430 KB | 正常 |
| 256 KB | 83 KB | 172 KB | 正常 |
| 192 KB | 83 KB | 108 KB | 正常 |
| 128 KB | 82 KB | 45 KB | 正常 |
| **64 KB** | — | — | **进程死：exit `0xC00000FD`**（`-1073741571`） |

⇒ **真实单次成本 ≈ 80 KB**（不是 49 KB：49 KB 只算了 D99 新增的两个包装 + helper；
**解析链那 ~32 KB 对 NQAF/NQFAF 也是新增的**——count15 里它们是纯透传，从不走解析链）。
⇒ 致命阈值：**线程栈 < ~128 KB 时，一次调用即可能溢出**；128 KB 只剩 45 KB 余量。

### 1.3 与"现场"的对照（已有车道证据）

- **v2 守卫把深度限制为 1**（同族环在入口即被拒绝）⇒ 80 KB 是**每次顶层调用付一次**，**不随深度相乘**。
- **A 件实测**（`D99-dbg-A-guard.patch` = `AA20D8DB…`/7,670 B；A 内容 = `3CB10F84…`；
  `pkgs` 构建件 = `E7B396A9…`/265,728 B）：**帧与 D99 完全相同**、只加守卫 ⇒
  `tierEffective=TS / launchMode=shim`、无 `fallbackReason`、无 `carrierExits`、无 `0xC00000FD`、3,240 ms、stdout 含 `D5_END`。
  ⇒ **在载体初始化期实际走到的每一个 NQAF/NQFAF 调用点，余量都 ≥ 80 KB**（否则 A 也会死）。
- 对照 **B 件**（`D99-dbg-B-smallframe.patch` = `DD08DE8F…`/3,741 B；内容 = `ACA0BD31…`；
  构建件 = `2136F973…`/306,176 B）：把 3 个新帧**全部**移出栈，**仍 `T1/restricted-token` + `0xC00000FD ×3`**
  ⇒ 缩栈**不是**本次崩溃的成因（成因是无界重入）。**这两条合起来正是"49 KB 值不值得优化"的判据来源。**

### 1.4 Q1 结论

**在真实载体（512 KB）上，单次 80 KB ≈ 16%，A 件现场实测余量充足 ⇒ 49/80 KB 单帧不构成实际风险。**
残余风险只有一种形态：**栈配额 < ~128 KB 的线程**调用这两个 API。已观测载体中：`powershell.exe` 的
`CreateThread(0)` 线程继承 PE 默认 512 KB，.NET Framework 托管线程默认 1 MB，node 8 MB
⇒ 触发残余风险需要 <128 KB 的自定义线程，属**非常规**（未在任何一轮证据中观测到）。

## 2. Q2 —— 若做，正确做法与**致命陷阱**（本节为重点）

### 2.1 陷阱的源码级证据（当前 v2，行号 = 上述 87,118 B 树）

**陷阱本体**：若把 scratch 换成 TLS 缓冲，而某个重入调用**在守卫拒绝它之前**就写了同一块 TLS，
它就会**覆写外层调用正在使用的缓冲** ⇒ 由"会崩溃"变成"**静默路径损坏**"。当前代码**确实有 pre-guard 写入**：

| 位置 | 行 | 事实 |
|---|---|---|
| helper | `1387–1389` | `path_out[0]=0; win_out[0]=0; nt_out[0]=0;` —— **在守卫判断（1390）之前**写调用方缓冲 |
| helper | `1393` / `1461` | `t_wsAttrBusy = 1` / `= 0`（单出口 `do{}while(0)`） |
| helper | `1402–1403` | helper 自己的 `nz`/`abs` 在置位之后 ⇒ 这两块**已被保护** |
| NQAF/NQFAF | `1489–1491`、`1556–1558` | `ws_path/ws_win/ws_nt` 在包装内声明并交给 helper（helper 在 1387–1389 先清零） |
| NQIFBN | `1638` | `ws_map[0] = 0;` —— **在其守卫（1675）之前** |
| NQIFBN | `1644` | `ws_nz` 声明 + 按 `Length` 复制 —— **同样在 1675 之前** |
| NQIFBN | `1675` / `1677` | 守卫只包住**那一次** `ws_stat_resolve`（1676） |
| NQIFBN | `1696` | `ws_nt`（staged 分支）**在守卫已清位（1677）之后**才作为 in-flight `ObjectName` 用 |
| NQIFBN | `1729` | `ws_nqifbn_orig(&ws_oa, …)` —— 真实 API 调用发生在守卫**已释放**之后 |

⇒ 两条独立的损坏路径：
**(i) pre-guard 清零/复制**：重入者在被拒绝前就写坏外层的 `path/win/nt`（helper 1387–1389、NQIFBN 1638/1644）。
**(ii) 守卫释放后仍在用**：`ws_nt` 作为 `ws_un.Buffer` 一直活到真实 API 调用（1696→1729），
而**环恰恰在真实 API 内部重入** ⇒ 重入者若获准使用同一 TLS，就会改写外层 in-flight 的 `ObjectName`。

### 2.2 (a) 修正后的守卫放置与**全部清位点清单**

必要条件（缺一不可）：
1. **每个包装的最早入口**取守卫——在**任何 scratch 写入/TLS 指针生效之前**（NQAF/NQFAF 在 `1489` 之前；NQIFBN 在 `1638` 之前）；已置位 ⇒ **立即原样透传**（含"不改返回值、不 fail-closed"）。
2. 守卫**必须跨越真实 API 调用**：helper 返回后并不释放，直到 `ws_nqaf_orig`（1508）/`ws_nqfaf_orig`（1575）/
   `ws_nqifbn_orig`（1729）**返回**、且相关 `ws_log` 打完为止。
3. 清位点必须**覆盖所有出口**（逐条列清，供实现时对照）：

| 包装 | 出口 | 需清位 |
|---|---|---|
| `ws_NtQueryAttributesFile` | whiteout `return ws_gone` / staged `return ws_st`（1508 之后）/ 透传 `return st` | **3 处**（另：日志在清位后再打，故日志用的缓冲必须**不**被复用于可重入路径，见 2.3） |
| `ws_NtQueryFullAttributesFile` | 同上（1575 之后） | **3 处** |
| `ws_NtQueryInformationByName` | whiteout `return ws_gone` / staged `return ws_st`（1729 之后）/ 透传 `return st` | **3 处** |
| `ws_attrbyname_overlay` | 内部 `ret = -1/0/1/2` 的 `break`（已有单出口 `1461`） | **保持**（作为冗余保险，A 的已验证代码不动） |

> 实现上建议：`t_wsAttrBusy++`/`--` 或 `=1/=0` + **单出口重构**（把三个包装各自改成 `do{…}while(0)`），
> 否则"3×3 个 return"极易漏清位 ⇒ 一旦漏清，全线程此后**永久静默透传**（功能退化，不崩溃）。

### 2.3 (b) 哪些缓冲可安全复用

**同线程内嵌套**（守卫修正后）：
- 可以复用：**整套 5 块**（`nz/abs/path/win/nt`）由两条路径**共用**——因为守卫从入口到真实 API 返回，
  重入者根本走不到 scratch（这正是 v2 守卫能成立的前提：**它把嵌套变成"直接透传"**）。
  ⇒ TLS 总量 5×8 KB = **40 KB/线程**即可同时覆盖 NQAF/NQFAF 与 NQIFBN（NQIFBN 的 32 KB 也一起消掉）。
- **不可复用**：任何在守卫释放后仍需读取/仍作为 in-flight 参数引用的缓冲（典型：`ws_nt` 在 1696→1729 之间）；
  以及日志用的 `path/mapped/nt`——若日志安排在真实 API 返回**之后**且守卫已释放，则必须确保日志前不再有
  可能重入的调用（当前日志确实在 API 返回后：属"安全区"，但**顺序**必须写死并注释）。
- **绝不能**在未修守卫的情况下做 TLS：那正是 2.1 的静默损坏。

**多线程并发**：
- `_Thread_local` ⇒ **每线程一份**，互不干扰 ⇒ 并发安全。**离线实测**（`.t\round10\shim\o2\o2-tls-host.c`）：
  72 KB TLS 块在 `LoadLibraryW` 载入的 DLL 中，主线程与工作线程的 TLS 地址不同（`isolated=YES`）；
  对照组（静态/栈）地址相同（`isolated=no`）⇒ 测试本身可判别。
- **必须避免**把 scratch 做成**普通 `static`**（跨线程共享 ⇒ 真损坏）；也**不要**用全局 + 自旋锁（热路径代价）。
- `t_wsAttrBusy` 本身已是 `_Thread_local`（`1381`）⇒ 守卫语义天然按线程隔离，与 TLS scratch 匹配。

### 2.4 (c) 替代方案对比

| 方案 | 栈占用 | 机制风险 | 体积/内存代价 | 评价 |
|---|---|---|---|---|
| **①保持现状**（栈缓冲） | 80 KB/次顶层调用 | **无新风险**（已验收路径） | 0 | Q1 实测支持下**推荐** |
| **②减少缓冲数**（去掉 `abs`；`path_out` 直接用 `nz`） | **-16 KB**（80→64 KB） | 低（需复核语义） | 0 | 若要做，**优先** |
| **③TLS scratch** | **≈0** | **高**（必须先修守卫与跨越真实 API，见 2.2） | 映像 +40 KB（5 块）；或 +72 KB（9 块） | 收益有限、改动面最大 |
| **④按需 `HeapAlloc`** | ≈0 | 中（分配失败必须透传；热路径多 2 次堆调用；每个出口都要 `HeapFree`） | RSS 峰值受线程数影响 | 可行但不如②简洁 |

**②的语义依据**（已核源码，供复核）：`ws_stat_resolve` 内部经 `ws_should_intercept` 会先做
`GetFullPathNameW(path, …, full, NULL)` 再 `ws_normalize_path(full, norm, cch)`（`ws_file.c:127–134`），
即**自己就绝对化**；因此 NQAF/NQFAF 侧再单独维护一个 `abs[4096]` 属**冗余**（它只多用于
`ws_wcscmp_ci(win_out, abs)` 的"路径未变"判定，可改为与 `nz` 比较或直接依赖 `isStaged`）。
**注意**：②改变了 `abs` 的使用，需按 `task-7` 的三层验收口径重跑（不能只做静态论证）。

## 4. Q4 —— 建议

**建议：不做（保持现状，①）。** 理由（全部可判读）：
1. **单次成本是"一次付清"**（v2 守卫把深度限制为 1），不是可乘放大器；
2. 载体真实配额 512 KB，单次 **80 KB ≈ 16%**，空栈余量 429 KB；
3. **A 件已用同样的帧在真实载体初始化期跑通**（TS、无 `0xC00000FD`、`D5_END`）⇒ 现场余量 ≥ 80 KB；
4. B 件证明**缩栈不解决任何已观测故障** ⇒ 收益是"预防未来"，而 ③TLS 的机制风险（静默路径损坏）**大于**它消除的风险；
5. 红线成本：③要动三个已验证包装 + 重跑三层验收，性价比低。

**记账（建议入册的门槛与观察项）**：
- **门槛 T-1**：任一线程栈配额 **< 128 KB** 而调用 NQAF/NQFAF/NQIFBN ⇒ 可能溢出（实测 64 KB 必死、128 KB 余 45 KB）。
  若将来出现该形态载体/线程，**再启动 O2**。
- **门槛 T-2**：单次链成本已从 49 KB 修正为 **~80 KB**；若再新增包装/缓冲使单次 > 128 KB ⇒ 必须重评。
- **观察项 O2-a**：`powershell.exe` 主线程 512 KB（非 1 MB）这一事实应写进载体画像。
- **可选廉价保险（比 TLS 更小、更安全，若你想要"残余风险"兜底）**：
  在**小帧 dispatcher** 里先读余量再决定是否进入大帧函数——余量不足 ⇒ **直接透传真实 API**（fail-safe、不崩溃、不损坏）：
  `NT_TIB`（`gs:[0x08]` StackBase / `[0x10]` StackLimit）或 `GetCurrentThreadStackLimits`；
  阈值建议 ≥ 96 KB；成本 ≈ 几条指令。**本项未实现**（需 Lead 决定）。

**若决定"做"的可执行补丁设计（不落树、不写进真树）—— 目标件：**
- 取 **②减少缓冲数** 优先：删 `abs`（NQAF/NQFAF helper）与 `path_out`（改日志用 `nz`）⇒ 单次 **80→64 KB**，
  改动仅限 D99 区域、不动守卫、不动 D98；验收：`task-7` 三层 + 载体门槛。
- 若仍要 ③TLS：必须**同时**落 2.2 的三条必要条件（入口取守卫 / 守卫跨越真实 API / 单出口清位），
  并在结论里按 §5 列出"守卫重定位"与"缩栈"两处各自的证据来源（前者 = 本次 2.1 的源码事实，
  后者 = B 件的栈画像与本次 80 KB 实测）。

## 6. 未决 / 说明

1. **本评估未测"载体初始化期的最深基线用量"**：无法离线取得该深度，故用 **A 件的存活**作为现场余量下界
   （≥80 KB）。若要更紧的界，需要车道内插桩（属另一立项）。
2. 未测 <128 KB 线程在真实载体中的存在性（只在探针里造过）：结论是"**未观测到**"，不是"不存在"。
3. `HeapAlloc` 方案未实测；②减少缓冲数未实测（属设计，需实现后按三层验收）。
