## 2. T6 的真缺陷：暂存里的"空键"按全路径打不开

### 2.1 症状（PowerShell 侧）

`tests/acceptance-transparent.mjs` 的 T6 在沙箱里报：

```
WRITE=FAIL:ItemNotFoundException
```

`New-Item -Path HKCU:\Software\X -Force`（建键）成功，紧随其后的
`New-ItemProperty -Path HKCU:\Software\X -Name Probe ...` 失败。

### 2.2 最小复现（`.t/reg-staged-key-reopen.mjs` 就是它）

在**被注入的 PowerShell 载体**里：

```
CREATE=OK                 CreateSubKey('Software\K')            → 建在覆盖层
REOPEN_EMPTY=NULL         OpenSubKey('Software\K')              → **打不开**（空键）
NEW_ITEM_PROPERTY=FAIL    New-ItemProperty -Path HKCU:\...\K    → ItemNotFoundException
```

对照实验（同一载体配置）：

| 序列 | 结果 |
|---|---|
| `D1/D2` 同一个 handle 上 `SetValue`/`GetValue` | OK（值为 `y`） |
| `D3` 写了值之后再 `OpenSubKey('Software\K')` | **OK** —— 一旦有值就能打开 |
| `E` native `reg.exe add` + 再打开 | OK（`z`） |
| `C3` `SetValue('Software\K\P')`（内部 create-if-missing） | OK |

### 2.3 根因

`ws_create_key()`（`shim/src/ws_reg.c`）在"覆盖层与真实 hive 都没有这个键"的分支上，
旧实现只返回一个 pseudo handle 并**什么都不写**（注释原文："the WAL record is deferred to
the first actual write"）。于是：

- 后续**按路径**的 `RegOpenKeyExW` → `ws_t3_key_exists()` 说"覆盖层没有" → 落到真实 hive
  → `ERROR_FILE_NOT_FOUND`；
- 只有"在同一个 handle 上写值"或"写值触发 `materialize_chain`"之后，键才进覆盖层。

即：**"创建"这个动作没有立刻进入暂存**，而"第一次写值"才进入 —— 但按路径的 open 夹在两者之间。

### 2.4 修法

新增 store 公共入口 `ws_rstore_key_materialize(hive, subkey)`（`shim/src/ws_regstore.c`），
内部复用既有的 `materialize_chain()`：**WAL-first** 写 CREATE_KEY（只对真实 hive 里也不存在的
层级），再把 app-hive 键建出来；`ws_create_key()` 的新建分支改为调用它（随后仍返回 pseudo handle，
调用方可见行为不变）。

语义变化（刻意）：**"新建一个键"本身就是净变化**，记录发生在 create 时刻而不是第一次写值。
这正是它应该出现在候选/审批面板里的原因；真实 hive 已有的容器层照旧不产生记录（`materialize_chain`
的净变化规则未动）。host 侧 apply 对 `create-key` 本来就是"中间键一并创建"
（`src/registry-stage.mjs:1989`），所以链上层级只记录叶子也够用。

### 2.5 回归门

```
node .t\reg-staged-key-reopen.mjs      # 绿=已修；红=缺陷回来了（exit 2）
```

## 3. 验收台的"逐载体注入"模式

```
WINSTAGE_ACCEPT_CARRIER=inject node tests\acceptance-transparent.mjs    # 或 --inject
```

`inject` 模式下 `runPowerShell()` 不再直接 spawn `powershell.exe`，而是把**每一个被测载体**
交给 `shim/out/winstage-inject.exe`（`--dll` + `WINSTAGE_STAGE_ROOT` / `DSH_REGSTAGE_ROOT` /
`WINSTAGE_SHIM_CONFIG` / `WINSTAGE_SHIM_LOG` + `--report`），配置与 TS 档位探测/闭环同源
（`failClosed`、`readThrough`、`readDenyFile=shim/out/mask.json`）。默认仍是 `shell` 模式，
行为与以前完全一致。

### 3.1 为什么必须"逐载体"，不能只注入一次

**shim 按进程打 IAT，且不向子进程传播**。实测（2026-09-30）：

```
把 shim 注入 node 后：
  node 自己写盘（openSync/writeFileSync）      → 进覆盖层（宿主看不到该文件）
  node 派生的 powershell 写 C:\Windows\Temp\x  → realExists=True（**真实磁盘**）
```

所以"把整个验收脚本托管成一个被注入的进程"覆盖不到任何被测操作；`docs/T5-痕迹与根统一报告.md`
§1.3 要求的"由 winstage 沙箱托管的命令"，在 shim（去令牌化 TS）这条路上等价于**逐载体注入**。
（在受限令牌 T1 那条路上，令牌会被子进程继承，因此整棵树同时受限 —— 但 T1 下 T2/T3/T4 会红，
这正是 TS 档位存在的理由。）

### 3.2 边界：stageRoot 对被注入进程是"私有树"

宿主**直接**写进 `stageRoot` 的文件，在被注入进程里**不存在**（`passthrough: [stageRoot]` 也不会
让它可见）。实测：把诊断脚本放进 `stageRoot` → 载体报
`The argument '...\accept-diag-*\diag.ps1' to the -File parameter does not exist`；
把它放到 `%TEMP%` 就正常。**脚本与输出一律放在 stageRoot 之外**（`%TEMP%`），这既不是崩溃也不是
权限问题，但极易踩。

### 3.3 证据位置

每次 inject 运行把证据留在 `<workspace>\.dshstage\accept-inject-<rand>\`：`inject-N.json`
（每次注入的 `childExitCode`/`remoteModule`）、`shim.log`、`registry\overlay.{hive,journal}`、
以及 `fs\...` 下被暂存的写入。T5/T6 的"真实磁盘/hive 不变"判据由**宿主**（未被注入）核对。

## 4. 仍未通过 / 仍待接线

### 4.1 跑验收前必须确认载体是谁

`ctx.shell` 必须是 WinStage（`include:winstage-shell enabled=true`）。本机实测：
`include:pwsh-sandbox enabled=true active` 而 `include:winstage-shell **enabled=false**`，
因此"直接在会话里跑验收"跑的是**平台 shell**，T5/T7 会红（写入真落盘）。根因是 bundle 把 shell
接管门控成 `process.env.WINSTAGE_SHELL === '1'`，而宿主环境里没有该变量；profile 层只覆写了
`name`，覆盖不了 bundle 的 `!!js disabled`。两条合法路径：

1. 启动 DSH 的环境里设 `WINSTAGE_SHELL=1`（推荐；保留"设置开关"对 shell 面的门控）；
2. 或者用本文的 `WINSTAGE_ACCEPT_CARRIER=inject`（不依赖 session 的 shell，自带强制）。

### 4.2 T8（审批面板）测不了的原因（2026-09-30 实测补全）

T8 读 `.dshstage\sessions\<sid>\review.json`，要的是 T5 那个**越界文件**与 T6 那个**注册表键**
出现在面板快照的 `files[]` 里。inject 模式的暂存落在 shim 覆盖层，默认不是 DSH 的 review store，
所以测不到。已试过的两条路与实测结果：

1. **把 inject 的 stage 根指到会话 store**（`WINSTAGE_ACCEPT_STAGE_ROOT=<root>/.dshstage/sessions/<sid>`
   + 在 T8 之前调用与 shell 执行器同一条发布路径 `publishWorkspaceSnapshot()`
   = `getReviewService(...).publish()`，`shell-executor.mjs:388`）：
   - 发布本身**成功**：`review.json` 变成 `pending=true, files=4`；
   - 但那 4 条全是**文件工具的候选**（我这些源码改动），**T5/T6 的写入一条都没进去**；
   - 而且把 stage 根指到会话 store 会让**载体自己坏掉**：T2 重定向空、T6 `UnauthorizedAccessException`、
     T7 载体 .NET 启动即 `FileNotFoundException(0x80070002)`（9 项掉到 5 项）。
   结论：目录形状虽然相同（store 里本来就有 `fs/`、`wo/`、`registry/`），但"shim 直接写进会话 store"
   不是一条可用路径 —— 载体的失败说明两者对同一棵树的读写约定并不一致。
2. **正确路径仍然是把 shell 面接起来**：由 `winstage-shell` 执行器托管命令 —— 它才知道"这次命令有没有
   净变化"，并在命令结束后调 `publishSnapshotIfChanged()` 发布快照（`shell-executor.mjs:1093`）。
   前提是先做**档位接线**（见 §6），而不是在验收台里人工造一次发布。

临时把 `stageRoot` 指到会话 store 时，shim 会在 store 根留下 `inject-*.json`、`shim.log`、
`winstage-shim.config.json`（本次已清理）。**真实磁盘/真实 hive 零污染**（复核 0 文件 / 0 键）。

### 4.3 验收台自身的两处加固（本轮一并落地）

- **T6 假绿**：旧判据"路径里带 `registry` 就算覆盖物"会命中 `capability-probe` 的**陈旧**
  `overlay.hive`，未生效时也报绿。现改为：只认名为 `overlay.hive`、不在 `capability-probe`
  旧根下、且 **mtime 在 5 分钟内**的文件，并用独立进程 `reg query` 判真实 hive。
- **未生效时不留垃圾**：T5 若发现真实磁盘出现探针文件、T6 若发现真实 hive 出现探针键，
  验收台自己删除并在证据里记 `realCleaned`。

### 4.4 证据新鲜度（运维注意）

`registry-guard` 的 A.2/A.5 会拒绝"WAL/报告比 DLL 旧"的证据（这是它的设计）。而
`tools/run-shim-closedloop.mjs` **默认清理**自己的 stageRoot ⇒ 重跑闭环后直接跑 guard 会读到
**别的**运行留下的 WAL，报成"数据不一致"。正确配对是：

```
node tools/run-shim-closedloop.mjs --keep-stage
node tests/registry-guard.mjs            # 378/0/1
```

（实测过：不 `--keep-stage` 时 A.2 报 `STALE_EVIDENCE`，且"记录里的数据字节"与当前探针写入的
值不一致 —— 那是**证据选错文件**，不是暂存逻辑错。判据本身是好的：它逼你重跑，而不是默默放绿。）

### 4.5 ★ 运维陷阱：带暂存候选时**重启会把候选写回真实文件**（2026-09-30 实测）

本轮踩到：`tests/acceptance-transparent.mjs` 的真实文件是 **26489 B**（含 inject 载体模式 +
stage 覆盖 + 发布），而 store 的 `staged/` 里还压着一份 **21478 B 的旧候选**（更早一次工具写入留下的）。
重启 DSH 之后：

- 面板变空（`pending=false, files=0`）——看起来"候选自动清理了"；
- 真实文件被改回 **21478 B**（那份旧候选的内容），我通过 shell 落盘的改动**全部丢失**。

⇒ **暂存层对"有候选的文件"是权威**。开着沙箱时不要留着**与真实文件分叉**的候选去重启：

1. 要改真实文件就走审批（`/winstage approve <路径>`）；不想留就 `/winstage reject <路径>`；
2. 用 shell 落盘（§8.3 的逃生口）之后，**必须把对应候选清掉或让它与真实文件同内容**，
   否则下一次重启会把落盘内容覆盖回去。

内容并非真丢：被 shell 落盘的那一版在 store 的 `blobs/`（内容寻址）里还在 —— 本次就是从
`blobs/04/0456bf…`（26489 B）恢复的。恢复后把 `staged/tests/acceptance-transparent.mjs`
也写成同一份，重启对账即成为空操作。

## 5. 构建后的一次瞬态 flake（如实记录）

重建 DLL 后的**第一次** `src/capability-probe.mjs --tier TS` 曾回退到 T1：

```
"effective": "restricted-token", "tierEffective": "T1",
"fallbackReason": "transparent shim unavailable (injector exit=3762504530 (111=injection failure) report.ok=true …
   Unhandled Exception: System.IO.FileNotFoundException … 0x80070002) — fail-closed fallback to the restricted-token mode"
```

当时 `tools/build-shim.mjs` 的输出里出现过 `moved the locked output aside
(winstage-shim.dll.stale-…)` —— 说明有**残留进程仍持有旧 DLL**；`shim/out` 里当时积了 13 个
`.stale-*` 文件（最早可追到 T1/T2 时期）。清掉这些残留后连续 5 次运行全部为
`effective=shim / tier=TS / fallback=none / 5,5`，因此判定为**那次构建窗口的瞬态**（新 DLL 刚落地
即被注入），不是暂存逻辑回归。

运维建议：重建后若第一次探测回退 T1，先清 `shim/out/*.stale-*`（或
`node tools/stop-shim-holders.mjs`）再重试一次；不要在 `.stale-*` 堆积的情况下判断档位。

## 6. 档位接线：让**会话里的 shell** 真的走 TS（2026-09-30）

### 6.1 缺的是什么

档位选择**早就实现好了**（`selectLaunchMode()`，`src/executor.mjs:3031`：`TS`/`auto` ⇒ 探测通过就走
`shim`，否则记 `fallbackReason` 回退受限令牌 `T1`）。缺的只是把它交给执行器：

- `WindowsStageExecutor` 的构造参数 `tier`（`src/executor.mjs:1441` 起）会按 `TS`/`auto` 跑三级探测，
  并把生效档位写回实例；
- 而 `dsh-plugin/shell-executor.mjs` 之前把它**写死**成 `'T1'`（原 `:550`）⇒ 会话里真正跑命令的执行器
  永远在受限令牌档，`--tier TS` 只活在能力探测里（正是 `docs/T5` §1.3 那条"T1 下 T2/T3/T4 不可能绿"）。

### 6.2 改了什么

| 文件 | 改动 |
|---|---|
| `dsh-plugin/shell-executor.mjs` | `this.tier` 默认 `'T1'` → **`'auto'`**，并接受行 `config.tier` / 环境变量 `WINSTAGE_TIER` 覆盖 |
| `src/executor.mjs` | `probeTransparentShim()` 加**进程内缓存**（键 = 产物 path+size+mtime、暂存根、captureDir、timeout；`cache:false` / `refresh:true` 绕过）；原实现改名 `probeTransparentShimUncached()` |

缓存不是优化而是必需：shell 执行器**每条命令新建执行器**，而金丝雀实测 **6.97 s** ⇒ 缓存后第二次
**1 ms**（`refresh:true` 仍重跑并给出新对象，实测 6.9 s）。

### 6.3 验证

```
node .t\shell-selftest.mjs                 # exit 0，失败项：（无）—— 契约形状未变（该套件本就没有 tier 断言）
node src\capability-probe.mjs --tier auto  # requested=auto effective=shim tierEffective=TS fallback=none summary=5/5
```

### 6.4 怎么开（需要人 + 重启）

```powershell
setx WINSTAGE_SHELL 1        # 用户级；只影响此后启动的进程
```

完全退出并重新启动 DSH（bundle 那两行的 `!!js disabled` 是**组合期**求值，读的是**宿主环境变量**与
profile 文件里的 `enabled`），然后复核：

```
plugin_manager list_plugins
  include:winstage-shell  enabled=true active      ← 接管 ctx.shell
  include:pwsh-sandbox    enabled=false            ← 平台 shell 让位
```

以及任意命令的子进程环境里应出现 `WINSTAGE_STAGE_ROOT` / `WINSTAGE_SHIM_CONFIG`。

预期与代价：
- **首次**命令多 ~7 s（金丝雀探测；按（产物 stat + 暂存根）缓存，通常每个会话一次）；
- 探测不过 ⇒ 自动回退 `T1`（`fallbackReason` 里带原因），行为与接线前完全一致；
- 开了 shell 面之后**两个面都在暂存**：命令写入不再直接落真实磁盘，代理自己的 shell 写入也一样
  （要批准才落盘）—— 这正是"透明沙箱"该有的形态，但"用 shell 绕开暂存"这条逃生口也随之消失；
- 想单侧覆盖：行 `config.tier: T1`（或 `WINSTAGE_TIER=T1`）可强制回受限令牌档。

## 7. ★ 自动对准基线（用户要求"要自动对准基线"，2026-09-30）

### 7.1 为什么要自动

§4.5 记的那个坑（陈旧候选在重启对账时把真实文件**覆盖回旧内容**）与"面板说基线过期、请自己
`/winstage rebase`"是同一个根因：暂存条目是"相对某个基线的 diff"，而基线随时可能被**外部**改动
（shell / 另一个进程 / 编辑器 / 代理自己用 shell 落盘）。旧行为把"重述基线"留给用户手动触发，
于是要么漂移留着、要么在重启对账时出现"陈旧赢过现实"的窗口。

### 7.2 改了什么

| 文件 | 改动 |
|---|---|
| `dsh-plugin/review-service.mjs` | 新增 `autoRebaseDrifted({force})` + `autoAlignQuietly()`；**每次修改**（`afterMutation()`，fs 写/改钩子）与**每次发布**（`publish()` = afterMutation / shell 命令的 `publishWorkspaceSnapshot()` / `/winstage refresh` 的共同出口）都**强制**对齐；`reload()`（fs 面每次读都会跑）走 1 s 节流版 |

语义**完全复用**已有的显式 rebase 路径（`_rebase()` → `Workspace.rebaseEntry()`）：
只重述 `baseHash/baseKind`，**不动** `stagedHash/state` ⇒ **是重述基线，不是强制覆盖**：

- 真实内容 ≠ 暂存内容 ⇒ 变成一条**可批准**的新 diff（before = 现实）；
- 真实内容 == 暂存内容 ⇒ 无净变化，条目自动退出视图（连批准都不需要）；
- 顺带丢弃受影响候选，并按剩余净 diff 重新冻结（同一条代码路径，不另造一套）。

工程细节：
- **每次修改都对齐**（用户要求）：`afterMutation()` 的第一件事就是强制对齐，**在冻结候选之前**
  ⇒ 候选的 `before` 一定是"现实"，不会带着过期基线发出去；`publish()` 同样强制（覆盖 shell 命令
  与 `/winstage refresh` 那条路）。这两处用 `force`，不受节流限制；
- **1 s 节流只给读路径**（`AUTO_REBASE_INTERVAL_MS`）：`reload()` 在 fs 面每次读上都会跑，而漂移
  判定要逐条 stat+hash 真实文件；节流让"改完立刻对齐"与"别为每次读都付这个钱"同时成立；
- **重入保护**：`_rebase()` 会经 `reconcileCandidates()`/`ensureCandidate()` 再次触发 `reload()`，
  没有这道闸就是无限递归；
- **逃生口**：`WINSTAGE_AUTO_REBASE=0` 关闭自动（退回显式 `/winstage rebase`）；
- 失败只记 error 级日志，**绝不影响**本次操作（与 review-service 里其它失败通道同一纪律）。

### 7.3 回归门

```
node .t\auto-rebase-selftest.mjs      # 15/15，含变异自证
```

它锁住六件事：暂存不改真实磁盘 → 外部改动后确实漂移 → **自动对齐后真实文件内容一字不变**
（no clobber）且 `baselineDrift().stale === false` → `WINSTAGE_AUTO_REBASE=0` 时漂移保留
（变异自证）→ 节流窗口内**不 force 不对齐、force 立刻对齐** → **源级断言** `afterMutation()` 与
`publish()` 里确实调用了 force 版（否则"每次修改都对齐"只测到空壳）。
