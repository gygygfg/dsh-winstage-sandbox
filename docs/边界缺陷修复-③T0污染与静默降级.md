## 2. 根因（`file:line`）

### 根因一（污染为什么会留下）：`process.exit()` 跳过了 `finally` 里的 `dispose()`

- `src\cli.mjs:259`：`process.exit(execution.exitCode === 0 ? EXIT.OK : EXIT.FAIL)` —— 在 `try` 块内部；
- `src\cli.mjs:260-262`：`finally { executor.dispose() }`。

`process.exit()` **不执行 `finally`**。本会话用同形状脚本实测（`node .t\fix3-repro\diag-exit-order.mjs`）：`finally` 一行都没打印，退出码 0。

于是 `WindowsStageExecutor.dispose() → this.appContainer.dispose() → AppContainerLauncher.revokeGrants()`
（`src\executor.mjs:640-653` 改造前 / `src\executor.mjs:677-694` 现在）**永远不会被调用**：

- T0 在 `attachRuntime()` 里用 `icacls <staged> /grant *<包SID>:(OI)(CI)M` 授予的 ACE 从不撤销
  （`src\executor.mjs:945` 的 `grantPathToAppContainerSid`，调用点 `src\executor.mjs:489`）；
- 每次 T0 运行再叠一条（包 SID 是 per-profile 的，所以是**多条**不同 SID 的历史累积）；
- 只要有任何一条在，之后该工作区的 T1 受限令牌写暂存根就 `Access is denied.`，且**重跑 `init` 不自愈**。

### 根因二（为什么会"静默"）：`run()` 从不看自检结论

`src\executor.mjs::run()`（`src\executor.mjs:2437` 起）在 `init()` 之后只过三道闸门：
`assertNetworkPolicyEnforceable()` / `assertStagingQuota()` / `CWD_OUTSIDE_STAGING`，
**没有一道读 `initReport.checks`**。因此 `inside-staging-write-allowed=fail` + `enforcement=degraded`
只被写进 `sandboxInit` 报告，人读通道不打印、执行路径不拦 ⇒ 命令照跑、退出码 0。

### Fix C（预防）：把授予 ACE 的那条路径接上退出兜底

`src\executor.mjs:508-532`：`AppContainerLauncher.attachRuntime()` 在授权成功后注册
`process.once('exit', this.exitHook)`（`this.exitHook = () => this._revokeGrantsOnExit()`）；
`_revokeGrantsOnExit()`（`:525`）做**同步** ACL 撤销（`icaclsRun` 是 `spawnSync` + 文件重定向，退出路径可用）；
`AppContainerLauncher.dispose()`（`:688`）显式撤销后 `removeListener`（幂等，不二次撤销）。

- `process.exit()` **会**触发 `exit` 事件 ⇒ 兜底成立；
- 兜底本身失败也不改变用户可见结果：漏掉的那条由 Fix B 在下一次 `init`/`exec` 摘掉（纵深防御）。

**ACE 是否来自外部依赖？** 不是。授权调用点是**本仓库自己构造的**
（`src\executor.mjs:489` → `grantPathToAppContainerSid` → `icaclsRun`，即 `icacls <dir> /grant *<sid>:(OI)(CI)M`），
`@deepseek-ai/dsh-sandbox-windows-acl` 只负责受限令牌与它自己的写 SID，**不写包 SID ACE**。
因此 Fix C 在本仓库范围内可做，无需绕外部依赖。

3. **`verdict='unmeasured'` 在真实链路上极难自然触发**：自检的输出不可解析时，
   `inside-staging-write-allowed` 会以 `fail` 记下来（reason 在 detail 里可见），
   所以"缺判据"主要发生在自检根本没跑起来（spawn 失败）时。
   闸门对两种形态都拒绝，但 `unmeasured` 只有替身用例（A5）覆盖，**没有真机端到端证据** `[未实测]`。
4. **AppContainer 包 SID ACE 的 OS 层因果只做到"现象级定因"**：本会话证明了
   "非继承的 `S-1-15-2-*` 允许 ACE ⇒ 受限令牌写被拒"，并用 `(RX)`/非包 SID 对照排除巧合；
   但"为什么包 SID 的显式 ACE 会让 `WRITE_RESTRICTED` 令牌在同一目录上被拒"的 Windows 内部机制
   **未取证**（`[推断]`：与包 SID 的受托者语义/受限 SID 交集判定有关）。修复不依赖该机制的细节。
5. **`icacls` 是外部进程调用**（`spawnSync` + 文件重定向）。本仓库既有纪律如此（残余边界 R10 说明管道捕获不可用），
   `readDaclSddl` 因此是"外部进程 + 纯解析"的混合体：解析有离线断言，**调用本身没有离线断言**。
6. **`.t\boundary-os\ws5\.dshstage\staged` 仍带一条包 SID ACE**：它是审计证据工作区，
   本会话刻意不动（`.t\fix3-clean-ws5.txt` 为该现场）。它会在下一次 `init`/`exec` 被修复路径摘掉。

## 9. 残余风险

1. **修复路径会动真实 ACL。** 判据限定为"**非继承** + `ACCESS_ALLOWED` + 受托者是 `S-1-15-2-*`"，
   作用域限定为"调用方给的那一个目录（生产=暂存根）"，不下钻、不碰父目录。
   若将来本仓库在暂存根上**故意**保留一条包 SID 授权（例如让某个长驻 AppContainer 助手持续写暂存根），
   这个修复会把它摘掉 ⇒ 那种设计必须显式传 `repairStaleAces:false`。
2. **`init` 现在是"有副作用"的动词**（会在暂存根上执行 `icacls /remove:g`）。
   它是幂等的；但只读审计场景若需要"绝不改盘"，应传 `repairStaleAces:false` 或 `DSH_CONFORMANCE_*` 式开关（**目前没有命令行开关** `[未实测]`）。
3. **`init --json` 新增字段 `staleAppContainerAces`**：纯新增，既有消费者按名取值不受影响；
   但把 `init --json` 输出做**逐字节**比对的脚本需要更新。
4. **两个既有替身套件（`executor-stub` / `integration-wiring`）现在显式注入"闸门判定=pass"**。
   这是本仓库既有的测试缝约定（`capabilities(overrides)` / `overrides.simulate`：显式声明，绝不让"没测"变成"通过"），
   但它**只在这两个离线套件里**是显式的；若将来有人把这道缝当成"生产默认"，就会重新引入静默降级。
   新套件 A 段的 `--plant` 已把"闸门被拿掉"变成红灯，这是对上述误用的机器防线。
5. **`process.once('exit')` 兜底只在"退出时还能跑同步代码"的前提下成立**（正常 `process.exit()` 与自然退出可以；
   被强杀/断电不行）。兜底漏掉时由 Fix B 的修复路径兜住，但**那一刻工作区的 T1 仍会短暂失效** ——
   这正是 Fix A 存在的意义（拒绝而不是静默跑）。
6. **并行改动风险**：本轮 `shim\out\winstage-shim.dll` 被外部会话重建，直接改变了两个沙箱套件的读数（§8.1/8.2）。
   本修复没有触 `shim\**`，但"谁的改动导致哪条断言变红"需要**时间戳 + 产物哈希**才说得清，建议门禁设计上把
   产物新鲜度检查与代码断言分开（当前 `registry-conformance` A 段把两者混在一起）。

### 11.2 §9 第 4 条（两个替身套件的"闸门判定=pass"测试缝）——审计结论

**判定：可接受的"有界夹具注入"（不是会掩盖真实失败的全局旁路）。** 精确行号：

- 注入处：`tests\executor-stub.mjs:330-344`、`tests\integration-wiring.mjs:289-303`
  （两处都是 `...(options.stagingWriteCheck === undefined ? { stagingWriteCheck: { evaluate: () => ({ verdict: 'pass', … }) } } : {})`，
  并带显式注释；调用方可用 `options.stagingWriteCheck` 覆盖）。
- 消费处：`src\executor.mjs:1599-1601`
  （`const override = this.options.stagingWriteCheck; … : this.stagingWriteEnforceability()`）。

判定依据（逐条可核）：

1. **只在这两个离线套件里显式传入**：`makeExecutor()` 是本套件自己的构造包装；生产侧六个构造点
   （`src\cli.mjs:190`、`src\audit.mjs:444`、`src\capability-probe.mjs:332`、
   `dsh-plugin\shell-executor.mjs:999`、`dsh-plugin\provider.mjs:159`、`dsh-plugin\selfcheck.mjs:56`）
   都传字面量选项对象，**没有任何一处会带上 `stagingWriteCheck`** ⇒ 生产路径不可达。
2. **注入是必要的**：这两个套件的 `spawnPipedProcess` 是替身，自检 JSON 恒为空
   （`tests\executor-stub.mjs:219` 默认 `stdout: ''`）⇒ 真判据是 `unmeasured` ⇒ 不加缝则
   `run()` 会以 `STAGING_WRITE_UNVERIFIED` 拒绝**所有**用例，网络/配额/顺序断言全部无法执行。
3. **只关掉这一道闸**：其余 fail-closed 闸门仍是真判据并被断言（`CWD_OUTSIDE_STAGING`、
   `SANDBOX_NETWORK_POLICY_UNENFORCED`（`integration-wiring.mjs:465`）、配额拒绝
   （`integration-wiring.mjs:570/590`）、零 spawn 断言）⇒ 不是"整体放行"。
4. **判据本身有专门覆盖**：`tests\boundary-degraded-failclosed.mjs` A2（纯判定函数 pass/fail/unmeasured/
   `documented-residual` 不算 pass）与 A5（降级 ⇒ `run()` 抛型别错误且**命令未 spawn**；健康 ⇒ 正常执行；
   不可解析 ⇒ 同样拒绝），其 `--plant` 模式会因闸门被拿掉而**8 项见红**。

**残余（如实声明）**：该缝是"替换判定结果"而不是"提供一次真实测量"，因此
(i) 它比 `overrides`（注入依赖）更强 —— 若将来有人把 `stagingWriteCheck` 当成生产默认值传入，就会重新引入静默降级；
(ii) 这两个套件**看不到**闸门自身的行为（该覆盖在 A2/A5）。本轮**未改动**这两个测试文件
（判为可接受），只在此登记结论与行号。
