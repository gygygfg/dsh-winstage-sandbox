### 1.1 关键机制：两层沙箱，写路径被分流

| 写入路径 | 行为 | 实测 |
|---|---|---|
| DSH 文件工具（`write` / `edit`） | **不落真实磁盘**。返回 "Created file"，实际只生成 `.dshstage\sessions\<sid>\staged\<相对路径>` + 内容寻址 `blobs\<前2>\<sha256>` + `candidates\cs_*.json`（`source=dsh-write`, `status=pending`） | 三方独立复现：t1 F3/F4、t3 t3-14、verifier f |
| pwsh 工具的写 | **直接落真实磁盘，且不进审批队列** | 本轮实测：`shell-write-bypass-marker.txt` 落盘 `True`、staged `False` |

> 结论：**write 工具的产物必须人工审批才落盘；而 shell 写入绕过了整个审批面。** 顺序为：`write` 落盘 `False`（在暂存区）→ `pwsh` 落盘 `True`（真实磁盘，不在暂存区）。
> 这是设计上的审批覆盖率缺口（详见 §8 缺陷 D1）。对本轮测试的直接后果：**所有测试脚本必须用 pwsh here-string 落盘才能被 node 执行**。

### 1.2 独立复核的哈希链闭合

暂存区内容与提交内容的哈希链完整闭合：`staged 文件 sha256` == 候选 `changes[].after.hash` == `blobs\<前2>\<sha256>` 文件名。
验证者自建探针实测：`e3c30070...746c` 三处一致（`verifier-01-staging.txt`）。

### 1.3 取证障碍（会影响脚本写法，非产品缺陷）

| 现象 | 原始错误 | 影响 |
|---|---|---|
| pwsh 管道 / 变量捕获原生 exe 的 stdout | `Program 'node.exe' failed to run: Access is denied`（带 `[sandbox: file access denied under workspace-write mode]`），`whoami.exe`、`git.exe` 同样命中；`Start-Process -RedirectStandardOutput` 亦被拒 | 无法用管道采集原生工具输出；绕行办法：由被测程序自己写文件，或 `cmd /c "... > file 2>&1"` |
| `reg.exe` / `cmd.exe` / `node.exe` 等外部可执行文件启动 | `ApplicationFailedException: Program 'reg.exe' failed to run: Access is denied`（11/11 全部 launched=False） | **t4 因此无法评估 `.reg` 导入通道与 `/reg:32` vs `/reg:64` WOW64 视图对照** |
| `Get-NetTCPConnection` | CimException HRESULT `0x80041003` 拒绝访问 | 监听面清点改用 .NET `IPGlobalProperties` + netstat |
| 内存/进程枚举 | `Get-Process -Id <pid>` 对所有 PID 返回 "Cannot find a process" | 端口只能归因到 PID，无法归因到进程名 |

> 有意思的对照：令牌是"受限"的（注册表全拒），却能成功绑定 `0.0.0.0:80` 且 `IsInRole(Administrator)=False`——说明注册表拒绝来自 **DSH 路径级策略**而不是"没权限"。

### 5.3 压力一致性：**全拒、无静默成功**

### 5.5 归因：**外层 DSH 受限令牌，不是内层托盘**
