## 1. 构建不可用（先决条件）

上一轮结束时 `shim/src/ws_file.c` 里有两处复制粘贴的调试行（`ws_DeleteFileW`、

shim/src/ws_file.c:293:34: error: use of undeclared identifier 'dwDesiredAccess'
shim/src/ws_file.c:512:66: error: use of undeclared identifier 'dwCreationDisposition'

这解释了"交接时最后一次成功构建是 14:20，而 `ws_file.c` mtime 是 14:24"。

修完 `node tools/build-shim.mjs` → 0 warning、15 exports。

## 2. IAT 自递归：注入载体为什么会静默死去

### 现象
`WINSTAGE_SHIM_VERBOSE=1` 时注入 `powershell.exe` 必定失败：注入器报
`{"ok":false,"error":"remote LoadLibraryW failed","win32Error":126}`。
关掉 verbose 就正常。`stale`/`old` 两个旧 DLL 在同样 env 下正常。

### 定位（逐步，皆有日志）
1. 加 init 面包屑后：日志停在 `init-phase: mask_init rc=0` 之后、`hooks installed` 之前
   ⇒ 死在 `ws_hook_install()` → `ws_patch_all()`。
2. 加逐模块面包屑后：死在**第 3 个模块**（`base=0x7FFA62490000`，即 kernel32/kernelbase 一级）。
3. 加逐 patch 面包屑后，最后一行是：

```
patch: base=00007FFA62490000 api=CreateFileW slot=00007FFA625198A0 oldfn=00007FFA612E3170 newfn=0000000053031E70
```

   即：**刚刚把 `CreateFileW` 的 IAT 槽改成 `ws_CreateFileW` 之后，下一次 `ws_log()` 就死了。**

### 机制
`ws_log()` 用自己的 IAT 调 `CreateFileW` → shim 的 IAT 槽指向 provider 模块的导出 → 该导出经
provider 自己的 IAT 槽转发 → **那个槽刚被我们改成 `ws_CreateFileW`** ⇒ 进入钩子 ⇒ verbose 下钩子
里的 `WS_TRACE_FILE` 又调 `ws_log()` ⇒ 无限递归。

### 修法（两处，互补）
1. **`ws_hook.c`：永不给自己 import 的模块打 IAT。** 从 DLL 自己的 import 目录收集 provider 名
   （`ws_collect_self_providers`），`ws_patch_all` 里按 `BaseDllName` 跳过它们
   （`ws_is_self_provider`，用本地 `WsLdrEntry` 覆盖结构读名字，因为工具链的 winternl.h 里没有
   `BaseDllName`）。日志实测：`skip provider module … KERNEL32.DLL / ADVAPI32.dll`。
   **注意 `ucrtbase` 不在跳过名单里**，所以 `fopen` 这类 CRT 文件 I/O 仍然被拦截。
2. **`ws_util.c`：`ws_log()` 走捕获到的原始 `g_orig.CreateFileW`**（未捕获前才退回 IAT 调用）。
   这样即使将来漏判某个 provider，内部日志也不会自我递归。

产物：patch 站点数从 121/11 模块降到 ~56/8 模块；verbose 模式恢复正常（72 行日志）。

### 为什么这曾是"redirect 0 字节"的一部分
递归只发生在 verbose；不 verbose 时钩子仍然会**重入**（`ws_should_intercept` 命中 stageRoot
后落到 `g_orig.CreateFileW`），文件写入路径被这条重入链扰动过。修掉之后，PowerShell 的 `>`
重定向立即写出正确字节（见 §3）。

## 3. redirect 门禁：真实根因是"看不见自己写的东西"

### 证据
`node src\capability-probe.mjs --tier TS` 的金丝雀（`$f = Join-Path $env:TEMP …; & node --version > $f`）
在覆盖层里**写对了**：

```
22 B  .dshstage\capability-probe\staged\fs\C\...\temp-32c2d08b\winstage-canary-<guid>.txt
      = UTF-16LE BOM + "v24.21.0\r\n"          # PS 5.1 的 > 写 UTF-16LE
shim.log: 恰好一条 CreateFileW staged(write)
```

但 shim 日志里**没有任何**对该路径的读打开，也没有 mask 拒绝。原因是 canary 的回读被前置守卫拦住：

```powershell
try { if (Test-Path -LiteralPath $f) { $redirText = (Get-Content -LiteralPath $f -Raw)… } } catch { }
```

`Test-Path`/`File.Exists` 走 `GetFileAttributesExW`（+`GetFileAttributesW`），
这两个 API **没有被 hook**，于是它们看的是**真实文件系统**，真实文件当然不存在 ⇒ 直接跳过回读 ⇒
`redirectText=""` ⇒ `redirectOk=false`。

结论：这不是 CoW 缺陷（覆盖层字节完全正确），而是**存在性/属性 API 不查覆盖层** ——
它同时违反"沙箱内进程认为写入成功"这一目标本身。

### 修法
`shim/src/ws_file.c` 新增 `GetFileAttributesW/A`、`GetFileAttributesExW/A` 四个覆盖层感知的
stat 钩子（`shim/src/ws_hook.c` 增加对应 target 与 `g_orig` 槽位）：

* 不该拦截 → 原样调用原 API；
* 有白障（whiteout）→ 表现得"文件不存在"；
* 覆盖层有副本 → 报告**覆盖层文件**的属性/大小；
* 否则 → 落到真实路径（read-through）；
* 读掩码在 stat 上也生效（存在性不作为侧信道）。

`ws_file_exists()` 内部仍用**真实** API（它决定 CoW，绝不能走新包装器）。

## 4. firewall 门禁：一个 `icacls` 就能解释的门禁

### 现象
未注入：`Get-NetFirewallProfile` → `FW-OK:Domain …`；
注入后：`FW-ERR:Access is denied.`（同一台机、同一用户、同一个 shell 命令）
但 `Get-NetTCPConnection`、`reg query FirewallPolicy` 都正常，暂存 journal **0 字节**
（即不是任何 `HARD_DENY`）。

### 隔离（每一步都排除一类假设）
用注入器新增的诊断开关做控制实验（`--no-inject` = 创建进程但**完全不加载任何 DLL**）：

| 用例 | 结果 |
|---|---|
| 直接启动 powershell（不经注入器） | `CIMV2=OK STDCIM=OK NETFW=OK` |
| 注入器 `--no-inject`（不加载 DLL） | `STDCIM=ERR:Access is denied.` |
| 注入器 + `version.dll`（系统无害 DLL） | `STDCIM=ERR:Access is denied.` |
| `--no-suspend` / `--no-inherit` / `--inherit-env` 任意组合 | 全部 `ERR` |
| 把 `winstage-inject.exe` 复制到 `C:\Windows\Temp` 后运行 | `FW-OK:Domain,Private,Public` |

⇒ 与钩子、与文件/注册表族、与 `CREATE_SUSPENDED`、与句柄继承、与环境块**都无关**。

### 根因
```
whoami /groups（直接启动）      Mandatory Label\High Mandatory Level   S-1-16-12288
whoami /groups（注入器启动）    Mandatory Label\Low  Mandatory Level   S-1-16-4096
```
令牌**完全相同**（24 条特权、组列表逐项相同）—— 差的是**进程完整性级别**。
Windows 用**镜像文件上的 mandatory label** 决定新进程的 IL：

```
C:\Users\Administrator\Desktop           Mandatory Label\Low Mandatory Level:(OI)   ← 显式设置
C:\Users\Administrator\Desktop\WinStageSandbox\shim\out\winstage-inject.exe
                                         Mandatory Label\Low Mandatory Level:(I)(NW) ← 继承
```
于是 `winstage-inject.exe` 自己跑在 Low IL，它创建的所有载体都是 Low IL，
而 `root\StandardCimv2`（`MSFT_NetFirewallProfile` ⇒ Windows 防火墙）**要求高于 Low 的完整性**，
`root\cimv2` 则不要求 —— 正好解释了"只有防火墙这一项红"。

### 修法
1. **构建期自愈**：`tools/build-shim.mjs` 在产物写完后检查 mandatory label，
   若为 Low 且本次构建的 IL ≥ Medium，就 `icacls <artifact> /setintegritylevel Medium`
   （只修坏掉的情形，绝不上调超过调用者自己的 IL，失败只告警不失败构建）。
2. **已就地修复** `shim/out/*` 与两个并行子会话的私有产物。
3. 复验：同一命令、同一产物，注入后 `FW-OK:Domain`。

> 环境建议（未由本仓库改动）：`C:\Users\Administrator\Desktop` 上的
> `Low Mandatory Level:(OI)` 会让**桌面上任何 exe** 都以 Low IL 运行；
> 若要根治可执行 `icacls C:\Users\Administrator\Desktop /setintegritylevel Medium`。
> 本仓库的构建期自愈已使门禁不再依赖这一步。

### 4.1 同一轮交付的注册表契约变更（T3 v1.4，独立子会话完成并自验）
`firewall` 与注册表无关这一点由两条独立证据链同时确认（Lead 的 `--no-inject` 控制实验、
该子会话的 inert/version.dll/禁用族控制实验），因此这一轮注册表侧只做交接文档要求的两件事：

* `KEY_WOW64_64KEY` 在 64 位进程里按**文档 no-op** 处理（`ws_create_key` 不再用裸
  `WS_SAM_WOW64_MASK` 判 restricted）；`KEY_WOW64_32KEY` 属于覆盖层无法复现的视图位 ⇒
  **透传真实 API + 记 `UNSTAGED`（kind 6 / flag 0x0010 / status 恒 0）**，不再伪装成
  `ERROR_ACCESS_DENIED`；apply 路径显式忽略 `UNSTAGED`（那些调用已经在真实系统上生效过，

## 5. 白障标记把祖先目录"删掉"：stat 钩子暴露出的潜伏缺陷

### 现象（A2 发现，Lead 独立复现）
一旦 `<stageRoot>\wo\` 下出现**任意**一个白障标记，之后所有注入的 PowerShell 都
**无法自加载 cmdlet**：`Write-Output : The term 'Write-Output' is not recognized`。
`cmd`/`node` 载体不受影响；`WINSTAGE_SHIM_DISABLE_FILE=1` 立即恢复正常
⇒ 文件族的白障判定。

复现（确定性，4/4）：
```
01-no-whiteout                 exit=0 out="PSOK3"
02-whiteout-unrelated          exit=1 "Write-Output ... not recognized"
03-whiteout-desktop            exit=1 同上
04-whiteout-file-family-off    exit=0 out="PSOK3"
```
（标记名与位置无关，甚至 `wo\C\Users\Administrator\Desktop\zzz.txt` 也一样。）

### 机制（用 stat 探针逐路径对比得出）
在载体里用 `[IO.File]::Exists` / `[IO.Directory]::Exists` 问同一组路径：

```
P6 C:\Windows   pass="file=False dir=True"     ← 无白障
                fail="file=False dir=False"    ← 有白障
```

`ws_stage.c` 的读分支先查白障：`ws_wo_path(path)` 命中且**路径存在**即判 WHITEOUT。
但 `ws_fs_map` 会把 `C:\...` 映射成 `<root>\wo\C\...`，于是
`wo\C\Windows\Temp\zzz-unrelated.txt` 这个标记让
`wo\C`、`wo\C\Windows`、`wo\C\Windows\Temp` **作为目录存在** —— 而"存在"测试
把目录也算存在，于是 `C:\`、`C:\Windows`、`C:\Windows\Temp` 全部被判为"已删除"。

这个缺陷一直潜伏：stat 系列没被 hook 时，PowerShell 的存在性检查走真实盘，看不出问题；
A1 把 `GetFileAttributesW/ExW` 接上覆盖层后，`C:\Windows` 在启动期就"消失"，
PowerShell 判定会话被锁定并拒绝加载自己的 `.psm1` 模块，于是连 `Write-Output` 都没有了。
同一条误判还会让**任何祖先目录**的读变成 `ERROR_FILE_NOT_FOUND`。

### 修法
`shim/src/ws_stage.c` 新增 `ws_marker_exists()`：白障标记**必须是普通文件**
（`!(attrs & FILE_ATTRIBUTE_DIRECTORY)`），并在 `dp_file_resolve` 与
`dp_file_whiteouted` 中替换原来只看"存在"的判断。目录只作为更深标记的父链容器。

修后：上面 4 个用例全绿；`run-shim-closedloop` 的 `E8.carrier-powershell` 恢复。

> 已知残余（窄）：若**先**删除了 `…\b\x.txt`（于是 `wo\…\b` 存在为目录），**再**删除目录
> `…\b`，`dp_file_whiteout` 仍以"wo 路径已存在"短路，无法在该处创建标记文件 —— 目录删除
> 不会被记录。调用方仍返回成功，因此属于"删除目录在沙箱内不可观测"的窄缺口；
> 与"目录枚举不合并"同源，尚未闭合。

## 6. 注入器：不再编造错误码（附带诊断开关）

远程 `LoadLibraryW` 返回 NULL 时，旧代码写死 `win32Error=126 (ERROR_MOD_NOT_FOUND)`，
把"真实失败"藏了起来。现在：

* 失败时报 `ERROR_DLL_INIT_FAILED`，并新增 `remoteThreadExit`（远程线程真实退出码）；
* 新增诊断开关（默认关，纯 additive）：
  `--no-inject`（只创建进程不加载 DLL）、`--inherit-env`（不重建环境块）、
  `--no-suspend`、`--no-inherit`。§4 的隔离表就是用它们做出来的。

## 7. 残余（如实声明，不当作已解决）

### 7.1 ~~注入载体启动 flake ≈ 4%~~ → **已定位并修复：shim 自己踩掉了 LastError**
**结论修正（重要）**：本节最初的"4% 环境 flake"归因是**错的**。真正原因是 shim 在
真实 API 调用**之后**写日志（`ws_log` → `CreateFileW`/`OPEN_ALWAYS`），把线程的 last error
覆盖成 `ERROR_ALREADY_EXISTS`(183)。CLR 启动时正读到这个值，于是报
`Starting the CLR failed with HRESULT 800700b7`（0xb7 = 183）并中止。

* 生产路径同样中招：`g_ws.traceStagedOps` 默认**为 1**，所以 `CreateFileW staged(write)` /
  `copy-on-write` 这类日志在生产里也会打；`WS_TRACE_FILE`（verbose）只是把它放大。
* 修法：`shim/src/ws_file.c` 在每个"调用真实 API 之后再写日志"的位置
  `GetLastError`/`SetLastError` 保存恢复。修前 3/3 复现，修后 3/3 干净。
* 我之前测的 flake 数字是**强制 verbose** 的结果（`carrier-flake.mjs` 当时写死 verbose），
  所以偏高；该脚本现在默认测生产路径（`--verbose` 才开）。

原始测量（保留作为"verbose 放大"的证据，不再是未解之谜）：

| 构造 | 失败/次数 |
|---|---|
| 不注入（直接 `powershell -Command`） | 0/24 |
| 注入 benign `C:\Windows\System32\version.dll` | 0/30 |
| 注入本 shim + **强制 verbose** | 5/96（≈4%，即上面的 LastError 踩踏） |
| 注入本 shim（Low 标签对照） | 0/12 |

两种签名（都与 183 一致）：
```
exit=0xffff0000  The shell cannot be started. A failure occurred during initialization:
                 Could not load file or assembly 'System.Data.dll' … (0x8007054F)
exit=0xe0434352  由于 Exception.ToString() 失败，因此无法打印异常字符串。
```

**待办（本轮未做）**：同一"调用后写日志"的模式在其它钩子族里也存在
（`ws_reg.c`、`ws_hook.c`、`ws_t3reg.c`）。注册表族的 trace 是 verbose-gated，生产里不打，
因此优先级低，但值得一次统一审计。

### 7.1b 另外三个由 A1 定位的载体级缺陷（已修，均有用例）
1. **AppLocker 探针**：PowerShell 启动时写 `%TEMP%\__PSScriptPolicyTest_<rnd>.ps1/.psm1`
   再问"它存在吗"；如果对一个**只存在于覆盖层**的探针文件回答"存在"，PowerShell 判定脚本执行
   被封锁，拒绝加载自己的 `.psm1` 模块 ⇒ `Write-Output`/`Out-File`/`Test-Path` 全部
   "not recognized"（实测 13/13）。修法：这两个名字的 stat **交给真实文件系统**
   （`ws_is_lockdown_probe`），其余路径仍走覆盖层。
2. **`TRUNCATE_EXISTING` 未 CoW**：对只有真实副本的文件做截断会以 `FILE_NOT_FOUND` 失败；
   现在截断也先 CoW（与真实 API 的"文件必须存在"语义一致）。
3. **fail-open 前缀匹配（安全相关）**：`ws_should_intercept` 用裸前缀比较 stageRoot/passthrough，
   于是**真实文件名恰好以 stage root 开头**时（例：stage=`…\stage`、文件=`…\stage-report.txt`）
   会静默绕过沙箱写到真实磁盘。现在要求前缀在分隔符处结束（`ws_under_prefix`）。

### 7.2 `node` 的删除不经 `DeleteFileW`（白障缺口）
`fs.unlinkSync` 用 `SetFileInformationByHandle(FILE_DISPOSITION_INFO)` 删除：
shim 会 CoW 那个打开，调用方删掉的是**覆盖层副本**，不写白障，真实文件仍可见
