## 1. P0-2 测试工具缺前置校验（已修 ✅）

**问题**：注入器被隔离/构建不完整时，工具仍逐条打印"载体失败 N 次"，把**环境故障伪装成产品失败**。

**修法**：三个工具在开跑前用 `tools/build-shim.mjs` 已有的
`artifactNames(profile)` + `checkArtifactIntegrity(outDir,names)` 校验三件套
（`winstage-shim.dll` / `winstage-inject.exe` / `winstage-probe.exe`：存在、`size>0`、`looksLikePe`）。
失败即打印 `ENVIRONMENT UNAVAILABLE: missing/corrupt <names>; run node tools/build-shim.mjs`
并以**独立的环境退出码**退出：

| 工具 | 环境码 | 说明 |
|---|---|---|
| `tools/carrier-flake.mjs` | **2** | 该工具本是 informer，正常恒退出 0 |
| `tools/smoke-inject.mjs` | **3** | 既有抛错码是 2 |
| `tools/run-shim-closedloop.mjs` | **3** | 既有抛错码是 2 |

位置：`tools/carrier-flake.mjs:24-36`、`tools/smoke-inject.mjs:48-61`、`tools/run-shim-closedloop.mjs:63-75`。

**`[实测]`（本机）**：把 `WINSTAGE_SHIM_OUT` 指向空目录：
`smoke-inject` 退出 3、`carrier-flake` 退出 2、`run-shim-closedloop` 退出 3，均打印同一句
`ENVIRONMENT UNAVAILABLE ...`，**不再打印任何"载体失败"行**。

## 2. P1 —— 沙箱本体

### 2.1 P1-3 `CreateProcessW` 钩子里的 30 s 阻塞等待（已修 ✅）

- 位置：`shim/src/ws_proc.c`（原 `WaitForSingleObject(th, 30000)`）。
- 修法：改为 **有界等待**，默认 `WS_INJECT_WAIT_DEFAULT_MS = 2000`（`ws_proc.c:41`），
  可用环境变量 `WINSTAGE_INJECT_WAIT_MS`（50..60000）覆盖（`ws_proc.c:43`）。
  超时即记录 `STUCK remote LoadLibraryW did not complete within ... ms; failing closed`
  （`ws_proc.c:189`），返回失败；调用方 `ws_create_process_common` 随即 `TerminateProcess` 子进程并
  `fail-closed`（原有逻辑，`ws_proc.c:259` 附近）。
- **为什么不是 100 ms**：冷缓存/Defender 正在扫刚加载的 DLL 时，合法的 `LoadLibraryW` 可能到秒级；
  过短会制造假失败（正是 `tools/carrier-flake.mjs` 注释里记录过的 8%→27.5% 教训）。
  2000 ms 已把"父进程被冻 30 s"的形态消除，同时留给慢路径余量。`[未实测]`。

### 2.2 P1-4 三处自旋锁不可重入 + 持锁做文件 I/O（已修 ✅）

- 新增共享**可重入锁** `WsLock`（owner tid + depth）：
  `winstage_internal.h`（声明）、`ws_util.c:117`（`ws_lock_init`）、`ws_util.c:125`（`ws_lock_enter`）。
  - 同线程重入直接 `depth++`，**永不自我死锁**；
  - 等待路径分级退避（`YieldProcessor` → `SwitchToThread` → `Sleep(0)`），有上限，
    **超限打一条 `STUCK waiting on lock <name>` 而不是硬冻**。
- 三处旧自旋锁全部替换：
  - `ws_hook.c`：`g_hookLock`（`ws_hook.c:131`）；
  - `ws_proc.c`：`g_procLock`（`ws_proc.c:31`）；
  - `ws_t3reg.c`：`g_t3.lock`（`ws_t3reg.c:101`，WAL 事务锁——`LockFileEx` 只跨进程串行，进程内两线程
    仍会同时拿到，所以进程内锁必须保留，只是改为可重入）。
- **把日志移出临界区**：`ws_hook_install` 原先在锁内 `ws_log`（原报告 `:610`），现改为
  "锁内只做补丁，出锁后再写日志"（`ws_hook.c:594-617`）。`ws_patch_all()` 内部仍有少量异常诊断日志，
  但那一路**不会**再取本锁（`ws_log` 走捕获的原始 `CreateFileW`），故不会自锁。
- 编译 `[实测]`；运行期 `[未实测]`。

### 2.3 P1-5 缺"卡死自证"能力（已修 ✅）

- 新增**卡死自证**：每线程登记"当前所在钩子 + 起始 tick"，守护线程每 5 s 扫描，
  超过 10 s 就打 `STUCK <ms> in <name> tid=<tid> path=<...>`。
  - `ws_util.c:140` 槽表 / `ws_util.c:190` 守护线程 / `ws_util.c:218` 懒启动 /
    `ws_util.c:234` 入口登记；头文件提供 `ws_stuck_enter/path/leave` 与
    **作用域宏 `WS_STUCK("Name")`**（`__attribute__((cleanup))`，**每条 return 路径都自动清除**）。
  - **不在 DllMain 起线程**（避免持加载器锁创建线程死锁）；首个被追踪钩子触发懒启动。
  - 不变量：**best-effort、不阻塞热路径**；槽满则本线程不追踪。
- 已埋点的钩子：`CreateFileW`（`ws_file.c:410`）、`DeleteFileW`、`MoveFileExW`、`RemoveDirectoryW`、
  `RegCreateKeyExW`、`RegOpenKeyExW`（`ws_reg.c:658`）、`RegSetValueExW`、`RegQueryValueExW`、
  `RegDeleteKeyExW`、`RegDeleteValueW`，以及 `CreateProcess`（`ws_proc.c:216`）。
- 另在 §2.1 的注入等待（`inject:remote-LoadLibraryW`）与 §2.2 的锁等待处直接打 `STUCK`。
- AI 提示：这是把"挂住"从现象变成**指名调用**的手段；首次埋点覆盖了报告点名的热路径。
- 编译 `[实测]`；运行期 `[未实测]`。

## 4. P0-1 Defender 隔离工具链（需 owner 动作，非代码修复）

- 证据/影响见原清单：`winstage-inject.exe` 被 `Trojan:Win32/Bearfoos.A!ml` 隔离，导致 200/200 `ENOENT`，
  测试结论全假。
- **需要 owner 以管理员身份执行**（非本机、非本会话可代做）：
  ```powershell
  Add-MpPreference -ExclusionPath 'C:\Users\Administrator\Desktop\WinStageSandbox'
  ```
- **产品化正解是给二进制签名**；排除路径只是本仓开发期的止血。
- 排除后应立即跑 `node tools/carrier-flake.mjs 200` 做 A/B：这是唯一能把"Defender vs shim"定量拆开的实验。
- 在完成 P0-1 之前，**P1-6 的失败率数字都不可信**（P0-2 现在至少保证"注入器没了"会报环境不可用，
  而不是假失败）。

## 6. P3 —— 按决策保留的限制（不是缺陷，交付时须一并写明）

1. **读侧遮蔽是"只记录不拦截"**（`MASK_CLASSES` 29 类，T5）：owner 决策 ①，语义为"内部记录、模型面不出现"。
2. **限制即失败**（T7/T1）：无替代路径（owner 决策 ④）；`T1 restricted-token` 回退是**全拒**
   （实测连 `node.exe` 都拒），这是设计后果，需写明其"可见降级"形态。
3. **`%ALLUSERSPROFILE%` 不展开**：owner 决策 ⑦（真正造成伤害的"目录 CoW 误拒"已修 ✅）。
4. **本档不能自测**：写入进 overlay、逐命令一 session；缺注入器时 deny-all。
   因此**写盘类测试必须由 owner 在真实会话跑** —— 这是环境约束，不是产品失败。
