## 2. P1 —— 沙箱本体

### 2.1 P1-3 `CreateProcessW` 钩子里的 30 s 阻塞等待（已修 ✅）

- 位置：`shim/src/ws_proc.c`（原 `WaitForSingleObject(th, 30000)`）。
- 修法：改为 **有界等待**，默认 `WS_INJECT_WAIT_DEFAULT_MS = 2000`（`ws_proc.c:41`），
  可用环境变量 `WINSTAGE_INJECT_WAIT_MS`（50..60000）覆盖（`ws_proc.c:43`）。
  超时即记录 `STUCK remote LoadLibraryW did not complete within ... ms; failing closed`
  （`ws_proc.c:189`），返回失败；调用方 `ws_create_process_common` 随即 `TerminateProcess` 子进程并
  `fail-closed`（原有逻辑，`ws_proc.c:259` 附近）。
- **为什么不是 100 ms**：冷缓存/Defender 正在扫刚加载的 DLL 时，合法的 `LoadLibraryW` 可能到秒级；
  过短会制造假失败（正是 `tools/carrier-flake.mjs` 注释里记录过的 8%→27.5% 教训）。
  2000 ms 已把"父进程被冻 30 s"的形态消除，同时留给慢路径余量。`[未实测]`。

### 2.2 P1-4 三处自旋锁不可重入 + 持锁做文件 I/O（已修 ✅）

- 新增共享**可重入锁** `WsLock`（owner tid + depth）：
  `winstage_internal.h`（声明）、`ws_util.c:117`（`ws_lock_init`）、`ws_util.c:125`（`ws_lock_enter`）。
  - 同线程重入直接 `depth++`，**永不自我死锁**；
  - 等待路径分级退避（`YieldProcessor` → `SwitchToThread` → `Sleep(0)`），有上限，
    **超限打一条 `STUCK waiting on lock <name>` 而不是硬冻**。
- 三处旧自旋锁全部替换：
  - `ws_hook.c`：`g_hookLock`（`ws_hook.c:131`）；
  - `ws_proc.c`：`g_procLock`（`ws_proc.c:31`）；
  - `ws_t3reg.c`：`g_t3.lock`（`ws_t3reg.c:101`，WAL 事务锁——`LockFileEx` 只跨进程串行，进程内两线程
    仍会同时拿到，所以进程内锁必须保留，只是改为可重入）。
- **把日志移出临界区**：`ws_hook_install` 原先在锁内 `ws_log`（原报告 `:610`），现改为
  "锁内只做补丁，出锁后再写日志"（`ws_hook.c:594-617`）。`ws_patch_all()` 内部仍有少量异常诊断日志，
  但那一路**不会**再取本锁（`ws_log` 走捕获的原始 `CreateFileW`），故不会自锁。
- 编译 `[实测]`；运行期 `[未实测]`。

### 2.3 P1-5 缺"卡死自证"能力（已修 ✅；含一次回归与收口）

- 新增**卡死自证**：每线程登记"当前所在钩子 + 起始 tick"，**任意一次钩子进入**时顺带扫描，
  超过 10 s 就对超阈值槽位打一次 `STUCK <ms> in <name> tid=<tid> path=<...>`。
  - `ws_util.c` 槽表 + 按 `GetCurrentThreadId` 查找 + `reported` 闩锁去重；
    头文件提供 `ws_stuck_enter/path/leave` 与 **作用域宏 `WS_STUCK("Name")`**
    （`__attribute__((cleanup))`，**每条 return 路径都自动清除**）。
  - 已埋点的钩子：`CreateFileW`、`DeleteFileW`、`MoveFileExW`、`RemoveDirectoryW`、
    `RegCreateKeyExW`、`RegOpenKeyExW`、`RegSetValueExW`、`RegQueryValueExW`、
    `RegDeleteKeyExW`、`RegDeleteValueW`，以及 `CreateProcess`。
  - 另在 §2.1 的注入等待（`inject:remote-LoadLibraryW`）与 §2.2 的锁等待处直接打 `STUCK`。
- **★ 回归与收口（Windows VM 实测）**：第一版实现用 `TlsAlloc()` + 守护线程。
  实测发现：**只要 `TlsAlloc()` 在被注入进程启动早期执行**，一个普通的注入态
  `node -e` 就会以 `OpenSSL configuration error ... BIO_new_file:No error:c:\ws\deps\openssl\...`
  退出（`0/10` 稳定复现）；把线程去掉、只留 `TlsAlloc` 仍失败 ⇒ 元凶是 **TLS 路径**，
  与线程无关；完全禁用该子系统则 `10/10` 通过。
  ⇒ 最终**去掉 TLS 与守护线程**，改为上述**协作式**上报。
  代价：整进程单线程且完全冻死时无人上报（锁等待/注入等待仍原地直接打 `STUCK`）。
- 现场证据：旧 shim `node-eval 100/100`；回归版 `0/10`；收口版 `15/15`（见 §8.5）。
- 编译 `[实测]`；`STUCK` 行本身尚未被强制触发验证（`[未实测]`，诊断能力已就位）。

## 6. P3 —— 按决策保留的限制（不是缺陷，交付时须一并写明）

1. **读侧遮蔽是"只记录不拦截"**（`MASK_CLASSES` 29 类，T5）：owner 决策 ①，语义为"内部记录、模型面不出现"。
2. **限制即失败**（T7/T1）：无替代路径（owner 决策 ④）；`T1 restricted-token` 回退是**全拒**
   （实测连 `node.exe` 都拒），这是设计后果，需写明其"可见降级"形态。
3. **`%ALLUSERSPROFILE%` 不展开**：owner 决策 ⑦（真正造成伤害的"目录 CoW 误拒"已修 ✅）。
4. **本档不能自测**：写入进 overlay、逐命令一 session；缺注入器时 deny-all。
   因此**写盘类测试必须由 owner 在真实会话跑** —— 这是环境约束，不是产品失败。

## 7. 本轮未做 / 遗留

- **P0-1** 需 owner 在**宿主**以管理员执行（排除或更好是签名）。VM 里 Defender 未隔离产物、
  排除前后无差异（§8.5），所以该问题无法在 VM 复现，只能在宿主落地。

- 卡死登记为**每线程单槽**（嵌套钩子覆盖同一槽）；这是 best-effort 设计，已在代码注释注明。

## 8. Windows VM 实测（ebk，win10）—— 本轮补做

`/shared` 挂仓库、`/oem` 挂一个安装后自动运行的 `install.bat`（装 Node 22.11、映射
`\\host.lan\Data`、构建、跑套件）。整个过程**在真实 Windows 上**，与 Linux 交叉编译互补。

⇒ 本轮 P1-3/4/5 的 C 改动在**目标平台**上编译/链接零告警，导出表完整。

### 8.2 离线全量（`[实测]`）
`node autotest.mjs --skip-audit` → **23 套件通过 / 8 失败，断言 1975 ok / 12 bad**。
通过的关键套件：`selftest 51/51`、`e2e-flow 21/21`、`appcontainer-runtime 178/178`、
`limits 192/192`、`integration-wiring 144/144`、`paths-masks 57/57`、`residual-baseline 43/43`、
`baseline-integrity 14/14`、`netpolicy/mitigations/wfp-layout` 全绿。
8 个失败经查**不是本轮改动引起**，原因三类：
- `registry-guard` 的 `A.5 报告必须比 DLL 新 ⇒ STALE_EVIDENCE`：把宿主里**已存在的旧构建报告**
  一并拷进 VM，与新建 DLL 时间戳不一致；
- `executor-stub` / `workspace-regressions` 的单条断言：从非标准路径（`C:\ebk\...`）运行；
- `diag-bindings` / `file-cow-dispositions` / `delete-capture` / `probe-selfkill-guard` /
  `whiteout-candidate-capture`：沙箱套件，需要**未受限会话**（OEM 脚本经 Run 起的 cmd 仍是受限
  令牌），README 已把这类列为机制边界。

### 8.3 载体 A/B（`[实测]`，P1-6 定量）
`node tools\carrier-flake.mjs 50`（注入）vs `--direct 50`（不注入）：

| 组 | 失败 | 说明 |
|---|---|---|
| 注入 | **1/50（2%）** | PowerShell 载体，全部快速返回，**无 30 s 挂住** |
| 直接 | **0/50** | 对照组 |

⇒ P1-3 的有界等待生效（50 次无一"无退出码/超时"）。同一台 VM **干净重建后复跑
100 次**为 **0/100**（注入与直接均 0），说明上一行那 1 次属首轮/环境抖动。

### 8.4 VM 实测当场发现并修掉的工具缺陷（`[实测]`）
1. `tools/carrier-flake.mjs` **硬编码** `REPO='C:\Users\Administrator\Desktop\WinStageSandbox'`，
   从 `C:\ebk\WinStageSandbox` 运行时前置校验报 `ENVIRONMENT UNAVAILABLE`（退回 2，行为正确，
   但工具本身不该绑死路径）⇒ 改为从 `import.meta.url` 推导 REPO。
2. 同一工具把**纯数字参数**（迭代次数）误当成 DLL 路径 ⇒ 50 次全在注入器 precheck 报
   `dll file does not exist`。⇒ 加 `/^\d+$/` 排除。

### 8.5 `node-eval` 载体缺陷的根因（`[实测]`，P1-6 收口）
首轮 VM 里 `smoke-inject` 的 `node-eval` 稳定 `0/5` 失败：
`OpenSSL configuration error ... BIO_new_file:No error:c:\ws\deps\openssl\...`。
用**旧 shim vs 新 shim** 做 A/B（同一台干净 VM）：

| shim | 注入态 `node -e` |
|---|---|
| 旧（本轮改动前） | **100/100 通过** |
| 新（P1-5 用 TlsAlloc+守护线程） | **0/10 失败** |
| 新，但只去掉守护线程、保留 `TlsAlloc()` | **0/10 失败** |
| 新，去掉 TLS 与守护线程（协作式，最终实现） | **15/15 通过** |

⇒ 根因是 **P1-5 第一版的 `TlsAlloc()`/TLS 路径**在被注入进程启动早期执行，
不是"注入态读/物化缺陷"，也不是线程本身。已在 §2.3 收口为无 TLS/无线程的协作式上报。

**P0-1（Defender）A/B**：该 VM `RealTimeProtectionEnabled=True`；加/不加
`Add-MpPreference -ExclusionPath C:\ebk` 前后，`smoke-inject` 均 **5/5 通过**——
即在本 VM 里 Defender **没有**隔离构建产物，排除项不构成差异。原报告里"工具链被隔离"
是**宿主特有**的（二进制未签名），须在宿主用管理员排除/签名处理，本 VM 无法代做。

> VM 现场脚本与日志留在宿主的 `ebk-*.log`（`*.log` 已在 `.gitignore`），未入库。
