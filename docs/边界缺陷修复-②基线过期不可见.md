## 1. 现象（复述 + 本轮实测复核）

| 步骤 | 期望 | 旧实现实际 |
|---|---|---|
| 1. `write` 暂存新文件 `f5b-stale.txt = STAGED-VERSION`（基线 = absent） | 面板出现"新增"候选 | 一致（`counts.staleBaseline=0` 是对的：此刻基线确实等于现实） |
| 2. `pwsh Set-Content` 把真实盘写成 `SHELL-VERSION`（绕过 `ctx.fs`） | 应出现 stale 提示 / 告警 / 至少批准时不静默覆盖 | **90 s 内 `review.json` 一次都没重发布**，`staleBaseline=0`、`alerts=[]`、UI 无徽标 |
| 3. 点「批准所选」 | 拒绝并提示 rebase | **静默覆盖**：真实盘由 `SHELL-VERSION` 变 `STAGED-VERSION`，无提示、无告警、无错误 |
| 4. 账本 | 应留下"外部内容被替换"的痕迹 | `manifest.baseHash = stagedHash`、`changed=false` ⇒ 磁盘上那份内容**没有任何痕迹** |

`[实测]` 本轮在原现场复核了第 4 条的账面状态（`.t/fix2-live-before.txt`）：
`origin=dsh-tool`、`baseHash == stagedHash == 231ff8ac…`、`changed=false`；
那份 `SHELL-VERSION` 在账本里不存在（第 3 步已经把它覆盖掉了）。

### 1.1 离线复现（修复前）

`.t/fix2-repro-f5b.mjs`（`ReviewService` + 真实文件系统，复刻 1→2→3）：

```
步骤1：counts.staleBaseline = 0、alerts = []（对：基线 == 现实）
步骤2：真实盘 = "SHELL-VERSION"（工具返回逐字如此）
步骤3：publish() 后 counts = {net:1, staleBaseline:0}、alerts = []   ← 不可见
       approve() => {"ok":true,"approved":1,"failed":[],"message":"已应用 1 项"}  ← 静默落盘

       该行 baselineStale 缺失、无逐条原因
结果：7 FAIL / 10（`[实测]` .t/fix2-repro-before.txt）
```

## 2. 根因（源码级，`file:line`）

### 2.1 可见性：漂移在**快照之前**就被抹掉了

- `dsh-plugin/review-service.mjs` 的 `reload()`（修复前 `:378-394`）在**每次**重读清单时调用
  `autoRebaseDrifted()`；
- 同一个方法的 `publish()`（修复前 `:908-916`）调用 `autoAlignQuietly()`；
- `afterMutation()`（修复前 `:531-535`）、`approve()`（修复前 `:924-932`）同样调用它。

于是 `snapshot()` → `reload()` 这条**取数路径本身**就会先把基线"重述"为现实：
`src/workspace.mjs` 的 `rebaseEntry()`（`:397-410`）把 `entry.baseHash/baseKind` 换成磁盘当前值。
重述之后 `renderChange()` 里的判据

```js
// dsh-plugin/review-service.mjs（修复前 :832-839）
const expected = change.before?.hash ?? hashAbsent()
const found = this.realHashOf(ws, change)
if (found !== expected) { item.baselineStale = true; … }
```

**永远为假** ⇒ `counts.staleBaseline = 0`、无徽标、`alerts = []`。
F5b 实测的"90 s 一次都没重发布"是同一个原因的另一面：`pwsh` 绕过 `ctx.fs`，
不触发任何 `afterMutation()`/命令，而发布路径一旦被触发又只会把漂移抹平。

### 2.2 静默覆盖：`approve()` 的自动对齐把外部写入变成"可批准"

`STALE_BASELINE` 闸门在 `src/workspace.mjs:1354-1360`（修复前行号 `:1224-1230`）：
`realNow !== expected` 才拒绝。而 `approve()` 里的 `autoAlignQuietly()` 会把
`expected` 改成 `realNow`，于是闸门**必然放行**，`applyOneChange()` 用
`writeFileAtomic()` 覆盖真实盘。旧注释写的"对齐只重述 before，所以不存在静默覆盖"
后半句是错的：**重述 before 正是让闸门失效的那个动作**。

### 2.3 触发点缺口：发布只在"变更/命令"时发生

`review.json` 的写点只有 `afterMutation()` / 命令面 / `publishWorkspaceSnapshot()`。
`pwsh` 直接写真实盘不产生这些事件 ⇒ 面板没有第二个观察窗口。

## 3. 修复（延伸既有 staleness 机制，不新造流程）

### 3.1 形状可命名（`src/workspace.mjs`、`dsh-plugin/review-service.mjs`）

- `src/workspace.mjs`：新增并导出 `driftReasonOf(expected, found)`（`:332-346` 区），
  返回 `baseline-appeared` / `baseline-deleted` / `baseline-drifted` / `null`；
  `baselineDrift()` 增加 `reason`（同一判据，同一字面量）。
- `src/workspace.mjs`：`applyOneChange()` 的 `STALE_BASELINE` 抛错里带
  `driftReason: driftReasonOf(expected, realNow)`；`applyCandidate()` 的
  `failed[]` 只加不改地透出 `driftReason`。
- `dsh-plugin/review-service.mjs`：`driftReasonOf` 从 `src/workspace.mjs`
  **re-export**（不写第二份），新增 `driftReasonText()`；
  `renderChange()` 给可批准行加 `baselineStaleCode`；
  顶层 `counts` 新增 `staleBaselineLossy`（漂移里"会盖掉磁盘上已存在内容"的条数）。

### 3.2 可见（快照 + 面板 + 人工侧诊断通道）

- 快照（`review.json`）：`files[].baselineStale` + `baseline{expected,found}` +
  **`baselineStaleCode`**；`counts.staleBaseline` / `counts.staleBaselineLossy`。
- 面板（`dsh-plugin/client.js`）：逐行徽标（`data-winstage-baseline-stale`，已有）
  + **新增逐行说明**（`data-winstage-baseline-stale-note`，如"真实文件在暂存之后出现
  （基线本为"不存在"）"）；顶部汇总与徽标 tooltip 文案改为"批准会被拒绝、不会静默覆盖"。
- 面板出路（`dsh-plugin/client.js`）：新增「**重新对齐并批准所选**」按钮
  （`data-winstage-rebase-selected`）。**为什么必须有它**：旧设计删掉了手动对齐按钮、
  理由是"每次修改都自动对齐"——而"自动对齐"正是缺陷②要拿掉的那条丢数据路径；
  没有这个按钮，用户就被卡在"点批准失败 → 提示你 rebase → 面板上没有按钮"里。
  它只在**已勾选的行里有 `baselineStale`** 时出现，走的仍是 `authorizedPaths()` 那份
  可写集合（不比「批准所选」多覆盖任何一个文件），命令是既有的 `/winstage approve --rebase`。
- 命令面（`dsh-plugin/host-plugin.mjs`）：`formatList()` 逐行带形状；有损漂移额外一行警告；
  `approve` 失败分支打印形状 + "真实磁盘上的那份内容**没有被覆盖**" + rebase/reject 出路。
- **诊断通道**：`ReviewService.emitDriftDiagnostics(stale)` 走既有的 `logError()`
  （`review-service.mjs:324-338`：`logger.warn` → `logger.error` → `console.error`），
  按 `路径+形状+两侧 hash` 去重，**绝不进模型可见的 stdout/stderr / 命令文本**
  （沿用 `shell-executor.mjs:1319-1335` 的分离纪律）。

### 3.3 安全（批准绝不静默）

- `review-service.mjs`：`autoRebaseDrifted()` **只对无损漂移自动对准**
  （真实内容 == 暂存内容 ⇒ 对准后无净变化、一个字节都不会被改）；
  有内容丢失风险的漂移进入返回值的 `blocked[]`，**不对准**（闸门代码：
  `if (drift.found !== hashAbsent() && drift.found !== staged) { blocked.push(…); continue }`）。
- `reload()` / `publish()` / `afterMutation()` / `approve()` **删掉**自动对准调用。
  副作用：漂移留在清单里 ⇒ 快照标 `baselineStale` ⇒ `applyOneChange()` 以
  `STALE_BASELINE` 拒绝。出路仍是既有的两条：`/winstage rebase`（`_rebase()` 不受此限）
  或 `/winstage reject`；面板上的「重新对齐并批准所选」= `approve --rebase`，
  一字未改。
- `_rebase()` 增加 `reasons` 返回（重述**之前**读形状），rebase 文案在
  `baseline-appeared` 时补充"现在面板显示的 before 就是磁盘上的真实内容"。

### 3.4 触发点（不忙等）

新增 `dsh-plugin/baseline-watch.mjs`（`host-plugin.mjs` 的 `apply()` 内、
`isEnabled()` 为真时装配；关闭态不装）：

- 节拍默认 **1500 ms**，与 Client 读 `review.json` 的轮询同一档
  （逃生口 `WINSTAGE_WATCH_MS`；非正数 = 关闭）；
- 每拍调用每个活会话的 `ReviewService.reviewDrift()`：**纯读**——不 rebase、不 discard、
  不冻结候选；先用"清单 mtime + 每条净 diff 两侧 hash + 漂移形状"组成指纹，
  **指纹没变立刻返回且不写盘**；变了才 `publish()` 一版快照；
- 用 `ctx.effect()` 装配（cordis 卸载协议），无 `ctx.effect` 时退化为
  `setInterval` + `unref()`。

## 6. 为什么改了 `.t/auto-rebase-selftest.mjs`（**行为确实有意变了**）

该套件原先把"**每次发布都自动对准基线**"当作契约，其中两条正断言与缺陷②的修复要求
**直接冲突**：

```
原 line 103-109：漂移后 service.approve([key]) 必须成功，并把暂存内容写进真实文件
原 line 97-98 ：publish() 里必须调用 autoAlignQuietly()
```

"漂移后一次点击就落盘"**就是** F5b 的静默覆盖路径。任务书要求"基线漂移的候选
**必须不能**被静默应用：批准路径必须拒绝它"。两者不可同时成立，因此本文件按新语义重写
（不是为了让红灯变绿）：

- 保留并**加强**了原有的 no-clobber 保证（真实文件在任何读/发布/批准尝试后都不被改回）；
- 新增：有损漂移**不进** `rebased`、进 `blocked[]`；`reload()`/`publish()` 连续调用不再抹掉漂移；
  `approve()` 第一次就被拒且带形状；`reviewDrift()` 只读且指纹短路；
- 无损档（真实内容 == 暂存内容）仍允许自动对准（变异自证：`WINSTAGE_AUTO_REBASE=0` 时连它也不做）；
- 源级断言**反转**：四个方法体里不许再出现自动对准调用（判据先去注释再匹配，
  并有"方法体长度在 40..3000"的自证，防止判据退化成空壳）。
