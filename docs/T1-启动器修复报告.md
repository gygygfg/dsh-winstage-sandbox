**一句话**：三类故障的根因是**平台 `WRITE_RESTRICTED` 受限令牌的 restricting 列表过窄**（只有 logon SID + EVERYONE，两种模式都丢 Authenticated Users/INTERACTIVE/LOCAL），

## 1. 采集环境（决定"哪些结论可以被读成实测"）

**T1（我）的委派会话在整个任务期间一直是受限的** —— 尽管 Lead 的会话已切到 `danger-full-access`。采集时刻的原始证据：

```
$ whoami /priv              → 只解析出 1 条 SeChangeNotifyPrivilege（未受限会话是 25 条）
$ Set-Content C:\Windows\Temp\...   → UnauthorizedAccessException: Access is denied
$ WindowsStageExecutor.init()       → INIT_FAILED: OpenProcessToken failed (Win32 5)
```

`OpenProcessToken(handle, 139)` 的 139 = `TOKEN_ASSIGN_PRIMARY|TOKEN_DUPLICATE|TOKEN_QUERY|TOKEN_ADJUST_DEFAULT`，其中 `TOKEN_ADJUST_DEFAULT` 是**写类**访问 ⇒ 被 restricting 检查拒掉，**这正是 `WRITE_RESTRICTED` 的签名**（README §4 已记录同一现象）。因此：

1. 三类能力的"**改前**"输出是在**本会话自身（= 平台受限令牌）**上实测的 —— 与平台 runner 铸出的令牌同源（restricting 列表同构），因此结论可迁移，但**不能**说成"在 winstage 自己的 T1 沙箱里测的"。
2. 本会话**无法建立 winstage 沙箱**（嵌套隔离不可用，R6），`capability-probe` 如实报 `mode.effective='inherited-confinement'`、`sandboxEstablished=false`、`confinementSource='host-inherited'`（`out/probe-ts.json`）。
3. **去令牌化模式要求启动方自身未受限**：受限父进程派生的子进程继承受限令牌，shim 金丝雀里的四类能力仍会失败 ⇒ 探测不通过（这正是它应有的 fail-closed 行为）。**最终验收因此必须在未受限宿主进程里跑**（Lead 已采纳为验收口径）。

## 2. 改前：三类能力 + 痕迹（原始输出）

### 2.1 管道：`& node --version | Out-String`

`out/ambient-pipe.txt`（宿主：平台受限令牌，PowerShell 5.1）：

```
--- native pipeline (| Out-String) ---
--- native redirect (>) ---
REDIR=[]
REDIR_FILE_EXISTS=True
--- cmd pipeline ---
--- plain native invoke (control) ---
v24.21.0
PLAIN_NODE_EXIT=0
CMD-PLAIN-OK
PLAIN_CMD_EXIT=0
[stderr]
Program 'node.exe' failed to run: Access is denied
Program 'cmd.exe'  failed to run: Access is denied
```

判据：**管道形式**（`| Out-String`）报 `Access is denied`；**普通调用**（不接管道）正常输出 `v24.21.0`。
即故障点是"子进程的输出管道"，不是命令本身。

### 2.2 重定向：`& node --version > file`

同一份输出：`REDIR=[]`、`REDIR_FILE_EXISTS=True` —— **文件被创建了，但内容是空的**。
这比报错更危险：**退出码 0 + 无输出**（静默丢数据）会被上层读成"命令成功且无输出"（README §1.1 / 残余边界 R10 记录的形态）。

### 2.3 TLS：`SslStream.AuthenticateAsClient`

`out/ambient-tls-write.txt`：

```
TLS=FAIL:MethodInvocationException: No credentials are available in the security package
--- write outside workspace ---
OUTSIDE_WRITE=FAIL:UnauthorizedAccessException: ... 'C:\Windows\Temp\winstage-ambient-outside.txt' is denied.
OUTSIDE_REAL_EXISTS=False
--- write inside workspace ---
INSIDE_WRITE=OK
```

`No credentials are available in the security package` = SChannel `SEC_E_NO_CREDENTIALS`：失败发生在**取凭据**这一步（还没到网络）。
同文件里还证明：工作区外写入被拒、工作区内写入 OK —— **写边界本身是生效的**，被破坏的只是"取用户加密存储"这条写类路径。

### 2.4 五项系统查询

`out/ambient-system.txt`：

```
PRIVILEGE_LINES=0
whoami /user     → exit=1   stderr: ERROR: Access is denied.
whoami /groups   → exit=1   stderr: ERROR: Access is denied. / Unable to get group membership information.
tasklist         → exit=1   stderr: ERROR: Access denied
Get-CimInstance Win32_OperatingSystem → 拒绝访问
Get-NetFirewallProfile                → 拒绝访问
Get-NetTCPConnection                  → 拒绝访问
对照：whoami /priv → 正常（唯一特权 SeChangeNotifyPrivilege）
```

### 2.5 根因，以及**为什么不能靠补 SID 修**

平台实现与自我说明（`@deepseek-ai/dsh-sandbox-windows-acl/lib/runner.js:22-30`，Lead 已核对原文）：

> restricting list = **只有 logon SID + EVERYONE**；workspace-write 再加 workspace/temp 两个 capability SID；
> 「BOTH modes drop **Authenticated Users** (CIM unavailable) and **INTERACTIVE/LOCAL**」。

`WRITE_RESTRICTED` 的语义是**写类访问要过两遍检查**：正常 SID 一遍、restricting 列表一遍。于是：

- 管道 DACL / 用户加密存储（`%APPDATA%\Microsoft\Crypto` 等）只授予**用户 SID** ⇒ 第二遍不过 ⇒ `Access is denied` / `SEC_E_NO_CREDENTIALS`；
- CIM / 防火墙 / TCP 连接需要 **Authenticated Users** 或 **INTERACTIVE/LOCAL** ⇒ 被平台刻意移除 ⇒ 全灭。

**把用户 SID 或 Authenticated Users 加进 restricting 列表确实能"一次修好三项"**，但那等于取消第二遍检查：
`C:\Program Files`、`HKCU`、`%APPDATA%` 等一切授予该用户写权限的对象立刻重新可写 —— **写边界当场崩塌**。
因此本任务明确不走这条路；`src/executor.mjs` 里也没有任何"加 SID"的改动，§2.5 的论证与 `docs/T1-启动器修复报告.md`（本文件）一起作为"为什么不做"的书面依据。

### 2.6 痕迹：`DSH_SANDBOX*`

改前（`buildChildEnvironment` 末尾）：

```js
env.DSH_SANDBOX = 'win-stage'
env.DSH_SANDBOX_TIER = options.tier || 'unknown'
env.DSH_SANDBOX_ENFORCEMENT = 'partial'
env.DSH_SANDBOX_NOTE = 'writes confined to the staged root; reads are NOT confined ...'
```

**已删除**，并由离线断言双向锁定（`tests/executor-stub.mjs` §6b）：
- 变量名集合里没有任何 `/^DSH_SANDBOX/i`；
- `JSON.stringify(env)` 里不含字符串 `DSH_SANDBOX`；
- 允许清单机制未被破坏（`TEMP` 仍按 `tempDir` 重写、显式非敏感变量仍生效）。

## 3. 改后：去令牌化运行模式

### 3.1 设计（`src/executor.mjs`）

档位 `tier: 'TS'`（或 `'auto'`）→ 先跑**三级真实可用性探测**，只有三级全过才用去令牌化模式；任一环失败 **fail-closed 回退受限令牌模式**。

| 门 | 检查 | 为什么必须这样 |
|---|---|---|
| 门 1 产物 | `winstage-shim.dll` 存在 + **x64 PE + 必需导出符号**（自行解析 PE 导出表）；`winstage-inject.exe` / `winstage-probe.exe` 存在 | "文件存在"不是可用性；**不在宿主里 LoadLibrary**（那会把宿主自己的 IAT 也 hook 掉 —— 探测动作不得改变运行期状态） |
| 门 2a 加载 | 一次性短命进程里跑 `winstage-probe.exe selftest <dll> <out.json>`，要求 `loaded=true`、`abiVersion=1`、`stats.initialized=true` | 真实加载 + 真实初始化，而不是看导出表 |
| 门 2b 激活 | `winstage-inject.exe` 对金丝雀退出 0（`report.ok != false`；T4 约定 111 = 注入失败） | 真实注入；失败必须能被识别成"基础设施故障"而不是"命令被拒" |
| 门 3 能力 | **经注入器启动的金丝雀子进程**里四类能力真的恢复：管道 / 重定向 / whoami(user,groups) / tasklist / CIM / 防火墙 / TCP 连接 / TLS 取凭据 / 且无 `DSH_SANDBOX*` | 只承认"用户真正得到了什么"，不承认"参数看起来对" |

配套不变量（都有离线断言）：

- `selectLaunchMode(requested, probe)` 是**纯函数**；`TS/auto` 探测通过 → `shim`，否则 → `restricted-token`（附 `fallbackReason`）；任何档位都**不会**产生"无强制的裸跑"；
- `TS` 模式**不建 AclSandbox**（没有 `CreateRestrictedToken`、没有 Low IL）、**不建 Job**；`initReport` 如实写 `jobEnabled=false`、`treeReclaim='taskkill /T /F (transparent mode has no Job Object)'`；
- `run()` 在 shim 模式下走注入器 + **文件描述符重定向**采集（不依赖命名管道），`launchMode='shim'`、`enforcement='shim-user-mode'`、`backend='winstage-shim-iat'`；
- 注入器拒绝（退出码 111）⇒ 结构化 `runner-failure`（`exitCode=127`、`launchFailed=true`），**不回退到受限令牌继续跑**、更不裸跑；
- 去令牌化的实例自检判据与受限令牌**不同**：工作区外写入「报成功」是**预期**，判据是「报成功 + 宿主侧真实磁盘没有它 + 暂存树里能找到它」；
- shim 的环境契约变量**不设** `WINSTAGE_SHIM_DISABLE`（设了 shim 就完全不生效 = 裸跑）。

### 3.2 与 T4 的接口（已对齐，来自 `t4-shim` 的书面答复 + `shim/include/winstage_shim.h`）

| 项 | 契约 |
|---|---|
| DLL | `shim/out/winstage-shim.dll`（x64；可用 `WINSTAGE_SHIM_DLL` 覆盖）。实测 192512 B / 7 个导出 |
| 导出 | `WinstageShimInit(const wchar_t*)`、`WinstageShimShutdown`、`WinstageShimAbiVersion`、`WinstageShimBindStageApi`、`WinstageShimOriginal`、`WinstageShimRefreshHooks`、`WinstageShimStatsJson`；ABI=1 |
| 注入方式 | **远程 `LoadLibraryW`**：`CreateProcessW(CREATE_SUSPENDED｜CREATE_UNICODE_ENVIRONMENT)` → `VirtualAllocEx`+`WriteProcessMemory`(DLL 全路径) → `CreateRemoteThread(kernel32!LoadLibraryW)` → 等远程线程结束 → `ResumeThread`。DllMain 会按环境变量自动初始化 |
| 注入器 CLI | `shim/out/winstage-inject.exe --dll <dll> [--set-env K=V]… [--report <json>] -- <exe> [args…]`；**退出码 111 = 注入失败**，否则转发子进程退出码；子进程 stdout/stderr 由调用方重定向 |
| 自检 | `shim/out/winstage-probe.exe selftest <dll> <out.json>`（在一次性进程里加载并调 `AbiVersion`/`StatsJson`；**不要**在宿主进程里 LoadLibrary） |
| 环境变量 | `WINSTAGE_STAGE_ROOT`（必需）、`WINSTAGE_SHIM_CONFIG`（可选，默认 `<stageRoot>\winstage-shim.config.json`）、`WINSTAGE_SHIM_LOG`、`WINSTAGE_SHIM_DISABLE`（非 "0" 即完全不生效，**调用方不得设置**） |
| config JSON | 扁平 JSON：`{stageRoot, logPath, failClosed, readThrough, verbose, traceStagedOps, passthrough[]}`；`passthrough` 必须含暂存根自身（否则暂存动作会被自己再暂存一次） |
| 观测 | 日志 `WINSTAGE_SHIM_LOG`（默认 `<stageRoot>\shim.log`，逐行 `[winstage-shim][pid][seq]`） |
| 我方注入点 | `ShimLauncher`（本模块）负责组参数、传环境、fd 重定向采集；`AppContainerLauncher.launch/_runChild` 另开 `beforeResume({pid,process,thread})` 钩子（T2 契约），供 T0 路径将来挂注入 |
| 边界声明 | shim 是**用户态 IAT 补丁**级重定向，不是内核级强制；未覆盖 `ntdll!Nt*`、`\\?\GLOBALROOT`、`CopyFile2`、`SHFileOperation`、内存映射、其它进程代写等 |

## 4. ★ 阻塞项（T4 侧）：shim 钩子破坏 `node.exe` / `powershell.exe`

**归因实验**（`out/inject-disable-test.txt`，同一注入器、同一 DLL，只切 `WINSTAGE_SHIM_DISABLE`）：

| shim 状态 | 目标 | injector/child 退出码 | 结果 |
|---|---|---|---|
| **ACTIVE** | `cmd.exe` | 0 / 0 | `INJECT-CMD-OK`（正常） |
| **ACTIVE** | `node.exe` | 2147483651 / 2147483651 | `WSAStartup: (10107) 系统调用失败` |
| **ACTIVE** | `powershell.exe` | 4294901760 / 4294901760 | `The type initializer for 'System.Management.Automation.Runspaces.InitialSessionState' threw an exception` |
| **DISABLED(=1)** | `node.exe` | 1 / 1 | node **起来了**（只是我传的 `-e` 参数被注入器引号破坏，见下） |
| **DISABLED(=1)** | `powershell.exe` | 0 / 0 | `PS-OK`（完全正常） |
| DISABLED / ACTIVE | `whoami.exe` | 1 / 1 | `ERROR: Access is denied.`（**本会话受限令牌所致，与 shim 无关**，两种状态一致） |

结论：**注入机制本身没问题**（`report.ok=true`、`remoteModule=0x53160000`），
问题在**钩子生效后这两个运行时的初始化被破坏**；而 `node` 与 `powershell` 正是 DSH 工具层要跑的东西 ⇒
门 3 的金丝雀（PowerShell + 内部再跑 `node --version`）永远拿不到哨兵 ⇒
**去令牌化主路径在当前 DLL 下无法端到端激活**。我方 gate 的行为是对的（fail-closed 回退），但**这不是一个可接受的终态**。

顺带发现的两个 T4 侧问题（都有原始输出）：

1. **注入目标必须是绝对路径**（`out/inject-target-test.txt`）：
   `powershell.exe`（裸名字）→ injector exit **111**、`{"stage":"CreateProcessW","error":"cannot create the target process","win32Error":2}`；
   换成绝对路径 → 注入成功（`ok:true, remoteChild module 0x53160000`）。
   原因：注入器把目标传给 `lpApplicationName`，不做 PATH/PATHEXT 解析 —— 与本项目"缺陷 6"同类。
   我方已修：`probeTransparentShim()` 里用 `resolveExecutable('powershell', …)` 传绝对路径；`ShimLauncher` 走的 `run()` 本来就传 `resolvedCommand`（绝对路径）。
2. **argv 引号**：`-- node.exe -e "process.stdout.write('X')"` 在子进程侧被解析成 `Cannot find module 'C:\...\WinStag…'`（`out/inject-disable-test.txt` 的 SHIM-DISABLED/node 行），需要 T4 核对命令行拼接。

已把上述三条（钩子破坏 node/PS、绝对路径、引号）发给 `t4-shim`。

## 5. 本轮自曝修出的真实缺陷（都是"看起来成功"那一类）

### 5.1 PE `SizeOfOptionalHeader` 偏移错 4 字节（**合成夹具与实现同错 ⇒ 测试假绿**）

- 症状：`parsePeExports()` 解析**真实** DLL 时报 `export name table out of range`，`probeShimDll()` 判不可用 ⇒ 门 1 假失败。
- 根因：COFF 头从 **PE 签名之后**开始，`SizeOfOptionalHeader` 在 `coff+16 = peOffset+20`；我写成了 `peOffset+16`（漏算签名 4 字节），于是把该字段读成 0 ⇒ 节表起点落到可选头上 ⇒ 节表/导出表全成垃圾。
- **为什么测试没抓住**：`tests/executor-stub.mjs` 里合成 PE 的夹具**也**把该字段写在 `peOffset+16`，两边一起错 ⇒ 6 条断言全绿。这是 README 缺陷 15（"替身失真比没有替身更危险"）的又一实例，**直到 T4 交出真实 DLL（7 节、`SizeOfOptionalHeader=0xF0`）才暴露**。
- 修复：实现按真实偏移读取；夹具改为按真实布局写；**新增一条有判定力的回归断言**——把该字段只写在错位置时解析必须失败（修前该断言为红）。
- 证据：`shim/out/winstage-shim.dll` 头 32 字节（`0x78: 50 45 00 00 64 86 07 00 … f0 00`）+ `out/ts-probe-real.txt` 的 `shim-dll: OK x64 PE, 192512 bytes, 7 exports`。

### 5.2 T4 probe 的 `statsRaw` 是**字符串**，不是嵌套对象

- 症状：门 2a 把"已初始化"误判成"不可用"（`selftest.stats` 永远 `undefined`）⇒ TS 永久假回退。
- 修复：`parseJsonMaybe(selftest.statsRaw)`（两种形态都支持），并把 `initReturn / hooksInstalled / iatSites / modules` 打进 check detail。
- 证据：`out/selftest-matrix.txt` 五行变体（`stage-root-only`/`+log`/`+config`/`full-host-env` 全部 `initialized=true, hooksInstalled=true, iatSites=111, modules=10`；`no-env` 时 `initReturn=1610`、`initialized=false` —— 说明 `WINSTAGE_STAGE_ROOT` 是必需的）。

### 5.3 把**相对路径**写进子进程的 argv，同时给了它别的 cwd

- 症状：T4 probe 返回 `exit=3` 且不产出 JSON（被误读成"shim 不可用"）。
- 根因：`captureDir` / selftest 输出路径是相对路径，而子进程的 cwd 被设成暂存根 ⇒ 子进程按自己的 cwd 解析 ⇒ 文件写不出来。
- 修复：`runCapturedToFiles()` 内部 `resolve(captureDir)`；`resolveShimArtifacts()`、`probeTransparentShim()`、`ShimLauncher.launch()` 一律使用绝对路径。

### 5.4 `icaclsRun()` 用命名管道捕获（T2 报告，我修）

`out/ac-runtime.txt` 前后对照（同一受限会话）：

| | 旧实现（`stdio:['ignore','pipe','pipe']`） | 新实现（fd 重定向） |
|---|---|---|
| 失败形态 | `EPERM spawnSync icacls EPERM`（恒失败，**与路径无关**） | `exit=2 \\| Successfully processed 0 files…` / `exit=5 \\| …: Access is denied.`（**icacls 真实文本**） |
| 对 T0 的影响 | `attachRuntime()` 恒抛 `T0_UNAVAILABLE`，ACL 授权成功路径完全不可用（`tests/appcontainer-runtime.mjs` §13 只能 SKIP） | 捕获机制恢复；**grant 本身**在本受限会话仍被拒（`/grant` 是 WRITE_DAC 写类操作），需未受限会话复跑才是真 PASS |

同一现象的直接对照：`icacls . > out.txt`（PS 重定向）⇒ 文件 **0 字节**；`runCapturedToFiles('icacls', ['.'])` ⇒ exit=0 + 完整 DACL 文本。

## 7. 未提供的保证 / 残余边界（必须与任何"通过"一起读）

1. **去令牌化模式未在本会话端到端取证**：门 1/2a 实测通过，门 2b/3 被 T4 shim 的真实缺陷挡住（§4）；且本会话自身受限（§1），即使 shim 完美也无法让"启动方受限"的子进程恢复四类能力。**需要在未受限宿主进程里复跑**（Lead 的 `danger-full-access` 会话 + T5 插件宿主侧）。
2. **shim 是用户态 IAT 重定向，不是内核级强制**：未覆盖 `ntdll!Nt*` 直调、`\\?\GLOBALROOT`、`CopyFile2`、`SHFileOperation`/`IFileOperation`、内存映射写入、其它进程代写、`FindFirstFile` 枚举等（T4 清单）。去令牌化模式的**写边界强度低于**受限令牌模式，这一点不得被读成"等价替换"。
3. **shim 的环境契约变量对子进程可见**：`WINSTAGE_STAGE_ROOT` / `WINSTAGE_SHIM_CONFIG` / `WINSTAGE_SHIM_LOG` 出现在沙箱子进程环境里（`envTrace.winstageVars` 如实上报）。任务的硬要求只是"不得有 `DSH_SANDBOX*`"（已满足），但"沙箱痕迹不可见"的更高目标**尚未达成**——建议 T4 在 DllMain 完成初始化后**自删**这三个变量。
4. **去令牌化模式没有 Job Object**：`jobEnabled=false`、进程树回收靠 `taskkill /T /F <injectorPid>`（超时/回收路径），而不是 `KILL_ON_JOB_CLOSE`；注入器自己 `CreateProcess` 出目标，宿主拿不到那个进程句柄。
5. **TLS 的"上网"用例是 informational**：`capability-probe` 的本机 TLS 判据是**回环自连 + SChannel 取凭据**（离线、确定性）；`internetHandshake`（`registry.npmmirror.com`）单独上报、**不参与**退出码与 TS 门 3。
6. **`node/PS` 与 shim 的兼容性缺口未定论根因**：已定位到"钩子生效即失败、`DISABLE` 即恢复"，但**具体哪个 hook** 尚未定位（属 T4）。
7. **平台侧不予修改**：`@deepseek-ai/*` 平台包一字未改（符合约束）。因此"受限令牌模式下三类能力仍失败"是**平台行为的如实转述**，winstage 侧只能通过"不再使用受限令牌"来绕开。
8. **T1 会话限制造就的证据分层**：§2 的"改前"是**平台受限令牌**上的实测（与 winstage T1 同源同构），不是 winstage T1 沙箱内的实测（本会话建不起来，R6）；README §4/§8.3 与 Lead 的 `acceptance-transparent.mjs` 基线可交叉印证。
