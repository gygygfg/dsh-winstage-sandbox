# T3：注册表写入暂存（覆盖 hive + WAL + 候选 + C ABI 契约）

> 模块：`src/registry-stage.mjs`（新建） · 测试：`tests/registry-stage.mjs`（新建）+ `tests/registry-guard.mjs`
> 上游依赖：`src/registry-guard.mjs`（快照/差异/回滚计划/编解码） · 下游消费者：T4 shim DLL、审批面板
> 一句话结论：**把"沙箱内注册表写入被内核硬拒"改成"写进私有覆盖层 → 看到成功 → 冻结候选 → 走审批面板 → 选择性应用/丢弃"**；
> 覆盖层是**逻辑重定向**，不是内核边界 —— 它只覆盖被 hook 的 8 个 `Reg*` 入口，且"写进覆盖层 ≠ 系统生效"。

---

## 1. 问题与定位

### 1.1 现状（`[实测]`，来自 `docs/dsh2-越界与注册表-实测诊断.md` §3）

| 探针 | 结果 |
|---|---|
| `New-Item HKCU:\Software\WinStageProbeTmp` | `UnauthorizedAccessException: Access to the registry key … is denied.` |
| `HKCU:\…\CurrentVersion\Run` 写值 | `SecurityException` |
| `HKLM:\Software\WSP3` | `UnauthorizedAccessException` |

归因证据：`HKCU:\Software` 的 SD 里 `NT AUTHORITY\RESTRICTED` 只有 **`ReadKey`**，
而受限令牌**确含**该 SID ⇒ 拒绝**恰由沙箱的受限令牌引入**，且由内核执行（不是"没捕获"）。

### 1.2 本层做什么 / 不做什么

| | 说明 |
|---|---|
| **做** | 私有覆盖 hive（`RegLoadAppKeyW` 加载）承接写入；写成功、能读回自己写的值；真实 hive 一个字节不动；变更冻结为**与文件候选同构**的候选；可**选择性应用**（宿主令牌）或**丢弃** |
| **不做** | 不做内核级隔离（那是 T0/AppContainer 的活，目前 fail-closed）；不覆盖未被 hook 的 API；不保证"系统认得"覆盖层里的写入（见 §8 语义级残余） |
| **三种结论（v1.4）** | 暂存 / **不可暂存 ⇒ 透传真实 API + `UNSTAGED` 审计记录** / 硬拒。把第二种伪装成 `ERROR_ACCESS_DENIED` 是**已修复的缺陷**（CLR `0x80070005`、node `WSAStartup 10107`）：调用方对 5 无能为力，而真实 API 知道该怎么做。逐条见 §8.0 |
| **与 `registry-guard` 的分工** | `registry-guard` = **检测**（执行前快照 / 执行后差异 / 回滚**计划**，从不阻止写入）；`registry-stage` = **暂存**（写入落到覆盖层 + 候选）。差异算法**复用** `diffSnapshots`，编解码**复用** `normalizeSnapshot` / 新导出的 `encodeRegistryValue` / `decodeRegistryValue`，路径解析**复用** `parseRegistryPath` / `HIVE_CANONICAL`，回滚计划**复用** `planRollback` —— **没有第二套实现** |

### 1.3 为什么"只落盘一个 hive 文件"不够：WAL 是宿主与 DLL 的暗号

覆盖层有两份落盘物：

| 文件 | 作者 | 读者 | 作用 |
|---|---|---|---|
| `overlay.hive` | shim DLL（`RegLoadAppKeyW` 自动创建/加载） | **只有 shim**（app hive 无法用绝对路径访问） | 承载"沙箱内写进去、再读回来"的实时语义（含枚举） |
| `overlay.journal` | shim DLL **先写**（WAL-first） | **宿主**（`replayJournal`） | 宿主据此产出候选，**不需要跨进程 IPC、也不需要宿主去读 hive** |
| `overlay.state.json` | 宿主 | 宿主/面板 | 已解决状态（applied / partially-applied / discarded / candidateId / appliedPaths） |
| `overlay.discarded.journal` | 宿主（丢弃时由 WAL 改名） | 审计 | 丢弃**不销毁**审计轨迹 |

⇒ 宿主侧候选生成的**唯一**输入是 `overlay.journal`，它是一份**跨语言**（C 写、JS 读）的定长记录流，
形状钉死在 §4（字段偏移由 `tests/registry-stage.mjs` 逐字节断言）。

## 2. 覆盖区布局

```
<sessionDir>/                         # = <workspaceRoot>/.dshstage/sessions/<key>（与文件暂存同一 session 目录）
  registry/
    overlay.hive                      # app hive：RegLoadAppKeyW 加载；不存在时自动创建
    overlay.journal                   # WAL：32 字节定长头 + 变长负载，仅追加
    overlay.state.json                # 宿主侧已解决状态
    overlay.discarded.journal         # 丢弃后的 WAL 审计副本
  candidates/<id>.json                # **与文件候选同一个目录**（候选同构，见 §6）
  queue.json                          # **与文件候选同一个待审队列**
```

纯函数（任何会话可离线验证，与权限/偏移无关）：

```js
resolveRegistryStageRoot(sessionDir)          // <sessionDir>/registry
resolveRegistryStagePath(sessionDir)          // <sessionDir>/registry/overlay.hive      ← shim 契约核心
resolveRegistryStageJournalPath(sessionDir)   // .../overlay.journal
resolveRegistryStageStatePath(sessionDir)     // .../overlay.state.json
resolveRegistryStageDiscardedPath(sessionDir)  // .../overlay.discarded.journal
overlaySubKeyFor('HKEY_LOCAL_MACHINE\\Software\\X')  // → 'HKLM\\Software\\X'（映射恒等，只做短名归一）
canonicalFromOverlaySubKey('HKLM\\Software\\X')      // → 同一个字符串（往返恒等）
overlayContainerChain('HKLM\\Software\\X')           // → ['HKLM\\Software','HKLM\\Software\\X']（不含裸 hive 根）
registryValueUnitPath('HKCU\\A', '')                 // → 'HKCU\\A\\@'（未命名/默认值的单元路径约定）
```

**路径映射为什么可以恒等**：覆盖 hive 每个会话独占、其根句柄本身就是 `RegLoadAppKeyW` 的
"特殊根"，所以真实 hive 的根名（`HKLM`）可以直接作为覆盖 hive 的**第一层子键名**，
无需转义（相对路径 `Software\...` 永远不会被当成根键，`parseRegistryPath` 会抛 `REG_HIVE_UNKNOWN`）。

## 3. hive 覆盖的生命周期（`[官方]` 事实 + 本层约定）

官方依据：<https://learn.microsoft.com/en-us/windows/win32/api/winreg/nf-winreg-regloadappkeyw>
（常量数值核对自 winreg.h：`REG_PROCESS_APPKEY 0x00000001`、`REG_USE_CURRENT_SECURITY_CONTEXT 0x00000002`）

| 环节 | 事实/约定 | 后果 |
|---|---|---|
| **创建/加载** | `RegLoadAppKeyW(file, &root, samDesired, REG_PROCESS_APPKEY, 0)`；**文件不存在时会自动创建空 hive** | 不需要先 `RegSaveKey`；空覆盖层可用 |
| **私有性** | hive 挂在**特殊根**下，"无法用绝对路径访问/枚举" | 覆盖层天然私有，不会污染全局命名空间 |
| **多进程** | 两个进程各自调 `RegLoadAppKey` 时，注册表**返回同一个已加载 hive 的句柄**（不会重复加载） | **WAL 必须全局串行**：DLL 内部对 `overlay.journal` 的写入要加锁（`LockFileEx` 或临界区 + `FILE_APPEND_DATA`），否则两条记录会交错 |
| **同进程重入** | `REG_PROCESS_APPKEY` 阻止**同一进程**再次加载同一文件 | `DshRegStageAttach` 必须**幂等**：重复 attach 不得二次 `RegLoadAppKey`（否则返回 `ERROR_SHARING_VIOLATION=32`） |
| **卸载** | **没有** `RegUnLoadKey`；**最后一个句柄 `RegCloseKey` 后自动卸载** | shim 必须关闭它打开过的每一个覆盖层句柄；`DshRegStageDetach` 关根句柄 = 卸载 |
| **安全描述符** | hive 内**所有键必须共享同一个 SD**，否则加载失败；且**禁止**对 hive 内任何键调用 `RegSetKeySecurity` | **SD 变更无法暂存**（硬拒，见 §8） |
| **多 hive** | Windows 8+：每进程可加载多个 app hive（Windows 7 及更早只能一个） | 本机为 Server 血统，按 Win8+ 设计；但**不为多会话复用同一 hive 文件** —— 每个 session 一个文件 |

**Hive 文件的写权限**：`overlay.hive` 只由 shim（沙箱内进程）与宿主读；
由于 app hive 的加载要求调用者对该文件有写权限（`samDesired` 覆盖的访问权由 SD 授予），
建议把 `registry/` 目录的 ACL 授予**沙箱账号**（宿主恒可访问）。这是 T1/T2 的接线范围，本层只约定路径。

## 4. 与 shim（T4）的 C ABI 契约

### 4.1 总体约定

* 调用约定：`__cdecl`（x64 上 `__cdecl` 即 Microsoft x64 单一 ABI；32 位构建同样只用 `__cdecl`，**不要** `__stdcall`）。
* 字符串：`const wchar_t*`，NUL 结尾，UTF-16LE。路径是**真实注册表路径的规范形式**（短 hive 名，如 `HKLM\Software\X`）。
* 返回值：一律 `LSTATUS`（`LONG`，`0 = ERROR_SUCCESS`）；负值不使用，错误码即 Win32 `ERROR_*`。
* 所有缓冲区由**调用方**提供并在返回前保持有效；DLL 不长期持有调用方指针。
* ABI 版本：`DshRegStageAbiVersion()` 返回 `1`；结构体里也有 `version` 字段，二者必须一致。

### 4.2 导出符号（DLL 必须导出，注入器/宿主调用）

```c
/* 内存/ABI 自检：返回 1（本契约版本）。调用方应先比对，不匹配则不要调用其余函数。 */
UINT32 __cdecl DshRegStageAbiVersion(void);

/* 幂等 attach：解析 stageRoot（NULL 时读环境变量 DSH_REGSTAGE_ROOT），
   打开/创建 WAL，加载覆盖 hive。重复调用必须返回 ERROR_SUCCESS 且不二次 RegLoadAppKey。
   返回：0 / ERROR_SHARING_VIOLATION(32) / 其他 Win32 错误 */
LSTATUS __cdecl DshRegStageAttach(const wchar_t* stageRoot, const wchar_t* sessionId);

/* 分离：关闭 WAL 句柄 + RegCloseKey(覆盖 hive 根) ⇒ 最后一个句柄关闭时 hive 自动卸载。
   进程退出前必须调用（否则 hive 变更可能未刷盘）。 */
LSTATUS __cdecl DshRegStageDetach(void);

/* WAL-first 的**唯一**写入原语。
   record->pathChars/nameChars/dataBytes 必须与实际缓冲区长度**一致**；函数会再校验一次。
   实现要求：WriteFile → FlushFileBuffers（追加失败必须让调用方看到失败），
   本函数返回 0 才允许调用方去改覆盖 hive。
   outBytesWritten 可空；非空时写入实际追加的字节数（= 32 + pathChars*2 + nameChars*2 + dataBytes）。 */
LSTATUS __cdecl DshRegStageJournalAppend(const DSH_REG_STAGE_RECORD* record,
                                        const wchar_t* path,
                                        const wchar_t* valueName,
                                        const void* data,
                                        UINT32* outBytesWritten);
```

> **WAL-first 是硬要求**：先追加并刷盘、再改覆盖 hive。反过来会出现
> "调用方看到写入成功、但宿主候选里没有这条变更"的分叉 —— 这正是本项目最忌讳的一类不一致。
> 若追加失败，`Reg*` hook 必须返回该 LSTATUS（**不许**静默成功）。

`DshRegStageState`（可选，T4 自用/注入器自检；**T3 未验证此结构**）：

```c
typedef struct DSH_REG_STAGE_STATE {   /* 32 字节，小端，调用方填 size */
    UINT32 size;              /*  0  调用方填 sizeof(DSH_REG_STAGE_STATE) */
    UINT32 abiVersion;        /*  4  = 1 */
    UINT32 hiveLoaded;        /*  8  1 = RegLoadAppKeyW 成功 */
    UINT32 journalOpen;       /* 12  1 = WAL 句柄已打开 */
    UINT64 rootKey;           /* 16  覆盖 hive 根句柄（仅本进程有效，禁止跨进程传递） */
    UINT32 recordsAppended;   /* 24  本进程已追加的记录数 */
    UINT32 lastStatus;        /* 28  最近一次错误的 LSTATUS */
} DSH_REG_STAGE_STATE;
LSTATUS __cdecl DshRegStageAttachState(DSH_REG_STAGE_STATE* out);
```

### 4.3 WAL 记录结构（**C 与 JS 共享，偏移已被测试钉死**）

```c
#pragma pack(push, 4)
typedef struct DSH_REG_STAGE_RECORD {
    UINT32 magic;        /*  0  'DSRG' = 0x47525344（字节序：44 53 52 47） */
    UINT16 version;      /*  4  必须 = 1 */
    UINT16 kind;         /*  6  1=CREATE_KEY 2=DELETE_KEY 3=SET_VALUE 4=DELETE_VALUE 5=HARD_DENY 6=UNSTAGED */
    UINT16 type;         /*  8  winreg.h REG_* 数值（仅 SET_VALUE 有意义；UNSTAGED 时 = 不可暂存的原因码 1..4，其余写 0） */
    UINT16 flags;        /* 10  位掩码，见下 */
    UINT32 pathChars;    /* 12  UTF-16 码元数（**不含**结尾 NUL） */
    UINT32 nameChars;    /* 16  UTF-16 码元数（不含 NUL） */
    UINT32 dataBytes;    /* 20  原始字节数 */
    UINT32 status;       /* 24  LSTATUS（HARD_DENY 时 = 返回给调用方的值，如 5；UNSTAGED **恒为 0**） */
    UINT32 reserved;     /* 28  必须 = 0 */
} DSH_REG_STAGE_RECORD;  /* 总大小 32 */
#pragma pack(pop)

/* 负载紧跟头部，顺序固定：path(UTF-16LE) → valueName(UTF-16LE) → data(原始字节) */
```

| flags 位 | 值 | 含义 |
|---|---|---|
| `HARD_DENY` | `0x0001` | 这是一条"被拒调用"的记录（不进覆盖层状态，只进审计） |
| `HAS_VALUE_NAME` | `0x0002` | 记录携带 `valueName`。**未命名（默认）值也要置位**（`nameChars = 0` 且此位为 1 ⇒ 默认值）；不置位 ⇒ 该记录没有值名字段 |
| `HAS_DATA` | `0x0004` | 记录携带 `data`（`dataBytes` 可为 0，如零长度 `REG_NONE`） |
| `VOLATILE` | `0x0008` | 调用来自 `REG_OPTION_VOLATILE` 的键（应用时保留该选项） |
| `UNSTAGED` | `0x0010` | 这是一条"**透传真实 API**"的记录（契约 v1.4；不进覆盖层状态、**不可重放**，只进审计） |

`kind` 与字段的对应关系：

| kind | `type` | `nameChars` | `dataBytes` | 说明 |
|---|---|---|---|---|
| 1 `CREATE_KEY` | 0 | 0 | 0 | 允许 DDL：**必须**为路径上的每一级（不含裸 hive 根）各写一条（对齐 `RegCreateKeyExW` 自动建中间键） |
| 2 `DELETE_KEY` | 0 | 0 | 0 | 调用方已确认该键**没有子键**（否则真实 API 返回 1020） |
| 3 `SET_VALUE` | `REG_*` | 见 flags | 原始字节 | `data` 就是 `RegSetValueExW` 的 `lpData`（DWORD 4 字节小端、QWORD 8 字节小端、DWORD_BE 4 字节大端、SZ/MULTI_SZ 含结尾 NUL） |
| 4 `DELETE_VALUE` | 0 | 见 flags | 0 | 删值 |
| 5 `HARD_DENY` | 0 | 0 | 0 | `status` = 返回给调用方的 LSTATUS（**必须非 0**）；`path` 可以是占位名（如 `<unknown:NtSetValueKey>`） |
| 6 `UNSTAGED` | 原因码 1..4 | 0 | 0 | **调用被交给真实 API**（不是拒绝）：`status` 恒为 0、不带值名/数据；`path` 是规范路径（知道时）或占位名（`<unstaged:Api:reason>`） |

**数据字节序**：DLL 直接把系统给它的 `lpData` 原样落盘即可（不需要编解码器）。
宿主侧用 `registryDataHex(type, wireBytes)` / `registryWireBytes(type, dataHex)` 与快照口径互转；
这两条路径的往返（含 `REG_DWORD_BIG_ENDIAN` 的字节序）已由测试断言。

### 4.4 句柄标记与路径映射（DLL 内部约定，hook 必须一致）

1. **句柄分类**：shim 维护一张自己发放的伪句柄表。
   * 伪句柄建议取值 `0xD5D50000 | (slot << 4)`（**最高位为 0**，不会与 `HKEY_*` 预定义常量混淆）；
     但**判定必须查表、不能只看数值区间**（内核句柄是 4 的倍数，数值上不可靠）。
   * 不在表中的句柄 = 真实句柄，按原参数转发给真实 API。
2. **路径映射**：`(hkey 或伪句柄) + lpSubKey` → 规范真实路径
   * 预定义根（`HKCR/HKCU/HKLM/HKU/HKCC`）直接拼；`HKEY_*` 全名归一成短名（与 `HIVE_CANONICAL` 一致）。
   * 伪句柄对应"已打开的覆盖层键"，其路径在发放时记录，后续 `lpSubKey` 追加。
   * 无法解析出规范路径的（原生 API 句柄、`RegConnectRegistryW`、非预定义根）⇒ **不猜路径**：
     **透传真实 API** 并记一条 `UNSTAGED`（kind 6，原因码 `UNRESOLVABLE_BASE_HANDLE=3`）。
     旧行为（硬拒 5）已作废 —— 见 §8.0 与 §8.5（"不可暂存" ≠ "没权限"）。
3. **覆盖层内的键**：在覆盖 hive 根下按 `overlaySubKeyFor(canonical)` 逐级 `RegCreateKeyExW`（容器链见 §2），
   并尽量保持"打开即可用"（缓存句柄，`RegCloseKey` 时释放）。
4. **读语义（`RegQueryValueExW` / `RegEnumKeyExW` / `RegEnumValueW`）**：
   * 先查覆盖层：命中（本会话写过 or 覆盖层里创建过）⇒ 返回覆盖层结果；
   * 覆盖层返回 `ERROR_FILE_NOT_FOUND` ⇒ **回落**到真实 hive（**注意**：受限令牌下真实读取本身是允许的，只有写被拒）；
   * **枚举必须合并（契约 v1.2；旧版"不合并"已作废，见 §11.1）**：`RegEnumKeyExW` / `RegEnumValueW`
     返回 **`覆盖层 ∪ 真实`**：
     1. 取覆盖层里该键的**直接子键名**（跳过内部文件 `values.wsv`）、以及覆盖层记下的值名；
     2. 取真实 hive 的子键/值（用真实键句柄枚举；**覆盖层独有的键没有真实句柄** ⇒ 跳过这一步，见 §11.1 实现要点）；
     3. **同名以覆盖层为准**（大小写不敏感去重，保留覆盖层那一次的写法）；
     4. **白障剔除**：覆盖层记了"删除"的名字（键白障 `__del_<hex>` / 值行 `D|<namehex>|`）从并集里**剔除**；
     5. 结果**按名字排序**（大小写不敏感）—— 保证同一份集合在多次调用间给出**稳定的 index→name 映射**
        （调用方用 `dwIndex` 递增枚举，集合顺序一变就会漏项/重复）；
     6. 末尾返回 `ERROR_NO_MORE_ITEMS(259)`；`cchName`/`cbData` 不足返回 `ERROR_MORE_DATA(234)`。
   * **为什么这条是硬的**（`[实测]`，见 §11.1）：只列覆盖层会让一个"打开或创建"留下的**空壳键**
     把它真实父键下的成千上万个子键全部遮掉 ⇒ .NET 证书存储读空 ⇒ PowerShell 起不来。
5. **写语义**：`journalRecordForOperation` 的记录形状（§4.3）→ `DshRegStageJournalAppend` → 覆盖 hive 写入。
   * `RegCreateKeyExW` 的 `lpdwDisposition`：`REG_CREATED_NEW_KEY=1` / `REG_OPENED_EXISTING_KEY=2`，按覆盖层现状填。
   * **净变化原则（契约 v1.2）**：真实 hive 里**已存在**的键，`RegCreateKeyExW` / `RegOpenKeyExW`
     **不得**产生覆盖层条目、**不得**写 WAL 记录；只有真实 hive 里没有的新键才记 `CREATE_KEY`。
     逐条规则与理由见 §11.2（这条与文件侧"内容与基线相同 ⇒ 不入候选"同一纪律）。
   * `RegDeleteKeyExW` 有子键 ⇒ 返回 `ERROR_KEY_HAS_CHILDREN(1020)`（**不要**去删整棵子树）。
   * `RegSetValueExW` / `RegDeleteValueW` 键不存在 ⇒ `ERROR_FILE_NOT_FOUND(2)`。
6. **SD 相关**：`RegSetKeySecurity` 一律硬拒（覆盖层不支持，且真实调用在受限令牌下也会被拒）。
7. **裸 hive 根的特别约定**：`RegOpenKeyExW(HKCU, NULL/"")` 这类调用**不得**记 `CREATE_KEY HKCU`
   （预定义根永远存在 ⇒ 净变化为零），直接透传真实根句柄即可。裸根的 `delete-key` 语义上非法
   （宿主侧抛 `REG_STAGE_ROOT_READONLY`）。**在根键上写值/删值**（`RegSetValueExW(HKCU, ...)`）在真实 API 上
   合法、但覆盖层里"根"不是可写路径 ⇒ 记 `UNSTAGED`（原因码 `BARE_HIVE_ROOT=4`）并透传（契约 v1.4）。

## 5. 宿主侧 API（`createRegistryStage`）

```js
const stage = createRegistryStage({
  sessionDir,                 // 必填：<workspaceRoot>/.dshstage/sessions/<key>
  sessionId,                  // 可选：写进候选，面板按会话聚合
  reader,                     // 必填（除纯 staging 外）：**宿主令牌**下的读取器（createRegistryReader(bindings)）
  writer,                     // 可选：应用候选时用（createRegistryWriter(bindings)）；不传则 apply() 抛错
  now, workspaceRoot,         // 可选：注入时钟与面板要用的工作区根
})

stage.open()                  // 建目录、解析已有 WAL（支持撕裂尾部）、恢复 overlay.state.json
stage.snapshot(path?)         // 带路径 → 覆盖层视图；不带 → 所有被触碰路径的 { baseline, overlay }
stage.diff()                  // 基线 vs 覆盖视图的 diffSnapshots（复用），返回 { changes, roots, unreadable, warnings }
stage.freezeCandidate()       // → { enqueued, candidate }（写 candidates/<id>.json + queue.json）
stage.apply({ paths?, force?, writer? })   // 选择性应用（宿主令牌，逐条重放 WAL）
stage.discard({ reason? })    // 清覆盖层 + 删 hive + WAL 改名留审计

stage.stageCreateKey / stageDeleteKey / stageSetValue / stageDeleteValue   // 宿主侧参考实现（与 DLL 同一份 WAL 协议）
stage.readKey / readValue / enumKeys / enumValues                          // shim 查询语义的参考实现
stage.setReader / setWriter / getState / getResolution / getCandidate / hardDenials
```

关键语义（都有断言）：

| 行为 | 语义 |
|---|---|
| `stageSetValue` 到不存在的键 | 抛 `REG_STAGE_KEY_NOT_FOUND`（LSTATUS 2，对齐 `RegSetValueExW`） |
| `stageDeleteValue` 到不存在的值 | 抛 `REG_STAGE_VALUE_NOT_FOUND`（LSTATUS 2） |
| `stageDeleteKey` 有子键 | 抛 `REG_STAGE_KEY_HAS_CHILDREN`（LSTATUS **1020**） |
| `delete-key` 后 `create-key` | 得到**空键**（基线里的值不复活），后代一律不存在 |
| 键名/值名 | **不区分大小写**（注册表语义），保留写者给的最后一种大小写 |
| `apply()` 无 writer | 抛 `REG_WRITER_MISSING`（**绝不**假装应用成功） |
| `apply()` 冻结后真实 hive 变了 | 该单元标 `stale` 且**不写**；`force: true` 才覆盖 |
| `apply()` writer 返回非 0 | 记 `failed` + 原始 LSTATUS（旧沙箱硬拒的形态被如实保留） |
| 同候选内对同一键的后续写入 | 成功写入后刷新该键的冻结基线（否则会被**我们自己的**写入误判 stale）。**代价**：同一候选内对同一键的两次写入之间发生的外部改动不会被 stale 捕获（已如实声明） |
| 基线读不到（`accessDenied`） | `diff()` 把它放进 `unreadable` 且**不产出差异**；`freezeCandidate()` 拒绝冻结该路径（`reason: 'no-freezable-change'` + warning）。候选必须冻结**可验证的 before**（手册 #12.6） |
| `discard()` 后 `apply()` | 抛 `REG_CANDIDATE_DISCARDED` |

## 8. **仍然是硬拒**清单（逐条；`REGISTERED_HARD_DENIALS` 是它的可执行版本）

> 词义：**硬拒** = 返回 `ERROR_ACCESS_DENIED(5)`，调用方**必须**看到失败。
> 与"语义级残余"区分：后者调用**成功**，但真实系统不认（见 8.6）。
> 与"不可暂存 ⇒ 透传"区分：后者**既不是**暂存成功**也不是**被拒（见 8.0）。

### 8.0 三种结论（契约 v1.4；**这是本节最容易写错的地方**）

| 结论 | 什么时候 | 返回给调用方 | WAL |
|---|---|---|---|
| **暂存** | 覆盖层能忠实复现这次调用 | 成功（覆盖层语义） | 操作记录（kind 1..4） |
| **不可暂存 ⇒ 透传** | 覆盖层**复现不了**这次调用（32 位视图、路径不可派生、根键上的值写入） | **真实 API 的返回值** | `UNSTAGED`（kind 6，含原因码；**不进状态、不可重放**） |
| **硬拒 fail-closed** | 暂存**能**做、但做失败会泄漏/失配（附录：见下） | `ERROR_ACCESS_DENIED(5)` | `HARD_DENY`（kind 5，带真实 LSTATUS） |

为什么必须分开（`[实测]` 2026-09-30）：把"沙箱表示不了"伪装成 `ERROR_ACCESS_DENIED`
让 `RegCreateKeyExW(..., KEY_WOW64_64KEY)` 去建一个**还不存在**的键时返回 5 ——
CLR 把它变成 `0x80070005`（"Starting the CLR failed"）、node 变成 `WSAStartup 10107`。
调用方对 5 无能为力（它没有别的 API 可用），所以那不是一个"权限"答案，而是一个**我们的实现细节**泄漏。

**fail-closed 只保留在这些情况**（逐条可执行，见 §S2）：
覆盖层完全没挂上（`DshRegStageAttach` 失败 ⇒ 既不能暂存也没有日志可记）、
`HKEY_PERFORMANCE_DATA`（无后备配置单元文件）、
以及 WAL 追加 / app hive 写入失败（暂存得了却写不成 ⇒ 放过就是真实 hive 与候选分叉）。

> **`WINSTAGE_UNSTAGED_WRITES` 的现状（诚实声明）**：那个环境开关（`1=deny`（默认）/`2=passthrough`）
> 原本是"不可暂存时要不要放过"的逃生门。v1.4 之后，**不可暂存那一类默认就是透传**（这是本节的结论），
> 于是该开关在注册表层**不再改变任何判定**（`ws_util.c` 仍会解析它，`ws_reg.c` 不再读它）。
> 也就是说：**没有**"把所有不可暂存都退回硬拒"的开关了 —— 想要旧行为只能改代码。
> 保留 fail-closed 的三类见上（它们不是"表示不了"，而是"根本没有沙箱"或"暂存本身失败了"）。

### 8.1 hive 级

| hive | 理由 |
|---|---|
| `HKPD`（= `HKEY_PERFORMANCE_DATA`） | 性能计数器伪 hive，**没有后备配置单元文件**，没有可挂载覆盖层的位置（**读**照旧透传） |

`HKEY_PERFORMANCE_TEXT` / `HKEY_PERFORMANCE_NLSTEXT`（`0x80000050` / `0x80000060`）连
`registry-guard` 的 `HIVE_HANDLES` 都没有 ⇒ `parseRegistryPath` 抛 `REG_HIVE_UNKNOWN` ⇒ 同样硬拒。

### 8.2 API 级（覆盖层语义无法忠实复现，一律 fail-closed；共 25 条）

`RegSetKeySecurity`（app hive 内全键共享同一 SD 且禁止调用）、
`RegLoadKey` / `RegUnLoadKey` / `RegSaveKey` / `RegSaveKeyEx` / `RegRestoreKey` / `RegReplaceKey`（整棵 hive 操作）、
`RegRenameKey`、`RegCopyTree`、
`RegCreateKeyTransactedW` / `RegDeleteKeyTransactedW` / `RegOpenKeyTransactedW`（事务语义不可模拟）、
`RegConnectRegistryW` / `RegConnectRegistryExW`（远程 hive）、
`RegOverridePredefKey` / `RegOpenUserClassesRoot` / `RegOpenCurrentUser`（另一层"预定义键重定向器"）、
以及原生 API：`NtCreateKey` / `NtOpenKey` / `NtSetValueKey` / `NtDeleteKey` / `NtDeleteValueKey` 与 `Zw*` 别名。

**任何不在被 hook 的 8 个 API 之内的调用**同样硬拒（`REG_STAGE_API_NOT_HOOKED`）：
白名单比黑名单诚实 —— 新 API 默认是"不覆盖"，而不是"悄悄放过去写真实 hive"。

### 8.3 选项/掩码级

| 位 | 结论 | 理由 |
|---|---|---|
| `REG_OPTION_CREATE_LINK` | 硬拒 | 覆盖层没有"链接键"对象；暂存会把链接变成普通键 |
| `REG_OPTION_BACKUP_RESTORE` | 硬拒 | 绕过 ACL、改变句柄语义，不可忠实复现 |
| `REG_OPTION_OPEN_LINK` | 硬拒 | 要求打开链接本身，覆盖层没有链接对象 |
| `KEY_WOW64_64KEY` | **64 位进程里是 no-op**（不拒、不是视图请求 ⇒ 走正常暂存）；WOW64 进程里才是真视图 ⇒ **透传** | `[官方]` winreg.h：64 位进程里该位无效果。把它当硬拒正是"新建键拿到 5"的根因 |
| `KEY_WOW64_32KEY` | **透传**（`UNSTAGED`，原因码 1） | 指向**另一个 hive 位置**（32 位视图）；app hive 没有视图概念 ⇒ 暂存会写错地方。但真实 API 知道那是哪里 ⇒ 交给它 |

对应实现：`REG_STAGE_HARD_DENY_SAM` **现在为空**（视图位不再是权限问题），
`REG_STAGE_UNSTAGED_SAM` 描述这两个位的透传语义；shim 侧只有**一个**判定函数
（`ws_reg_wow64_unrepresentable()`），创建/打开/写入路径共用它 —— 旧版 `ws_create_key()`
自己拿**原始掩码**判"受限"，于是同一个位在读路径是 no-op、在创建路径是硬拒（两套规则，两套 bug）。

### 8.4 值类型级（合法类型但无编解码器）

`REG_LINK(6)`、`REG_RESOURCE_LIST(8)`、`REG_FULL_RESOURCE_DESCRIPTOR(9)`、`REG_RESOURCE_REQUIREMENTS_LIST(10)`。
静默当成 `REG_BINARY` 会把语义改掉 ⇒ 抛 `REG_TYPE_UNSUPPORTED`。
（**受支持**的 8 种：`REG_NONE` / `REG_SZ` / `REG_EXPAND_SZ` / `REG_BINARY` / `REG_DWORD` /
`REG_DWORD_BIG_ENDIAN` / `REG_MULTI_SZ` / `REG_QWORD`。零长度 `REG_NONE` 合法。）

### 8.5 路径/句柄级

* 无法从**预定义根**派生出规范路径的句柄（原生 API 句柄、`RegConnectRegistry` 句柄、跨进程传递的裸句柄）
  ⇒ **不猜路径**：透传真实调用 + `UNSTAGED`（原因码 `UNRESOLVABLE_BASE_HANDLE=3`）。
  （旧版是 `REG_STAGE_ROOT_UNKNOWN` 硬拒 5；**纯层**仍然拒 —— 纯层没有任何真实句柄可以转发，
  它连"这个句柄是谁"都不知道，"不猜"在那里只能表现为拒绝。真实 API 由 shim 转发。）
* 裸相对路径（`Software\X`）⇒ `REG_HIVE_UNKNOWN`（**不猜**根键，猜错会让快照悄悄记错位置）。
* **根键上的值操作**（`RegSetValueExW(HKCU, ...)` / `RegDeleteValueW(HKCU, ...)`）：真实 API 上合法，
  覆盖层里根不是可写路径 ⇒ 透传 + `UNSTAGED`（原因码 `BARE_HIVE_ROOT=4`）。

### 8.5.1 `UNSTAGED` 记录（kind 6）为什么**不能**被重放

`UNSTAGED` 描述的是"这次调用**已经被交给真实系统**"。把它当覆盖层操作重放 = **双重写入**
（真实 hive 已经改过一次）。因此实现上它是**结构性**隔离的，而不是靠调用方自觉：

* `replayJournal()` 把 kind 6 收进 `unstaged[]`，**不放进 `state.ops`**；
* 候选（`diffOverlay`）与应用单元（`applyUnits()`）都只读 `state.ops` ⇒ 候选/`apply()` 里不可能出现它；
* `validateJournalBuffer()` 对 kind 6 额外要求：置 `UNSTAGED` 位、`type` ∈ 1..4、`status == 0`、
  不带值名/数据 —— 少一条就判红（"透传"与"暂存成功/硬拒"混在一起正是这条契约要消灭的歧义）。
* **载体完整性级别的注意**：仓库目录（`...\Desktop\WinStageSandbox`）带 **Low 强制完整性标签**，
  于是仓库里构建出来的 exe 也是 Low ⇒ 载体一启动就是 Low IL ⇒ 内核的 no-write-up 会拒绝**任何**
  真实 hive 写入 ⇒ 透传看起来"没生效"。`tools/build-shim.mjs` 现在会把产物标签修回 Medium
  （构建日志里有一行 `integrity: repaired a Low mandatory label...`），
  `tests/registry-unstaged-wow64.mjs` 则把 injector/DLL 复制到 `%TEMP%`（无标签）再跑，
  从而让"真实 hive 真的变了"成为可判定的事实（而不是被 IL 拦掉的假阴性）。

### 8.6 **语义级**残余（调用成功，但系统不认 —— 最容易粉饰的一类）

1. 覆盖层**只**影响被 hook 的 8 个 `Reg*` 调用。`NtSetValueKey`/`ZwSetValueKey`、直接写
   `C:\Windows\System32\config\*` / `NTUSER.DAT`、**未注入**的 `reg.exe`/`regedit`（含 `.reg` 导入）
   照样命中真实 hive —— 在受限令牌下照样是**原始的内核硬拒**（也就是本次要解决的问题本身）。
2. **写进覆盖层 ≠ 系统生效**：服务/COM/驱动/启动项读的是真实 hive。
   `HKCU\...\Run` 写进覆盖层**不会**真的开机自启；沙箱内程序自洽（写进去、读回来），系统层面什么都没有。
3. **安全描述符**变更无法暂存（app hive 全键共享一个 SD，且禁止 `RegSetKeySecurity`）。
4. `HKEY_USERS\<其他用户>` 的候选**可以**冻结，但应用需要加载对方 hive（管理员），否则 `apply` 如实报失败。
5. `REG_OPTION_VOLATILE` 键在覆盖层里是**文件型** hive，"重启即失"要等应用时按 volatile 选项重建才成立。
6. **读取面没有被覆盖**：覆盖层只覆盖"本会话暂存过的路径"，其他读取仍走真实 hive
   （受限令牌下可能读不到 —— 与 `registry-guard` 记录的读取面残余同源）。
7. **合并枚举下的残余**（v1.2；旧的"枚举不合并"条目已删除 —— 它不再成立，而且是**错的**）：
   * 并集只能剔除**被显式记过删除**的名字；覆盖层无法表达"真实侧某个名字不存在"以外的信息。
   * 并集顺序是**按名字排序**，不是真实 hive 的枚举顺序：依赖"注册表原始顺序"的程序会看到不同的顺序
     （真实 API 本身也不保证顺序，但这里更明显）。
   * 枚举期间真实键若被并发增删，`dwIndex` 递增过程可能**跳过或重复**某个名字
     （单次调用内先取快照再排序，已把窗口缩到最小）。
8. 同一候选内、对**同一键**的两次写入之间发生的外部改动，不会被 stale 检查捕获（见 §5 表格最后两行）。
9. **同值写入不入候选**：净变化为零的 `RegSetValueExW`（类型与数据都与现值相同）不会进 WAL/候选，
   因此真实键的"最后写入时间"变化不会被暂存（与文件侧"内容相同不入候选"一致，属**有意**取舍）。
10. **shim 侧不重放自己的 WAL**（`[实测]`，T4 明确声明）：DLL 目前**不解析** `overlay.journal`
    （未实现 `replayJournal`）⇒ `RegDeleteKeyExW` / `RegDeleteValueW` 的白障只是**进程内 tombstones**，
    跨进程或 shim 重启后**丢失**：journal 里确实有 `DELETE_*` 记录、宿主侧算得对（§5/§6 的 diff 与候选正确），
    但 shim 自己重启后的读视图会**漏掉删除**（把已删的键/值又读出来）。
    这是**跨边界不一致**（同一份 WAL，宿主的"会话终态"与 shim 的"重启后视图"分歧），
    而不只是 shim 内部细节 —— 因此必须写进"未提供的保证"，并且下一轮由 DLL 在
    `DshRegStageAttach` 时按与宿主同一套语义重放 journal（`create`/`set` 覆盖、`delete` 建白障）。见 §14 第 1 条。

## 9. 验证（怎么复跑、断言了什么）


## 11. 契约 v1.2：枚举合并 + 净变化原则（**实测驱动的契约变更**）

### 11.1 变更一：枚举必须合并（作废旧的"v1 不合并"）

`[实测]`（Lead，未受限会话，注入 shim 跑真实 `powershell.exe`）：

```
覆盖层:  reg\HKEY_CURRENT_USER\Software\Microsoft\SystemCertificates\CA\Certificates   ← 空壳（无 values.wsv）
真实 hive: HKCU\Software\Microsoft\SystemCertificates\CA\Certificates 子键数 = 1
          HKCU\Software\Microsoft\SystemCertificates 子键: CA, Disallowed, MY, Root, ...
后果: 枚举 HKCU\Software 只返回覆盖层里的两个子键 ⇒ 真实 Software 下成千上万子键全部消失
      ⇒ .NET 证书存储读空 ⇒ The type initializer for 'System.Management.Automation.Runspaces.
        InitialSessionState' threw an exception ⇒ childExitCode = 0xFFFF0000
```

**这是阻塞级的**：任何 shell 命令都是 PowerShell 子进程。因此：

* 旧契约里"枚举 v1 不合并"**作废**（它不仅是"简化"，而且是**错的**）；§8.6 的对应残余条目**删除**，
  换成"合并枚举下的残余"（顺序稳定但非原始顺序 / 并发增删可能跳过或重复）。
* 合并算法（DLL 实现要点，逐步对齐 §4.4.4）：
  1. **先在覆盖层取一次快照**（名字集合 + 白障集合），再取真实侧；两次读之间不重入自己的 hook
     （DLL 自己的 Win32 调用不打自己的 hook，见 `ws_util.c` 的不变量注释）。
  2. 覆盖层侧：列目录得子键名（跳过 `values.wsv`）；解析 `__del_<hex>` 白障 → **删除集合**；
     值侧读 `values.wsv` 行：`S|<namehex>|<type>|<datahex>` 是值，`D|<namehex>|` 是**值白障**。
  3. 真实侧：**只有"这个键在真实 hive 里存在"时才能枚举**。伪句柄必须记住
     `realKey`（真实键句柄）或 `realExists`（创建时是否已存在），否则只能枚举覆盖层那一半 ——
     这一点是"空壳键遮蔽真实子键"的根因，必须在句柄表里带上。
  4. 合并：`union = overlay ∪ real`；**同名以覆盖层为准**（大小写不敏感）；再 `minus whiteouts`；
     最后**按名字排序**（大小写不敏感，稳定比较器）。
  5. 错误码：末尾 `ERROR_NO_MORE_ITEMS(259)`；`cchName`/`cbData` 不足 `ERROR_MORE_DATA(234)`；
     `lpName`/`lpType` 可为 NULL（只问长度）时必须只回长度。
  6. **一致性**：任何报告"数量/最大长度"的 API（`RegQueryInfoKeyW`）必须与合并枚举**同源**计算，
     否则调用方会把数量当循环上界，得到截断或越界。
* 宿主侧参考实现与断言：`overlayView` / `overlayEnumKeys` / `overlayEnumValues`
  （`src/registry-stage.mjs`）已经就是合并语义；S11 的 5 条断言 + 变异体自证把它钉住。

### 11.2 变更二：净变化原则（"打开或创建"不得造空壳）

真实 hive 里**已存在**的键，`RegCreateKeyExW` / `RegOpenKeyExW` **不得**产生覆盖层条目、不得入候选。
判据（宿主参考实现：`classifyOverlayNetEffect` / `filterOverlayNetOperations`）：

| 操作 | 何时是 **no-op**（不写 WAL、不进覆盖层、不进候选） |
|---|---|
| `create-key` | 真实（或本次 WAL 到此为止的视图里）**已存在**该键 |
| `create-key` | 目标是**裸 hive 根**（永远存在） |
| `delete-key` | 视图里**不存在**该键 |
| `set-value` | 类型与数据都与现值**逐字节相同** |
| `delete-value` | 值不存在 |
| 任意 | 基线**读不到**（`accessDenied`）⇒ 不是 no-op 而是**失败**（`REG_BASELINE_UNREADABLE`/5）：分不清打开还是创建时不许猜 |

* `create-key` 的**容器链**同样按此过滤：`HKCU\Software\Microsoft\SystemCertificates` 在真实 hive 里
  已存在 ⇒ 只为真正新增的层级写 `CREATE_KEY`（S11 断言：`HKCU\Software` 与 `...\Microsoft`
  不得出现在 WAL 里）。
* **候选侧**：宿主 `diff()` 本来就是净变化（基线 vs 覆盖视图），因此只读路径不会产生幻影条目；
  `apply()` 另外只应用**候选里冻结过**的单元（`reason: 'not-in-candidate'`），
  即使 DLL 的 WAL 里有 no-op 记录，也绝不会被重放到真实 hive。
* 代价（如实声明）：同值写入的"最后写入时间"变化不入候选（§8.6 第 9 条）。

## 13. `apply()` 的真实副作用、事务性程度与回滚状态（**如实标注**）

### 13.1 真实副作用（逐步）

`apply()` 是**唯一**会碰真实 hive 的入口；它按候选冻结的单元**逐条**调用真实 API（宿主令牌下）：

1. `create-key` → `RegCreateKeyExW`（`dwOptions` 保留 `REG_OPTION_VOLATILE`）；
2. `set-value` → `RegSetValueExW`（数据是 WAL 里的**原始字节**，类型用 winreg 数值）；
3. `delete-value` → `RegDeleteValueW`；
4. `delete-key` → `RegDeleteKeyExW`（父键句柄 + 子键名）。

顺序：**按 WAL 顺序重放**（`applyUnits()`），因此"先建父键、再写值"这种真实依赖天然成立。
每次成功写入后刷新该键的冻结基线（否则会被自己的写入误判 stale，见 §5 表格）。
`apply()` **只应用候选里冻结过的单元**：WAL 里净变化为零的记录（"打开或创建"命中真实已有键、
同值写入等）`reason: 'not-in-candidate'` 进 `skipped`，**不会**被重放到真实 hive。

### 13.2 事务性程度：**没有事务**（部分失败会留下部分写入）

这是**有意**的、也是必须写清楚的：`Reg*` 没有可用的跨键事务，
`apply()` 逐单元独立执行，**不会**在失败时自动撤销已成功的单元。终态如实反映在返回值里：

| 结果字段 | 含义 |
|---|---|
| `applied[]` | 已成功写入真实 hive 的单元（**真实生效**） |
| `failed[]` | writer 返回非 0 LSTATUS 的单元（带原始状态码；旧沙箱硬拒的形态被保留） |
| `stale[]` | 冻结后真实 hive 变了、拒绝写入的单元（候选的 before 已失效） |
| `blocked[]` | 父键不存在且其 `mkdir` 单元未被应用（`status=2`，见 §13.3） |
| `skipped[]` | `not-in-candidate` / `not-selected` / `already-applied` |
| `status` | `applied` / `partially-applied` / `stale`（会话状态另存 `overlay.state.json`） |

**部分失败 = 真实 hive 处于"部分应用"状态**，需要人工按 §13.4 的计划处理。
要"全有或全无"，只有三条路：① 让候选只包含一个单元；② 调用方先备份真实键值；
③ 在真实 API 层面用事务 API（本层对事务 API 一律硬拒，见 §8.2 —— 覆盖层不假装原子性）。

### 13.3 父键依赖（契约 v1.3）

`RegSetValueExW` / `RegDeleteValueW` / `RegDeleteKeyExW` 都要求目标键存在。当审批者**只勾选子单元、
没勾选父键的 `mkdir`** 时，`apply()` **如实失败**：

* 结果进 `blocked[]`，`status = ERROR_FILE_NOT_FOUND(2)`，
  `reason` 是 `parent key <path> does not exist in the real hive and its create-key unit was not applied ...`；
* 判定依据：该键要么在真实 hive 里本来就有，要么**由本次 apply 的 `create-key` 单元刚建出来**
  （后者按顺序天然成立）；
* **绝不**替调用方静默补建一个没被批准的键（那等于应用了未审批的单元）。
* 反过来说：同一个候选里"先只批准 mkdir、再批准值单元"是**可以**分两步完成的，`blocked` 不是永久拒绝。

### 13.4 回滚：**只有计划，没有执行器**（本轮未提供自动回滚 API）

* `diff()` 为每个 root 产出 `planRollback()` 计划（每个操作带 `reversibility`：
  `exact` / `lossy` / `impossible`，并统计数量与 warnings）。
  `impossible` 的项**不会被藏起来**（例如"键被删除"只能重建空键，内容不可恢复）。
* **`registry-stage` 不提供"执行回滚"的 API**：谁执行、何时执行、是否要再走一次审批，
  属于调用方（面板/宿主）的决策。这一点必须如实读作：
  **"回滚目前只是计划"**，不是"已支持回滚"。
* 计划本身的**可用性**由 `tests/registry-apply-e2e.mjs` 在真实 hive 上验证：
  用例在 apply 之后**按计划手工执行**（delete-value → delete-key 深→浅 → set-value 还原），
  并断言真实键恢复到 apply 前的状态（键不存在）。**注意**：执行发生在**测试里**，
  不是产品能力 —— 它证明的是"计划够用"，不是"有自动回滚"。
* 安全阀：用例在执行计划前拒绝任何**浅于三级**的路径（例如 `HKCU\Software`），
  以免误删系统键；命中即判红且不执行。

### 13.5 真实 hive 端到端证据（`tests/registry-apply-e2e.mjs`）

```powershell
node tests\registry-apply-e2e.mjs     # ⚠ 会临时写真实 HKCU；**不在 verify.cmd 里**（离线套件不碰真实注册表）
```

| 退出码 | 含义 |
|---|---|
| `0` | 在真实 hive 上全部断言通过（P1 正例 + P1b 回滚计划 + P2 选择性依赖 + P4 清理） |
| `1` | 有断言失败，或**清理失败**（清理失败也是失败：不许留残留） |
| `2` | **未验证**：会话受限（写注册表被拒）/ 无可写后端 / 探针键已被别人占用 —— 打印大写 NOT VERIFIED，**这不是通过** |

* 被测键：`HKCU\Software\WinstageShimProbe`（与 T4 闭环节 runner 同一个键）。
  用例先确认它**不存在**（或只含 `t4-probe-*` 形状的自家残留，才允许清理后继续），
  **拒绝覆盖既有数据**；`finally` 里删除并**回读验证**已恢复原状。
* WAL 来源：优先最新一份 `shim/.stage/run-*/registry/overlay.journal`（**真实产物字节**）；
  找不到时用本层编码器造一份**同布局**的日志，并在输出里标明 `WAL 来源 = synthesized`。
* 后端：读取器恒用 `reg.exe`（独立于写入器）；写入器优先 koffi 的
  `createRegistryWriter(bindings)`，koffi 不可用时退化到 `reg.exe` 后端。两者都由同一个
  `stage.apply()` 驱动，因此"真实副作用"的结论不依赖 FFI。
  `reg.exe` 后端的已知限制：无法表达 `REG_MULTI_SZ` / `REG_NONE`（命令行参数带不了内嵌 NUL），
  遇到时抛 `REG_E2E_BACKEND_UNSUPPORTED` 并提示用 koffi。
* **变异体自证**（P3，纯判定，任何会话都能跑）：把同一判定器喂给
  ① apply 变成 no-op、② 编码/长度写错、③ apply 前键已存在 —— 三种都必须判红；
  因此"apply 后逐字节相等"这条断言**有判定力**，不是永远绿的装饰。
* `[实测]` 状态：**T3 的本机会话是受限的**（`reg add` → `Access is denied`，exit 5），
  因此这里跑出来是 `exit 2 / NOT VERIFIED`（P3 变异体自证通过）。
  **真实 hive 的 apply 证据需要在未受限会话里由 Lead 复跑**，本文件不假装已经验过。
